# How gocpp maps to C++

This document shows what the C++ output of gocpp looks like: how types, names, functions,
methods, structs, multiple results and package initialization are written in C++.

| | |
|---|---|
| Status | v0, written in Phase 00 from the plan. Later phases extend it ([what is still missing](#later-phases-extend-this-document)) |
| Source | the type table in the [root README §6](../../plans/2026-10-13-gocpp/README.md#6-type-mapping-cheat-sheet), and the Phase 02, 03 and 06 READMEs linked below |
| See also | [language.md](language.md) (the language), [interop.md](interop.md) (C and C++ values) |

The C++ here is simplified, as in the plan. The real output also has a `#line` directive before
most generated lines ([`#line` and debugging](#line-and-debugging)). The output is plain C++20 for
GCC 13+ and Clang 17+. All gocpp runtime types and helpers live in the namespace `gp`.

## A first example

```go
// hello.gp
package main

import "fmt"

func add(a, b int) (int, bool) {
	return a + b, a+b > 10
}

func main() {
	s, big := add(7, 5)
	fmt.Println("hello, gocpp", s, big)
}
```

`gocpp emit hello.gp` prints:

```cpp
// hello.gp.cpp: generated by gocpp, do not edit
#include <gocpp/rt.hpp>

namespace gpkg_main {

std::tuple<int64_t, bool> add(int64_t a, int64_t b);   // prototypes first:
void main();                                           // Go doesn't care about order, C++ does

#line 6 "/home/me/hello/hello.gp"
std::tuple<int64_t, bool> add(int64_t a, int64_t b) {
#line 7 "/home/me/hello/hello.gp"
    return {a + b, a + b > 10};
}

#line 10 "/home/me/hello/hello.gp"
void main() {
#line 11 "/home/me/hello/hello.gp"
    auto gp_t0 = add(7, 5);
#line 11 "/home/me/hello/hello.gp"
    int64_t s = std::get<0>(gp_t0);
#line 11 "/home/me/hello/hello.gp"
    bool big = std::get<1>(gp_t0);
#line 12 "/home/me/hello/hello.gp"
    gp::fmtshim::Println("hello, gocpp"_gs, s, big);
}

} // namespace gpkg_main

int main(int argc, char** argv) {
    return gp::run_main(argc, argv, nullptr, &gpkg_main::main);
}
```

This is the Phase 02 output, when `fmt` is still a small stand-in (`gp::fmtshim`) and there is no
package init yet, so `run_main` gets `nullptr` as its init function. From Phase 06 on, it gets
`&gp_init_all` ([package initialization](#package-initialization)).
Source: [Phase 02 §2.1](../../plans/2026-10-13-gocpp/phase-02-walking-skeleton/README.md#21-example).

## Types

| gocpp (`.gp`) | Generated C++ | Notes |
|---|---|---|
| `int`, `uint` | `int64_t`, `uint64_t` (64-bit targets, like Go) | gocpp has only 64-bit targets ([D9](language.md#d9-64-bit-targets-only)); signed overflow wraps as in Go, because all C++ is compiled with `-fwrapv` |
| `int8` … `int64`, `uint8` … `uint64`, `uintptr` | `int8_t` … `int64_t`, `uint8_t` … `uint64_t`, `uintptr_t` | results of `int8`, `int16`, `uint8` and `uint16` arithmetic are cast back (`uint8_t(a + b)`), because C++ turns these types into `int` first |
| `byte`, `rune` | `uint8_t`, `int32_t` | in Go too, `byte` is `uint8` and `rune` is `int32` |
| `float32`, `float64`, `complex64`, `complex128` | `float`, `double`, `std::complex<float>`, `std::complex<double>` | compiled with `-ffp-contract=off`, so the C++ compiler doesn't fuse floating-point operations |
| `bool` | `bool` | the same type in both languages |
| `string` | `gp::string` (immutable bytes, usually UTF-8; cheap substrings) | 32 bytes: owner, data pointer, length. A literal `"hi"` becomes `"hi"_gs` and points at static storage (no allocation); `s[a:b]` shares the bytes |
| `[N]T` | `gp::array<T, N>` (value type, bounds checked) | wraps `std::array`; assignment copies it, as in Go; `==` exists when the elements are comparable |
| `[]T` | `gp::slice<T>` | 40 bytes: owner, data pointer, length, capacity; `append` grows like Go, but gocpp only promises `cap >= len`, not Go's exact capacity |
| `map[K]V` | `gp::map<K, V>` (reference type) | a shared pointer to the table (v1 wraps `std::unordered_map`); reading a missing key gives the zero value and never inserts |
| `*T` where `T` is a gocpp type | `gp::ptr<T>` (reference counted, nil-checked) | a `std::shared_ptr<T>` with nil checks; a nil dereference panics with Go's message ([pointers](#pointers-and-boxing)) |
| `*pkg.T` where `T` is a C/C++ type (`*SDL.SDL_Window`, `*cstdio.FILE`) | `T*` (raw pointer, C++ rules) | not reference counted; it follows C++ lifetime rules ([interop.md](interop.md#cc-types-in-gocpp-code)) |
| `unsafe.Pointer` | `gp::ptr<void>` (keeps a gocpp object alive, like Go) | shares the owner of the object it came from, and converts to `void*` for C ([D16](language.md#d16-unsafepointer-and-pointers-from-c)) |
| `func(A) R` | `gp::func<R(A)>` | a `std::function` wrapper: calling a nil func panics, and `f == nil` works |
| `struct{...}` | `struct` + generated `==`, hash, field info | `operator==` only when the struct is comparable; the field info (`gp_fields`) is for `fmt`'s `%v` ([structs](#structs-and-named-types)) |
| `type Celsius float64` (named non-struct type) | `struct Celsius : gp::newtype<Celsius, double>` (a distinct type that can have methods) | gocpp inserts a conversion wherever Go converts implicitly ([structs](#structs-and-named-types)) |
| `interface{...}`, `any`, `error` | generated interface class, `gp::any`, `gp::error` | an interface value holds data, a type descriptor and a method table (32 bytes); no C++ virtual functions (Phase 05) |
| `chan T` | `gp::chan<T>` | a shared reference to the channel; `<-chan T` and `chan<- T` are the same C++ type, but different Go types (Phase 08) |
| results `(A, B)` | `std::tuple<A, B>` | `return a, b` becomes `return {a, b};` ([multiple results](#multiple-results)) |
| `C.int`, `C.char`, `C.size_t`, … (C's built-in types) | `int`, `char`, `size_t`, … (same names as cgo) | the full list is in [interop.md](interop.md#what-c-holds) |
| `std.vector[int]` | `std::vector<int64_t>` | a C++ template; gocpp's `int` is `int64_t` there too ([interop.md](interop.md#cc-types-in-gocpp-code)) |

**One C++ type, several Go types.** Some different Go types share one C++ type: `int` and
`int64` are both `int64_t`. They stay different where Go can tell them apart
(`any(int(1)) != any(int64(1))`, type switches, `%T`), because interface values carry a type
descriptor chosen by the **Go** type
([Phase 05 §2.2](../../plans/2026-10-13-gocpp/phase-05-interfaces-errors/README.md#22-type-descriptors-chosen-by-the-go-type)).

**Sizes.** `unsafe.Sizeof`, `unsafe.Alignof` and `unsafe.Offsetof` report the layout of these
C++ types, which differs from Go's ([D15](language.md#d15-different-sizes)): a pointer is 16
bytes, a `string` 32, a slice 40, a map 16, a `weak.Pointer` 24, and an empty struct 1. A struct
is laid out like the C++ struct (fields in source order). The table that gives the type checker
these numbers is in `internal/check/sizes.go`; `runtime/include/gocpp/sizes.hpp` is generated
from it and checks them with `static_assert`s.

[Phase 02 §2.3](../../plans/2026-10-13-gocpp/phase-02-walking-skeleton/README.md#23-expressions-the-important-rules),
[Phase 03 §2.1–2.4](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#21-one-ownership-system-for-everything-v1).

## Names

### Packages

```cpp
namespace gpkg_main { /* ... */ }                                // package main
namespace gpkg_fmt { /* ... */ }                                 // import "fmt"
namespace gpkg_github_dcom__huuhait__game__engine { /* ... */ }  // import "github.com/huuhait/game/engine"
namespace gpkg_github_dcom__mattn__go_hsqlite3 { /* ... */ }     // import "github.com/mattn/go-sqlite3"
```

- Each package is **one flat namespace**: `gpkg_` followed by the escaped import path. Letters
  and digits stay as they are. Every other character is replaced by a short code that starts
  with `_`:

  | In the import path | In the namespace |
  |---|---|
  | `/` | `__` |
  | `.` | `_d` |
  | `-` | `_h` |
  | `_` | `_u` |
  | `~` | `_t` |
  | `+` | `_p` |
  | any other byte | `_x` and two hex digits |

- Every `_` in the result starts such a code, so the name can be decoded back. That is why two
  import paths can never give the same namespace.
- C++ reserves names that contain `__`, but GCC and Clang accept them without a warning (checked
  with `-Wall -Wextra -pedantic`), so the readable `__` for `/` stays.
- Namespaces are never nested (`gpkg::main`). Inside a nested `gpkg::main`, the C function
  `time()` would be hidden by the package namespace `gpkg::time`, and a package `game` that
  declares `engine` would clash with the sub-package `game::engine`.
- Generated code refers to other packages by full name: `::gpkg_fmt::Println`.
- A package header is included as `#include "gpkg/<import path>/pkg.hpp"`, for example
  `"gpkg/fmt/pkg.hpp"`. The `gpkg/` prefix keeps these apart from real C++ headers such as
  `<fmt/format.h>`.

### Names inside a package

gocpp keeps your names (`Vec2`, `Len`, `X`) wherever C++ allows it. These names get special
treatment:

| Go name | C++ name | Why |
|---|---|---|
| a C++ keyword: `new`, `class`; the list also has words that are keywords or operators in GCC's and Clang's C++ mode, such as `_Pragma` and `_Complex` | `new_`, `class_`, `_Pragma_` | it would not compile |
| a name that is a macro in the headers the runtime includes: `EOF`, `errno`, `assert`, `stdin`, `stdout`, `stderr`, `NULL`, `EINVAL`, `BUFSIZ`, … | the name with a `_` suffix (`EOF_`) | the C macro would replace it, so `io.EOF` would not compile. Phase 04 adds the macros of your own headers |
| a user name that starts with `gp_` (`gp_count`) | the name with a `_` suffix (`gp_count_`) | `gp_` is reserved for generated code, and generated names never end in `_`, so the two can't clash |
| a name that C++ reserves (`_X`, `a__b`) | not renamed: it stays as written | GCC and Clang accept them, even with `-Wall -Wextra -pedantic` (only Clang's opt-in `-Wreserved-identifier` warns); `gocpp vet` warns about them |
| a method named like its type (`func (U) U()`) | `U_` | C++ would read it as a constructor |
| a variable that shadows one of an outer scope: `v := v + 1`, `err := f()` | not renamed: `v`, in a C++ block of its own from its declaration to the end of its Go block; a value that reads the name goes into a temporary first: `int64_t gp_t0 = v + 1; { int64_t v = gp_t0; ... }` | in C++ the new name is already in scope inside its own initializer, so `int64_t v = v;` would read garbage; and debug info puts a variable in scope in its whole block, so without the block a debugger would show the inner `v`, not yet set, on the lines above the declaration. The block also lets a loop body declare the loop's own variable again (`for i := range n { i := i * 2 }`), which C++ forbids in the outermost block of the body |
| several `init()` functions | `gp_init_1` … `gp_init_n` | Go allows many `init` functions in one package |

- Temporaries made by the compiler always start with `gp_` (`gp_t0`), so they can't collide with
  your names.
- Local variables keep their names, so a debugger finds them by their Go names and shows the
  variable that Go means at each line (shadowing included, see the table).
- A `type` declared inside a function moves to namespace scope with a unique name (C++ local
  classes can't have the static members gocpp needs).
- An embedded field is declared with a fully qualified type, `::gpkg_main::Base Base;`, because
  GCC rejects `Base Base;` (Phase 05).

### C and C++ names

| gocpp | C++ |
|---|---|
| `stdio.printf`, `ctime.time` | `::printf`, `::time`: fully qualified, so no gocpp name can hide them |
| `cerrno.errno`, `raylib.RAYWHITE` (macros) | `errno`, `RAYWHITE`: macros stay unqualified |
| `std.vector`, `std.chrono.steady_clock.now()` | `::std::vector`, `::std::chrono::steady_clock::now()` |

The full rules are in [interop.md](interop.md#how-names-are-translated).

## Files

```
$XDG_CACHE_HOME/gocpp/gen/<main module>/gpkg/<import path>/
├── pkg.hpp            everything other packages need: types, prototypes, extern vars, templates
├── render.gp.cpp      one translation unit per .gp file
├── physics.gp.cpp
└── pkg_init.cpp       package variables, init() functions, gp_var_init()/gp_init_funcs()
```

- From Phase 06 on, each package gets one header (`pkg.hpp`), one `.cpp` per `.gp` file and one
  `pkg_init.cpp`. Before that (Phases 02–05), a program is one generated file, as in the
  [first example](#a-first-example).
- Until then, `gocpp build` and `gocpp run` write that file into a temporary work folder
  (`-work` keeps it, `-x` shows the commands) and compile it with
  `-std=c++20 -fwrapv -fno-strict-aliasing -ffp-contract=off -g -gno-column-info -O0`, plus
  `-Qunused-arguments` for clang. The debug info has no columns (`-gno-column-info`): they would
  be the columns of the C++ code, and debuggers would show them on `.gp` lines. Valid Go can
  make the compilers warn about generated code that is right, so that code also gets
  `-Wno-tautological-compare` (clang) or `-Wno-overflow` (g++); every other warning stays
  visible. The runtime comes from the gocpp binary: it is extracted once into the user
  cache folder (`$XDG_CACHE_HOME` or `~/.cache` on Linux), to `gocpp/rt/<version>-<hash>/`, and
  its object files are kept there, per compiler and flags.
- `gocpp run` exits like the program: with its exit status, or, when a signal kills the
  program, by dying of the same signal (on Linux; elsewhere with status 128 plus its number),
  after it removed the work folder. Unlike `go run`, it prints no `exit status N` line.
- `pkg.hpp` has a fixed order: `#pragma once` and `<gocpp/rt.hpp>`; the headers of imported gocpp
  packages; the package's C/C++ headers that its declarations need; forward declarations of all
  named types; type definitions in by-value dependency order; function prototypes, `extern`
  package variables and exported constants (`inline constexpr`); inline and template
  definitions; type descriptors.
- gocpp headers are always included **before** C/C++ headers, so C macros can't break gocpp
  declarations.

Source: [Phase 06 §2.2–2.3](../../plans/2026-10-13-gocpp/phase-06-packages-build/README.md#23-header-layout-c-needs-declarations-before-use-go-doesnt).

## Functions

```go
func add(a, b int) (int, bool) {
	return a + b, a+b > 10
}

func count(names ...string) int {
	return len(names)
}
```

```cpp
std::tuple<int64_t, bool> add(int64_t a, int64_t b) {
    return {a + b, a + b > 10};
}

int64_t count(gp::slice<gp::string> names) {
    return gp::len(names);
}
```

- A Go function becomes a C++ function in the package namespace. **Prototypes come first**,
  because C++ needs a declaration before use and Go doesn't.
- **Parameters are passed by value**, as real copies, as in Go.
- **Variables get explicit C++ types:** `x := e` becomes `int64_t x = e;`. Only compiler
  temporaries and opaque C/C++ values use `auto`. `var x T` becomes `T x{};` (the Go zero value).
- **Variadic** `names ...string` is a `gp::slice<gp::string>`. A call `count("a", "b")` becomes
  `count({"a"_gs, "b"_gs})`, and `count(s...)` becomes `count(s)`.
- **Order of evaluation:** Go evaluates calls left to right, C++ doesn't promise that (and g++ and
  clang++ really differ). So calls are moved into `gp_` temporaries in Go's order where it
  matters: `fmt.Println(next(), next())` becomes `auto gp_t1 = next();` followed by the call.
- **Func values and closures** are `gp::func<...>` values; see [closures](#closures).

Sources: [Phase 02 §2.4–2.5](../../plans/2026-10-13-gocpp/phase-02-walking-skeleton/README.md#24-statements-the-important-rules),
[Phase 03 §2.6–2.7](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#26-functions-func-values-closures).

## Multiple results

```go
s, big := add(7, 5)
```

```cpp
auto gp_t0 = add(7, 5);
int64_t s = std::get<0>(gp_t0);
bool big = std::get<1>(gp_t0);
```

- Results `(A, B)` are a `std::tuple<A, B>`. `return a, b` becomes `return {a, b};`, which
  evaluates left to right.
- `a, b := f()` stores the tuple in a temporary and reads each element. The same works when one
  of the names already exists (`a, err := ...` with an existing `err`).
- `a, b = b, a` evaluates the whole right side first, as Go says:
  `{ auto gp_t0 = b; auto gp_t1 = a; a = gp_t0; b = gp_t1; }`.

Source: [Phase 02 §2.4](../../plans/2026-10-13-gocpp/phase-02-walking-skeleton/README.md#24-statements-the-important-rules).

## Methods

```go
type Vec2 struct {
	X, Y float64
}

func (v Vec2) Len() float64 {
	return math.Sqrt(v.X*v.X + v.Y*v.Y)
}

func (v *Vec2) Scale(k float64) {
	v.X *= k
	v.Y *= k
}
```

```cpp
struct Vec2 {
    double X = 0;
    double Y = 0;
    double Len() const;                           // value receiver
    static void Scale(gp::ptr<Vec2> v, double k); // pointer receiver
    bool operator==(const Vec2&) const = default;
};

double Vec2::Len() const {
    Vec2 v = *this;   // Go gives a value receiver its own copy
    return ::gpkg_math::Sqrt(v.X * v.X + v.Y * v.Y);
}

void Vec2::Scale(gp::ptr<Vec2> v, double k) {
    v->X *= k;   // gp::ptr panics on nil like Go
    v->Y *= k;
}
```

| Go | C++ |
|---|---|
| `func (v T) M(a int) int` (value receiver) | a `const` member function that starts with `T v = *this;`. Go gives a value receiver **its own copy**. A `const T&` would see writes made through other pointers while the method runs, and could dangle. A reference is used only when the body provably can't write memory or call unknown code |
| `func (p *T) M()` (pointer receiver) | `static void M(gp::ptr<T> p);`: the method needs an owning pointer that can escape |
| `p.M()`, value method, `p` a pointer | `p->M()`: auto-deref with a nil check. If `p` is not a local of the caller (a global, a field or an element), the caller first copies it into a local, so the object can't be freed while the method runs |
| `x.PM()`, pointer method, `x` addressable | `T::PM(<address of x>)` (see [pointers](#pointers-and-boxing)) |
| `f := x.M` (method value) | a lambda that copies the receiver **now** (Go evaluates the receiver when the method value is made) |
| `T.M`, `(*T).PM` (method expressions) | lambdas that take the receiver as the first parameter |

Sources: [Phase 03 §2.5](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#25-methods),
and the example of the [root README §2](../../plans/2026-10-13-gocpp/README.md#2-what-it-looks-like)
(here with `math.Sqrt` instead of the C++ `std.sqrt`). Phase 15 may turn pointer methods that
don't escape into normal member functions on `this`.

## Structs and named types

```go
type Point struct{ X, Y int }
type Celsius float64

func (c Celsius) String() string { return fmt.Sprintf("%.1f°C", float64(c)) }
```

```cpp
struct Point {
    int64_t X = 0;
    int64_t Y = 0;
    bool operator==(const Point&) const = default;   // only when comparable
    static constexpr auto gp_fields = gp::fields(&Point::X, "X", &Point::Y, "Y"); // for fmt %v/%+v
};
struct Celsius : gp::newtype<Celsius, double> {      // a distinct type with double's operators
    using newtype::newtype;
    gp::string String() const;
};
```

- **Zero values** come from default member initializers and `T{}`.
- **Keyed literals:** `Point{Y: 2, X: 1}` becomes `Point{.X = 1, .Y = 2}`. C++ needs declaration
  order, so if the values have side effects, they are first stored in temporaries in source
  order.
- **Anonymous struct types** get one generated name per distinct type (`gp_anon_3f2a…`), because
  Go type identity for them is structural. Their definitions live in a shared generated header
  (Phase 06).
- **Named non-struct types** (`Celsius`, `type IDs []int`) are distinct C++ types through
  `gp::newtype`, so they can have methods. Go also converts implicitly in some places (a `[]int`
  assigned to an `IDs` variable, a func literal passed as a `Handler`), so gocpp inserts a
  conversion wherever the source and target types are not identical.
- A `switch` on a newtype (an enum such as `type Color int`) switches on the underlying value,
  because C++ rejects a class type in a `switch`.
- **Order:** all structs are declared first, then defined in dependency order (only by-value
  fields create dependencies), then the functions follow. Runtime types such as `gp::ptr` and
  `gp::slice` accept incomplete types, so recursive types like
  `type Node struct{ next *Node; kids []Node }` work.
- **Runtime types have no plain-named members.** `gp::string`, `gp::slice` and friends expose only
  operators and `gp_` members; everything else is a free function (`gp::len(s)`). So your method
  named `get` or `len` can never clash with a runtime member.

Source: [Phase 03 §2.4](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#24-structs-and-named-types).

## Strings

A `gp::string` is immutable: copies and substrings share the bytes, and only concatenation
and conversions make new ones.

| gocpp | C++ | Notes |
|---|---|---|
| `"héllo"` | `"h\303\251llo"_gs` | static storage: no allocation, no reference count |
| `s[i]`, `len(s)` | `s[i]`, `gp::len(s)` | a `uint8_t`, bounds checked: `index out of range [5] with length 3` |
| `s[a:b]`, `s[a:]`, `s[:b]`, `s[:]` | `gp::sub(s, a, b)`, `gp::sub(s, a)`, `gp::sub(s, 0, b)`, `s` | shares the bytes; Go's checks and messages: `slice bounds out of range [:5] with length 3`, then `[3:2]` |
| `a + b`, `a + b + c` | `a + b`, `gp::concat(a, b, c)` | a chain of `+` allocates once |
| `string(r)` (an integer `r`) | `gp::rune_to_string(r)` | UTF-8; `"\uFFFD"` for a value that is no code point (negative, a surrogate half, above U+10FFFF) |
| `for i, r := range s` | `for (auto gp_it0 = gp::range_string(s); gp::range_next(gp_it0);) { int64_t i = gp_it0.gp_i; int32_t r = gp_it0.gp_r; ...` | `s` is evaluated once; an invalid UTF-8 byte is U+FFFD and steps one byte, as in Go; `i` and `r` are copies of the hidden counters (Go 1.22) |

`[]byte(s)`, `string(b)`, `[]rune(s)` and `string(runes)` come with the slices (Phase 03, step
3.5). As in Go's compiler, a slice expression is evaluated in its place among the calls of its
statement: `fmt.Println(s[i:], f())` slices `s` (and panics, if `i` is out of range) before
`f` runs, while `s[i]` is checked after the calls.

## Pointers and boxing

```go
func NewCounter() *Counter {
	c := Counter{step: 1} // address taken below → c is boxed
	return &c
}
```

```cpp
gp::ptr<Counter> NewCounter() {
    gp::ptr<Counter> c = gp::new_<Counter>(Counter{.step = 1});  // boxed: lives on the heap
    return c;                                                     // &c == the box itself
}
```

- `*T` is `gp::ptr<T>`, a `std::shared_ptr` with nil checks. `new(T)` becomes `gp::new_<T>()`
  (the zero value), and `&T{...}` becomes `gp::new_<T>(T{...})`.
- **Boxing.** A local variable (also a parameter, a receiver copy or a named result) lives on the
  heap, in a "box", when the function takes its address or the address of anything inside it,
  calls a pointer method on it, slices an array in it, or captures it in a closure **and** changes
  it anywhere. A local variable larger than 128 KB (Go's limit for stack variables) is boxed
  too, so it can't overflow the C++ stack. Uses of a boxed `x` become `(*x)`, and `&x` is the
  box. This is a simple, safe version of Go's escape analysis; Phase 15 adds the real one.
  - A boxed parameter keeps its name: the C++ parameter is copied into its box at the
    function's entry, and the box is a variable of the same name in a block around the body,
    the shape of a shadowing declaration:
    `int64_t twice(int64_t n) { gp::ptr<int64_t> gp_t0 = gp::new_<int64_t>(n); { gp::ptr<int64_t> n = static_cast<gp::ptr<int64_t>&&>(gp_t0); ... } }`
    (a class type is moved into the box too; the moves are written as casts, because g++ -O0
    leaves a line of `<bits/move.h>` in the function for a call of `std::move`). A debugger shows the value the
    parameter came with in the frame line (`twice (n=21)`) and the box as `n` in the body
    (`print *n` shows its value).
  - A boxed named result starts as a new zero box, `gp::ptr<T> r = gp::new_<T>();`, and a
    bare `return` returns `(*r)`.
  - A boxed variable of a 3-clause `for` gets a new box for each iteration (Go 1.22): before
    the post statement, `i = gp::new_<int64_t>(*i);`, so a pointer keeps the variable of its
    iteration. The variables of a `range` loop are declared in the body, a new box each time.
- **Order of evaluation.** A boxed variable and `*p` can change in any call (through a
  pointer), so like a package variable they are read after the calls of their statement, as
  gc does: in `x + f()`, `*p = f()` and `y, z := x, f()`, `f` runs first (and a nil `*p` panics
  after it). In `p, *p = q, 1` the store goes through the old `p`, which is copied first.
- **Pointers into objects** share ownership with the object (the aliasing constructor of
  `std::shared_ptr`), so they are memory safe too:

  | Expression | Owner | C++ |
  |---|---|---|
  | `&x` (`x` is a boxed local) | its box | `x` |
  | `&p.f` (`p` is a `*T`) | `p` | `gp::ptr<F>(p, &p->f)` |
  | `&s[i]` (`s` is a slice) | the slice's array | `gp::ptr<T>(s.gp_owner(), &s[i])` |
  | `&globalVar`, `&globalVar.f` | a static owner that is never freed | `gp::static_ptr(globalVar)`, `gp::static_ptr(globalVar.f)` |

- Dereferencing a nil `gp::ptr` (`*p`, `p->f`, also `&p->f`) panics with Go's message:
  `runtime error: invalid memory address or nil pointer dereference`. Unrecovered, it also
  prints Go's signal line (`[signal SIGSEGV: ...]`).
- `p == nil` is `p == nullptr`, and `p == q` compares the addresses. A conversion between
  pointer types whose base types have identical underlying types, `(*Q)(p)`, is
  `gp::ptr_cast<Q>(p)` (with named types, step 3.9); `(*int)(nil)` is
  `gp::ptr<int64_t>(nullptr)`. `&*p` is `gp::ptr<T>(p, &*p)`: Go's `&*p` panics for a nil `p`.
- `weak.Pointer[T]` is `gp::weak_ptr<T>`: `weak.Make(p)` is `gp::weak_make(p)` and
  `w.Value()` is `gp::weak_value(w)` (free functions, since runtime types have no plain-named
  members). `weak` is a compiler intrinsic until generics come (Phase 07).
- Freeing a long chain (a list of millions of nodes) doesn't recurse deeply: past a depth of
  128, the runtime puts the rest on a per-thread list and frees it in a loop.

Source: [Phase 03 §2.2](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#22-pointers-and-boxing).

## Closures

```go
func counter() func() int {
	n := 0
	return func() int { n++; return n }
}
```

```cpp
gp::func<int64_t()> counter() {
    gp::ptr<int64_t> n = gp::new_<int64_t>(0);              // boxed: captured + modified
    return [n]() -> int64_t { (*n)++; return (*n); };
}
```

- A func value is a `gp::func<R(A...)>`. A closure is a C++ lambda.
- A captured variable that never changes after its initialization (and whose address is never
  taken) is **captured by value**. Any other captured variable is **boxed**, and the lambda
  captures the box, so the closure and the function see the same variable, as in Go.
- Go 1.22 loop variables: each iteration has its own variable. Only when a loop variable is boxed
  does gocpp make a new box per iteration.

Source: [Phase 03 §2.6](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#26-functions-func-values-closures).

## Package initialization

```cpp
void gp_init_all() {                      // generated by the driver for the final program
    ::gpkg_c::gp_var_init();      ::gpkg_c::gp_init_funcs();
    ::gpkg_z::gp_var_init();      ::gpkg_z::gp_init_funcs();
    ::gpkg_b::gp_var_init();      ::gpkg_b::gp_init_funcs();
    ::gpkg_main::gp_var_init();   ::gpkg_main::gp_init_funcs();
}

int main(int argc, char** argv) {
    return gp::run_main(argc, argv, &gp_init_all, &gpkg_main::main);
}
```

Here package `main` imports `b` and `c`, and `b` imports `z`. Go 1.25 runs the inits in the order
`c`, `z`, `b`, `main`.

- **Inside a package**, package-level variables are set in Go's dependency order
  (`types.Info.InitOrder` from `go/types`), inside a generated `gp_var_init()`. Then the `init()`
  functions (renamed `gp_init_1` … `gp_init_n`) run in source order from `gp_init_funcs()`.
- **Across packages**, gocpp uses Go's rule since Go 1.21: sort all packages by import path, then
  again and again initialize the **first** package in that list whose imports are all
  initialized. The driver computes this order at link time and generates `gp_init_all()`.
- Package variables are declared `constinit`, so C++ runs no dynamic initializers of its own. A
  variable with a constant value gets it at compile time; the others are assigned in
  `gp_var_init()`. Variables of C++ types that can't be constant-initialized use `gp::lazy<T>`
  storage, which is constructed in `gp_var_init()`.
- `gp::run_main(argc, argv, init, main)` stores the arguments (for `os.Args`), runs the init
  function, runs `main`, and exits with code 0. An unrecovered panic prints `panic: <message>`
  and `goroutine 1 [running]:` and exits with code 2, as in Go.
- In the `c-archive` and `c-shared` build modes, initialization runs at the first exported call
  instead, as in Go.

Sources: [Phase 03 §2.10](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#210-builtins-printing-and-package-initialization),
[Phase 06 §2.4](../../plans/2026-10-13-gocpp/phase-06-packages-build/README.md#24-initialization-across-packages-go-121-rule),
[Phase 06 §2.7](../../plans/2026-10-13-gocpp/phase-06-packages-build/README.md#27-build-modes--buildmode-like-go).

## `#line` and debugging

- Before every generated line whose `.gp` line is not "the previous line + 1", gocpp writes a
  `#line N "/abs/path/file.gp"` directive. So compiler errors and debuggers (gdb, lldb) point at
  `.gp` lines, and a breakpoint on a `.gp` line stops at the right place.
- The paths are absolute, so editors that match breakpoints by full path find the file. They are
  written as C string literals, so Windows backslashes are escaped (`#line 6 "C:\\work\\hello.gp"`).
- Your variable names stay the same in C++, so `print s` works in the debugger.
- The lines that have no place in the `.gp` source (the C++ `main` wrapper) get `#line`
  directives that point at the generated file itself, in the work folder; `gocpp emit` leaves
  them out.
- A C++ compile error in generated code is a bug in gocpp: `gocpp build` prints
  `internal error: generated C++ did not compile`, the compiler's first errors (at `.gp` lines,
  thanks to `#line`) and the work folder, which it keeps; it exits with status 2.

Source: [Phase 02 §2.1 and §2.8](../../plans/2026-10-13-gocpp/phase-02-walking-skeleton/README.md#28-debugging-works-from-day-1).
