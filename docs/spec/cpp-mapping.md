# How gocpp maps to C++

This document shows what the C++ output of gocpp looks like: how types, names, functions,
methods, structs, multiple results and package initialization are written in C++.

| | |
|---|---|
| Status | v0, written in Phase 00 from the plan. Later phases extend it ([what is still missing](#later-phases-extend-this-document)) |
| Source | the type table in the [root README §6](../../plans/2026-10-13-gocpp/README.md#6-type-mapping-cheat-sheet), and the Phase 02, 03 and 06 READMEs linked below |
| See also | [language.md](language.md) (the language), [interop.md](interop.md) (C and C++ values) |

The C++ here is simplified, as in the plan. The real output also has a `#line` directive before
most generated lines ([`#line` and debugging](#line-and-debugging)). The output is plain C++20 for
GCC 13+ and Clang 17+. All gocpp runtime types and helpers live in the namespace `gp`.

## A first example

```go
// hello.gp
package main

import "fmt"

func add(a, b int) (int, bool) {
	return a + b, a+b > 10
}

func main() {
	s, big := add(7, 5)
	fmt.Println("hello, gocpp", s, big)
}
```

`gocpp emit hello.gp` prints:

```cpp
// hello.gp.cpp: generated by gocpp, do not edit
#include <gocpp/rt.hpp>

namespace gpkg_main {

std::tuple<int64_t, bool> add(int64_t a, int64_t b);   // prototypes first:
void main();                                           // Go doesn't care about order, C++ does

#line 6 "/home/me/hello/hello.gp"
std::tuple<int64_t, bool> add(int64_t a, int64_t b) {
#line 7 "/home/me/hello/hello.gp"
    return {a + b, a + b > 10};
}

#line 10 "/home/me/hello/hello.gp"
void main() {
#line 11 "/home/me/hello/hello.gp"
    auto gp_t0 = add(7, 5);
#line 11 "/home/me/hello/hello.gp"
    int64_t s = std::get<0>(gp_t0);
#line 11 "/home/me/hello/hello.gp"
    bool big = std::get<1>(gp_t0);
#line 12 "/home/me/hello/hello.gp"
    gp::fmt::Println("hello, gocpp"_gs, s, big);
}

} // namespace gpkg_main

int main(int argc, char** argv) {
    return gp::run_main(argc, argv, nullptr, &gpkg_main::main);
}
```

This is the Phase 02 output of one file (the unit layout, which the emitter tests still use), when `fmt`
was still a small stand-in and there is no package init yet, so `run_main` gets
`nullptr` as its init function. `gocpp build` writes the [files of the split layout](#files)
instead: the same code, split into a header, a unit for each file and `pkg_init.cpp`, where main's
`run_main` gets `&gp_init_all` when a package has variables to set or init functions
([package initialization](#package-initialization)).

## Types

| gocpp (`.gp`) | Generated C++ | Notes |
|---|---|---|
| `int`, `uint` | `int64_t`, `uint64_t` (64-bit targets, like Go) | gocpp has only 64-bit targets ([D9](language.md#d9-64-bit-targets-only)); signed overflow wraps as in Go, because all C++ is compiled with `-fwrapv` |
| `int8` … `int64`, `uint8` … `uint64`, `uintptr` | `int8_t` … `int64_t`, `uint8_t` … `uint64_t`, `uintptr_t` | results of `int8`, `int16`, `uint8` and `uint16` arithmetic are cast back (`uint8_t(a + b)`), because C++ turns these types into `int` first |
| `byte`, `rune` | `uint8_t`, `int32_t` | in Go too, `byte` is `uint8` and `rune` is `int32` |
| `float32`, `float64` | `float`, `double` | compiled with `-ffp-contract=off`, so the C++ compiler doesn't fuse floating-point operations: the results are gc's on amd64 with `GOAMD64=v1` or `v2`, everywhere (from `v3` on, and on arm64, gc fuses `a*b + c` itself) |
| `complex64`, `complex128` | `gp::complex64`, `gp::complex128` (`gp::complex<float>`, `gp::complex<double>`) | 8 and 16 bytes, the real part first, as in Go; not `std::complex`: `*` and `/` follow Go's rules for infinities and NaN ([complex numbers](#complex-numbers)) |
| `bool` | `bool` | the same type in both languages |
| `string` | `gp::string` (immutable bytes, usually UTF-8; cheap substrings) | 32 bytes: owner, data pointer, length. A literal `"hi"` becomes `"hi"_gs` and points at static storage (no allocation); `s[a:b]` shares the bytes |
| `[N]T` | `gp::array<T, N>` (value type, bounds checked) | wraps `std::array`; assignment copies it, as in Go; `==` exists when the elements are comparable ([arrays](#arrays)) |
| `[]T` | `gp::slice<T>` | 40 bytes: owner, data pointer, length, capacity; `append` gives Go's exact capacities (see below: Go's element sizes, its malloc size classes and header) |
| `map[K]V` | `gp::map<K, V>` (reference type) | a shared pointer to the table (a Swiss table: [ADR-059](../adr/059-swiss-table-maps.md)); reading a missing key gives the zero value and never inserts |
| `*T` where `T` is a gocpp type | `gp::ptr<T>` (reference counted, nil-checked) | a `std::shared_ptr<T>` with nil checks; a nil dereference panics with Go's message ([pointers](#pointers-and-boxing)) |
| `*pkg.T` where `T` is a C/C++ type (`*SDL.SDL_Window`, `*cstdio.FILE`), declared in gocpp code | `gp::cptr<T>` (a `gp::ptr<T>` that a raw `T*` converts to, and that converts to `T*`) | owns or aliases what it points to, as Go's pointer does; `**C.T`, the members of C structs and what C functions return are raw `T*` with C++ lifetime rules ([interop.md](interop.md#pointers-unsafe-and-slices-at-the-boundary)) |
| `unsafe.Pointer` | `gp::ptr<void>` (keeps a gocpp object alive, like Go) | shares the owner of the object it came from, and converts to `void*` for C; `unsafe.Slice`, `String`, `SliceData`, `StringData` and `Add` are `gp::unsafe_slice`, ... in `gocpp/unsafe.hpp` ([D16](language.md#d16-unsafepointer-and-pointers-from-c), [interop.md](interop.md#pointers-unsafe-and-slices-at-the-boundary)) |
| `func(A) R` | `gp::func<R(A)>` | 24 bytes: the closure's owner and its code; copies share the closure, calling a nil func panics, and `f == nil` works ([closures](#closures)) |
| `struct{...}` | `struct` + generated `==`, hash, field info | `operator==` and `gp_hash()` only when the struct is comparable; the field info (`gp_fields`) is for `fmt`'s `%v`; an anonymous struct type is `gp_anon_` and a hash of the type ([structs](#structs)) |
| `type Celsius float64` (named non-struct type) | `struct Celsius : gp::newtype<Celsius, double>` (a distinct type that can have methods) | gocpp inserts a conversion wherever Go converts implicitly ([named types](#named-types)) |
| `interface{...}`, `any`, `error` | generated interface class, `gp::any`, `gp::error` | an interface value holds data, a type descriptor and a method table (32 bytes); no C++ virtual functions (Phase 05) |
| `chan T` | `gp::chan<T>` | a shared reference to the channel; `<-chan T` and `chan<- T` are the same C++ type, but different Go types with their own type descriptors ([goroutines and channels](#goroutines-and-channels)) |
| results `(A, B)` | `std::tuple<A, B>` | `return a, b` becomes `return {a, b};` ([multiple results](#multiple-results)) |
| `C.int`, `C.char`, `C.size_t`, … (C's built-in types) | `int`, `char`, `size_t`, … (same names as cgo) | the full list is in [interop.md](interop.md#what-c-holds) |
| `std.vector[int]` | `std::vector<int64_t>` | a C++ template; gocpp's `int` is `int64_t` there too ([interop.md](interop.md#cc-types-in-gocpp-code)) |

**One C++ type, several Go types.** Some different Go types share one C++ type: `int` and
`int64` are both `int64_t`. They stay different where Go can tell them apart
(`any(int(1)) != any(int64(1))`, type switches, `%T`), because interface values carry a type
descriptor chosen by the **Go** type
([Phase 05 §2.2](../../plans/2026-10-13-gocpp/phase-05-interfaces-errors/README.md#22-type-descriptors-chosen-by-the-go-type)).

**Sizes.** `unsafe.Sizeof`, `unsafe.Alignof` and `unsafe.Offsetof` report the layout of these
C++ types, which differs from Go's ([D15](language.md#d15-different-sizes)): a pointer is 16
bytes, a `string` 32, a slice 40, a map 16, a `weak.Pointer` 24, and an empty struct 1. A struct
is laid out like the C++ struct (fields in source order). The table that gives the type checker
these numbers is in `internal/check/sizes.go`; `runtime/include/gocpp/sizes.hpp` is generated
from it and checks them with `static_assert`s, and each generated struct has one of its own.

**The capacity after `append`.** `cap(s)` is unspecified by the Go spec but programs print it, so
`append` gives what gc 1.25's `growslice` gives (the same numbers as real Go, tested by
`tests/run/append_cap_*.gp`): `nextslicecap`, then the size of the malloc block it needs, rounded
up to Go's size classes (an array of 8 KiB pages from 32 KiB), and for elements that hold
pointers, over 512 bytes, with the 8-byte malloc header (`71` for 33 appends of strings, not
`64`). That depends on **Go's** element size, not the C++ one (a Go `string` is 16 bytes, an
interface 16, a slice 24), so the runtime computes Go's size, alignment and pointer-ness of each
element type from its C++ type at compile time (`runtime/include/gocpp/golayout.hpp`: a
struct's `gp_fields` are laid out as gc does). A zero-size element (`struct{}`, `[0]int`) takes no
memory and gives `cap == len`, as in Go. `[]byte(s)` and `[]rune(s)` give what a slice that
escapes gets in Go (the size class of the length); a constant `s` gets `cap == len`. gc also
has cases that depend on its escape analysis (a slice that does not escape may start in a
32-byte stack buffer): gocpp always gives the heap's numbers. A standard type that gocpp declares
with other fields than Go's (`sync.Cond`, `time.Timer`, a stub that leaves fields out) carries
Go's layout (`gp_go_layout`, `internal/lower/golayouts.go`, checked against real Go by
`TestStdGoLayouts`). Only a type that comes from C or C++ has no Go layout: its C++ size is used.

[Phase 02 §2.3](../../plans/2026-10-13-gocpp/phase-02-walking-skeleton/README.md#23-expressions-the-important-rules),

## Names

### Packages

```cpp
namespace gpkg_main { /* ... */ }                                // package main
namespace gpkg_fmt { /* ... */ }                                 // import "fmt"
namespace gpkg_github_dcom__huuhait__game__engine { /* ... */ }  // import "github.com/huuhait/game/engine"
namespace gpkg_github_dcom__mattn__go_hsqlite3 { /* ... */ }     // import "github.com/mattn/go-sqlite3"
```

- Each package is **one flat namespace**: `gpkg_` followed by the escaped import path. Letters
  and digits stay as they are. Every other character is replaced by a short code that starts
  with `_`:

  | In the import path | In the namespace |
  |---|---|
  | `/` | `__` |
  | `.` | `_d` |
  | `-` | `_h` |
  | `_` | `_u` |
  | `~` | `_t` |
  | `+` | `_p` |
  | any other byte | `_x` and two hex digits |

- Every `_` in the result starts such a code, so the name can be decoded back. That is why two
  import paths can never give the same namespace.
- C++ reserves names that contain `__`, but GCC and Clang accept them without a warning (checked
  with `-Wall -Wextra -pedantic`), so the readable `__` for `/` stays.
- Namespaces are never nested (`gpkg::main`). Inside a nested `gpkg::main`, the C function
  `time()` would be hidden by the package namespace `gpkg::time`, and a package `game` that
  declares `engine` would clash with the sub-package `game::engine`.
- Generated code refers to other packages by full name: `::gpkg_geom::New`, `::gpkg_geom::Point`,
  `::gpkg_geom::Counter` (a variable). The name is the one the package chose for its own
  declaration (its C/C++ headers' macros can rename it, `Bool_`), and a package never recomputes it.
- A package header is included as `#include "gpkg/<import path>/pkg.hpp"`, for example
  `"gpkg/example.com/app/geom/pkg.hpp"`. The `gpkg/` prefix keeps these apart from real C++ headers
  such as `<fmt/format.h>`. (`fmt` has no header: the runtime has its functions.)
- The package main is `gpkg_main` whatever its import path is; its files are in the folder of its
  import path (`gpkg/command-line-arguments/` for `.gp` files named on the command line).

### Names inside a package

gocpp keeps your names (`Vec2`, `Len`, `X`) wherever C++ allows it. These names get special
treatment:

| Go name | C++ name | Why |
|---|---|---|
| a C++ keyword: `new`, `class`; the list also has words that are keywords or operators in GCC's and Clang's C++ mode, such as `_Pragma` and `_Complex` | `new_`, `class_`, `_Pragma_` | it would not compile |
| a name that is a macro in the headers the runtime includes: `EOF`, `errno`, `assert`, `stdin`, `stdout`, `stderr`, `NULL`, `EINVAL`, `BUFSIZ`, … | the name with a `_` suffix (`EOF_`) | the C macro would replace it, so `io.EOF` would not compile. Phase 04 adds the macros of your own headers |
| a user name that starts with `gp_` (`gp_count`) | the name with a `_` suffix (`gp_count_`) | `gp_` is reserved for generated code, and generated names never end in `_`, so the two can't clash |
| a name that C++ reserves (`_X`, `a__b`) | not renamed: it stays as written | GCC and Clang accept them, even with `-Wall -Wextra -pedantic` (only Clang's opt-in `-Wreserved-identifier` warns); `gocpp vet` warns about them |
| a method named like its type (`func (U) U()`) | `U_` | C++ would read it as a constructor |
| a variable that shadows one of an outer scope: `v := v + 1`, `err := f()` | not renamed: `v`, in a C++ block of its own from its declaration to the end of its Go block; a value that reads the name goes into a temporary first: `int64_t gp_t0 = v + 1; { int64_t v = gp_t0; ... }` | in C++ the new name is already in scope inside its own initializer, so `int64_t v = v;` would read garbage; and debug info puts a variable in scope in its whole block, so without the block a debugger would show the inner `v`, not yet set, on the lines above the declaration. The block also lets a loop body declare the loop's own variable again (`for i := range n { i := i * 2 }`), which C++ forbids in the outermost block of the body |
| several `init()` functions | `gp_init_1` … `gp_init_n` | Go allows many `init` functions in one package |

- Temporaries made by the compiler always start with `gp_` (`gp_t0`), so they can't collide with
  your names.
- Local variables keep their names, so a debugger finds them by their Go names and shows the
  variable that Go means at each line (shadowing included, see the table).
- A `type` declared inside a function moves to namespace scope with a unique name (C++ local
  classes can't have the static members gocpp needs).
- An embedded field is declared with a fully qualified type, `::gpkg_main::Base Base;`, because
  GCC rejects `Base Base;` (Phase 05).

### C and C++ names

| gocpp | C++ |
|---|---|
| `stdio.printf`, `ctime.time` | `::printf`, `::time`: fully qualified, so no gocpp name can hide them |
| `cerrno.errno`, `raylib.RAYWHITE` (macros) | `errno`, `RAYWHITE`: macros stay unqualified |
| `std.vector`, `std.chrono.steady_clock.now()` | `::std::vector`, `::std::chrono::steady_clock::now()` |

The full rules are in [interop.md](interop.md#how-names-are-translated).

In typed interop mode (the default when clang++ is installed; `-interop=typed` requires it, [typed-interop.md §8](typed-interop.md#8-code-generation-step-126)) the same
programs get more exact C++ for calls into C and C++: `p.m` on a raw pointer is `gp::nonnull(p)->m`, `x.m` on a class is
`x.m` (not `gp::deref(x).m`), a keyed C struct literal is a designated initializer, a Go string passed to a `const char*`
parameter is `gp::cstr(s).gp_ptr()`. This document shows the output of opaque mode.

## Files

```
$XDG_CACHE_HOME/gocpp/gen/<hash>/gpkg/<import path>/      (a stable folder; with -work: <work>/gen)
├── pkg.hpp            everything other packages and the package's own units need
├── render.gp.cpp      one translation unit per .gp file that has functions
├── physics.gp.cpp
├── pkg_desc.cpp       the descriptors of the package's types (and the forwarders of promoted methods)
└── pkg_init.cpp       package variables, gp_var_init(), gp_init_funcs(); main's also gp_init_all and main
```

- Each package gets one header (`pkg.hpp`) and its translation units, in a folder of its own named
  by its import path. `<hash>` is of the main package (its folder, import path, files and the
  target), so the folder, and with it the `-iquote` and the `#line` paths, are the same in every
  build of the program. `gocpp emit` prints all the files one after the other, each after a line
  `//// gpkg/<import path>/<file>`; the output is the same for the same program (the files are in
  the order of the packages: imports first). Files are written only when their bytes change, and a build
  removes the folders of programs that were not built for a week, when there are more than 100.
- [ADR-025](../adr/025-split-layout.md) has the reasons. In short: a package's descriptors are
  declared `extern` in `pkg.hpp` and defined in its `pkg_desc.cpp` (one object per type in the
  program, compared by address), and the unnamed struct and interface types are in the global
  namespace with a guarded definition in each header that uses them.
- `gocpp build` and `gocpp run` compile every unit of every package, at the same time, through the
  object cache (a unit that did not change, and whose headers did not, is not compiled again), and
  link the objects with the package's C and C++ files, the libraries of the cxx recipes (once for
  the program), and the runtime. The compile uses
  `-std=c++20 -fwrapv -fno-strict-aliasing -ffp-contract=off -fstack-clash-protection -g -gno-column-info -O0 -ffunction-sections -fdata-sections`, plus
  `-Qunused-arguments` for clang, and `-iquote <the folder of the generated files>`. The debug info has no columns (`-gno-column-info`): they would
  be the columns of the C++ code, and debuggers would show them on `.gp` lines. Valid Go can
  make the compilers warn about generated code that is right, so that code also gets
  `-Wno-tautological-compare` (clang) or `-Wno-overflow` (g++); g++ also gets `-Wno-psabi` (the note about the ABI of a 64-byte-aligned parameter, which nothing here can act on); every other warning stays
  visible. g++ also gets `-Werror=conditionally-supported`: a class object such as a gocpp
  pointer passed through a C function's `...` is then an error, as it is with clang (the callee
  would read a copy of the object as its pointer). The runtime comes from the gocpp binary: it is extracted once into the user
  cache folder (`$XDG_CACHE_HOME` or `~/.cache` on Linux), to `gocpp/rt/<version>-<hash>/`, and
  its object files are kept there, per compiler and flags. `-work` keeps the work folder (the objects)
  and the generated files in it; `-x` shows the commands, one compile for each unit.
- `gocpp run` exits like the program: with its exit status, or, when a signal kills the
  program, by dying of the same signal (on Linux; elsewhere with status 128 plus its number),
  after it removed the work folder. Unlike `go run`, it prints no `exit status N` line.
- `pkg.hpp` has a fixed order: `#pragma once` and `<gocpp/rt.hpp>`; the headers of the imported gocpp
  packages; the package's C/C++ headers, but only when a declaration of the header needs a C/C++
  type (a field, a signature or a variable; the units include them again for their bodies); forward
  declarations of all named types and of the unnamed ones the package uses; the interface structs,
  then the type definitions in by-value dependency order (the types of other packages are fully
  qualified: `::gpkg_geom::Point Origin;`), the fmt hooks and the interface wrappers (inline); the
  extern declarations of the descriptors; the exported constants (`inline constexpr int64_t Max =
  10;`, a string as `constexpr std::string_view`, a constant of a named type as `inline const`); the
  prototypes; the `extern` package variables; `gp_var_init` and `gp_init_funcs`. A declaration has no
  `#line`, so a change in a function body does not change the header.
- gocpp headers are always included **before** C/C++ headers, so C macros can't break gocpp
  declarations. A package whose header includes C/C++ headers makes its compile flags (and its
  folder, for `"./x.h"`) **public**: the packages that include its `pkg.hpp` compile with them too,
  so no two units see a C struct with two layouts.
- A unit holds the functions and methods declared in its `.gp` file (the methods are members declared
  in their struct and defined out of line). `pkg_init.cpp` holds the package variables (`constinit`,
  defined here, `extern` in the header) and the initialization.

Source: [Phase 06 §2.2–2.3](../../plans/2026-10-13-gocpp/phase-06-packages-build/README.md#23-header-layout-c-needs-declarations-before-use-go-doesnt).

## Functions

```go
func add(a, b int) (int, bool) {
	return a + b, a+b > 10
}

func count(names ...string) int {
	return len(names)
}
```

```cpp
std::tuple<int64_t, bool> add(int64_t a, int64_t b) {
    return {a + b, a + b > 10};
}

int64_t count(const gp::slice<gp::string>& names) {
    return gp::len(names);
}
```

- A Go function becomes a C++ function in the package namespace. **Prototypes come first**,
  because C++ needs a declaration before use and Go doesn't.
- **Parameters are real copies**, as in Go: a number is passed by value. A string, slice, map,
  channel, func, interface or pointer (that is not [borrowed](#borrowed-pointers-adr-086)) that the
  body never assigns is a `const T&`: the call passes a temporary, a constant or a local variable that
  nothing can change as it is, with no reference count, and a copy of anything else (a package variable,
  a field, an element, a boxed variable), unless the callee drops no string, pointer, slice, map,
  interface or func. So `f(x)` where `f` changes `x` through a pointer, a package variable or a field
  still sees the value it was called with. A parameter that the body assigns (`s += "x"`) is a real
  by-value copy, and so is one larger than 128 KiB (a `const T&` that the function copies into a box).
- **Variables get explicit C++ types:** `x := e` becomes `int64_t x = e;`. Only compiler
  temporaries and opaque C/C++ values use `auto`. `var x T` becomes `T x{};` (the Go zero value).
- **Variadic** `names ...string` is a `gp::slice<gp::string>`. A call `count("a", "b")` becomes
  `count(gp::slice_of<gp::string>({"a"_gs, "b"_gs}))`, `count()` passes a nil slice, and
  `count(s...)` becomes `count(s)`: the callee shares `s`'s array, as in Go. Variadic methods
  and func values take their arguments the same way.
- **Order of evaluation:** Go evaluates calls left to right, C++ doesn't promise that (and g++ and
  clang++ really differ). So calls are moved into `gp_` temporaries in Go's order where it
  matters: `fmt.Println(next(), next())` becomes `auto gp_t1 = next();` followed by the call
  (see [order of evaluation](#order-of-evaluation)).
- **Func values and closures** are `gp::func<...>` values; see [closures](#closures).

Sources: [Phase 02 §2.4–2.5](../../plans/2026-10-13-gocpp/phase-02-walking-skeleton/README.md#24-statements-the-important-rules),
[Phase 03 §2.6–2.7](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#26-functions-func-values-closures).

## Multiple results

```go
s, big := add(7, 5)
```

```cpp
auto gp_t0 = add(7, 5);
int64_t s = std::get<0>(gp_t0);
bool big = std::get<1>(gp_t0);
```

- Results `(A, B)` are a `std::tuple<A, B>`. `return a, b` becomes `return {a, b};`, which
  evaluates left to right.
- `a, b := f()` stores the tuple in a temporary and reads each element. The same works when one
  of the names already exists (`a, err := ...` with an existing `err`).
- `a, b = b, a` evaluates the whole right side first, as Go says:
  `{ auto gp_t0 = b; auto gp_t1 = a; a = gp_t0; b = gp_t1; }`.

Source: [Phase 02 §2.4](../../plans/2026-10-13-gocpp/phase-02-walking-skeleton/README.md#24-statements-the-important-rules).

## Order of evaluation

Go evaluates the calls of a statement from left to right. C++ leaves the order of a call's
arguments and of the operands of most operators open, and g++ and clang++ really choose
differently (g++ often goes from right to left). gocpp gives Go's order, and where the spec
leaves it open, the order of Go's compiler gc (its `walk/order.go` and `walk/assign.go`), since
that is what programs see. It moves the parts whose order matters into `gp_` temporaries in
front of the statement, and only where C++ could get the order wrong:

```go
fmt.Println(next(), next())  // Go: 1 2
fmt.Println(s[i], a[j])      // both out of range: Go reports i
s[i] += a[j]
```

```cpp
{ auto gp_t0 = next(); gp::fmt::Println(gp_t0, next()); }
{ auto gp_t1 = s[i]; gp::fmt::Println(gp_t1, a[j]); }
{ auto& gp_r0 = s[i]; gp_r0 = gp_r0 + a[j]; }
```

**What is evaluated when.** As in gc, the statement's calls come first, in order, each with its
own arguments just before it. A few other things are evaluated in their places among the calls,
as if they were calls: `len`, `cap`, `min`, `max`, `complex`, `real` and `imag`, `make`,
`append`, `copy`, `clear`, a slice expression `s[a:b]` (whose bounds that are not a name, a
constant or `len` of a name are copied first), `[]byte(s)` and `[]rune(s)`, a map literal, `x
&& y` and `x || y` as a whole, an argument of `fmt.Print*` that gc copies (see [fmt and the
builtins](#fmt-and-the-builtins)), and some keys of a map read or store, which gc copies
(its `mapKeyTemp`): when its map call takes the key's address (a key of type `bool`, `int8`,
`int16`, `uint8`, `uint16`, a float or a complex number, most arrays and structs, or any key of a
map whose values are larger than 128 bytes), a key that is not addressable (`m[!b]`, `m[x+1]`;
an addressable one, `m[b]` or `m[bs[i]]`, is read where the map is), and an array or a struct of
4 or 8 bytes of plain memory (`[2]int32`), always.
Everything else is evaluated after all of them: the reads of memory that a call can change (a
package or boxed variable, `*p`, `p.f`, an element of a slice, `m[k]`) and the operations that
can panic (an index, a nil pointer, a division by zero, a negative shift count, a slice to array
conversion). So in `x + f()` the new `x` is read, and `a/b + f()` calls `f` before it panics.
They go from left to right, except that the key of a map read and the operands of an ordering
comparison of strings (`<`, `<=`, `>`, `>=`, not `==`) go before the rest of their expression:
gc makes those runtime calls and evaluates their arguments first, so `s[i] + m[a[j]]` checks
`j` first.

**Two operations that panic.** When two of them would fail, Go reports the first one it
evaluates, and so does gocpp: the first goes into a temporary when C++ could evaluate the other
one first (an argument next to another argument, an operand next to another operand). The
target of `x op= y` is bound once, `auto& gp_r0 = s[i];`, since nothing runs between its check
and its store (unless only the statement holds it, as in `[]int{1, 2}[i] += x`). Another place
that the statement uses as one (the operand of `&`, a sliced array) and an array or a struct
value are only checked in front, with `static_cast<void>(...)`, and evaluated again in the
statement, which gives the same result. There are three places where gc doesn't go from left to
right:

- in `x = v`, the panics of `v` come before those of the operands of `x` (`s[a[i]] = t[j]`
  checks `j` first), except in the parts of the operands that gc copies first, which are not a
  name, a field, `*p` or an index of an array, a slice or a string (`s[a[i]&1] = t[j]`,
  `s[-a[i]] = t[j]`, `s[int(u[i])] = t[j]` and `s[m[a[i]]] = t[j]` check `i` first; a conversion
  to the value's own type is no conversion); in `m[k] = v` and `m[k] op= v` (but not `/=` and
  `%=`) they come before all of the key; each entry of a map literal is such a store; each store
  of an assignment with several targets that is evaluated late (below) follows the same rule, and
  so do `x op= y` and `x++`, as `x = x op y`: the copied parts of `x` first, then the rest of `x`,
  then `y`;
- a call of a func value checks its arguments before the func value (`fs[i](a[j])` checks `j`
  first); a func value with a call in it (`mk()(x)`) is evaluated before the arguments;
- the receiver of a method call is the first argument: its calls go first, its reads and its nil
  check with the other arguments.

A deferred call is the exception to the second rule: gc copies its func value, its receiver and
then its arguments into new variables, in that order, so `defer fs[i](a[j])` checks `i` first,
and `defer p.M(s[i])` with a nil `p` panics for `p` (the receiver is an argument of
`gp_push_call` there, which C++ doesn't order, so it goes into a temporary or is checked first).

**Assignments** follow Go's two-phase rule: first the operands of the targets' index
expressions and pointer indirections and the values, then the stores, from left to right:
`a, b = b, a` and `p, *p = q, 5` (stores through the old `p`). Which of the operands and values
are evaluated before all the stores is gc's rule (`ascompatee`): an operand or a value goes
early, into a temporary, when a store before it could change it (it reads a variable stored
before, or memory after a store to memory: a package or boxed variable, `*p`, `s[i]`, `m[k]`;
in a function with defers, everything after a store to a result); the others are evaluated
late, in their own store, value first. That decides which panic a statement with several
targets reports:

```go
a, b := s[i], t[j]  // Go checks i first: a and b are plain locals
x, y = s[i], t[j]   // x is a package variable: t[j] is evaluated early, Go checks j first
```

```cpp
int64_t a = s[i]; int64_t b = t[j];
{ auto gp_t0 = t[j]; x = s[i]; y = gp_t0; }
```

A store `m[k], x = v, 1` whose value can panic takes the entry first, as gc does (the key's
check and a nil map's panic come before the value's): `auto& gp_r0 = gp::ref(m, k); gp_r0 =
v;`. A `return a, b` in a function with defers assigns the results like an assignment (so its
values after the first are evaluated early); without defers it is `return {a, b};`, which C++
evaluates in order.

**Where the temporaries go.**

- A simple statement, a return and a deferred call: in front of it, in a block `{ ... }`, so that
  a `goto` never jumps over their initialization; a declaration has them on its line, without
  the block (its names must stay in scope).
- The condition of a loop: at the top of the body, followed by `if (!cond) break;` (the
  condition runs before every iteration, and `continue` goes there too). A post statement that
  needs temporaries is written at the end of the body, where `continue` jumps.
- An `else if` condition and a `case` expression: in the `else` branch, since they run only when
  the conditions before them failed. In a case list, the expressions after the first set a
  `bool` only while the ones before didn't match, as Go stops at the first match.
- The right side of `&&` and `||`, when it needs temporaries: in an `if` on the left side's
  value, `bool gp_t0 = x; if (gp_t0) { ...; gp_t0 = y; }`, so it still runs only when Go runs it.

Not needed: a temporary next to constants and plain local variables (which only an assignment
can change), and in the lists that C++ evaluates in order: the elements of a braced list
(composite literals, `return {a, b}`) and declarations one after the other.

[Phase 03 §2.7](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#27-evaluation-order),

## Methods

```go
type Vec2 struct {
	X, Y float64
}

func (v Vec2) Len() float64 {
	return math.Sqrt(v.X*v.X + v.Y*v.Y)
}

func (v *Vec2) Scale(k float64) {
	v.X *= k
	v.Y *= k
}
```

```cpp
struct Vec2 {
    double X = 0;
    double Y = 0;
    double Len() const;                           // value receiver
    static void Scale(gp::bptr<Vec2> v, double k); // pointer receiver (borrowed: v is only read and written)
    bool operator==(const Vec2&) const = default;
};

double Vec2::Len() const {
    Vec2 v = *this;   // Go gives a value receiver its own copy
    return ::gpkg_math::Sqrt(v.X * v.X + v.Y * v.Y);
}

void Vec2::Scale(gp::bptr<Vec2> v, double k) {
    v->X *= k;   // gp::bptr panics on nil like gp::ptr and Go
    v->Y *= k;
}
```

| Go | C++ |
|---|---|
| `func (v T) M(a int) int` (value receiver) | a `const` member function that starts with `T v = *this;`. Go gives a value receiver **its own copy**. A `const T&` would see writes made through other pointers while the method runs, and could dangle. A reference is used only when the body provably can't write memory or call unknown code |
| `func (p *T) M()` (pointer receiver) | `static void M(gp::bptr<T> p);` when the body cannot keep `p` past the call (it only reads and writes through it, compares it, or lends it to borrowing callees): a raw pointer, no reference count. Otherwise `static void M(gp::ptr<T> p);`, an owning pointer that can escape: stored, returned, captured, converted to an interface, passed to an owning parameter ([Borrowed pointers](#borrowed-pointers-adr-086)) |
| `p.M()`, value method, `p` a pointer | `p->M()`: auto-deref with a nil check. If `p` is not a local of the caller (a global, a field or an element), the caller first copies it into a local, so the object can't be freed while the method runs |
| `x.PM()`, pointer method, `x` addressable | `T::PM(<address of x>)` (see [pointers](#pointers-and-boxing)): `gp::borrow(&x)` for a local that the escape analysis keeps on the stack ([ADR-114](../adr/114-escape-analysis-keeps-non-escaping-objects-on-the-stack.md)) or for a package variable, `gp::lend(x)` for a boxed `x`, when `PM` borrows its receiver; else the box, `gp::stack_ptr(x)` or `gp::static_ptr(x)` |
| `f := x.M` (method value) | `gp::func<Sig>([gp_r = x](auto&&... gp_a) { return gp_r.M(gp_a...); })`: the receiver is copied **now** (Go evaluates it when the method value is made); `p.M` copies `*p` now, and panics now for a nil `p`; `x.PM` captures the pointer (`&x`, x boxed) |
| `T.M`, `(*T).PM`, `(*T).M` (method expressions) | `gp::func<Sig>([](auto&& gp_r, auto&&... gp_a) { return gp_r.M(gp_a...); })`, the receiver the first parameter; `(*T).M` of a value method first panics for a nil pointer with Go's `value method main.T.M called using nil *T pointer`; a call `T.M(x, a)` calls the lambda at once, without a `gp::func` |
| `o.M()`, `M` promoted from an embedded `Inner` / `*Inner` | `o.Inner.M()`, `o.Inner->M()`, `Inner::PM(gp::borrow(&o->Inner))` (`Inner::PM(gp::field_ptr(<&o>, &Outer::Inner))` when `PM` takes an owning pointer): the path that `go/types` gives, written out (embedding is allowed from Phase 05; the [forwarding members](#embedding) below are for C++ callers and the method tables, not for these calls) |
| `defer x.M(a)` | `gp_df.gp_push_call([](auto&& gp_a0, auto&& gp_a1) { gp_a0.M(gp_a1); }, x, a);`: the receiver is stored at the defer statement, a copy of the value for a value method (`defer p.M()` copies `*p` there, and panics there for a nil `p`) |

What the C++ looks like (step 3.10, internal/lower/methods.go):

- The methods are declared in their type's struct (also a named type that isn't a struct, a
  `gp::newtype`) and defined out of line after all the structs, in source order with the
  functions, so a method may use a type declared after it. Their C++ names are escaped like the
  fields' (`MethodName`: a C++ word gets a `_`, `func (w Words) Words()` is `Words_`), so a method
  never clashes with a field. Inside a method, the struct's members (its fields, methods and, for
  a named type over a runtime class, the base's names `slice`, `string`, ...) would hide the
  package's names, so a package variable, function or type of such a name is written qualified
  there: `gpkg_main::X`.
- A value receiver is a copy, `T v = *this;`; a box, `gp::ptr<T> v = gp::new_<T>(*this);`, when
  the method takes its address (or calls a pointer method on it) or when `T` is larger than
  128 KiB; and `const T& v = *this;` when the body provably can't change the object: it calls
  only `len`, `cap`, `min`, `max`, `new`, `make`, `print`, `println`, `panic` and conversions,
  takes no address, has no `defer`, `go` or func literal, and assigns only its own variables
  (or their parts), not `v`. A receiver without a name (or `_`) is not copied.
- A **borrowed** receiver or parameter (`gp::bptr<T>`, [below](#borrowed-pointers-adr-086)) is a raw pointer that the
  caller keeps alive; the call writes `gp::lend(p)`, `gp::borrow(&p->f)` or an owning copy.
- Go's order: the receiver is evaluated with the arguments, as gc does (it makes the receiver the
  first argument): its calls run before the arguments' calls (`h().M(f())` calls `h` first), its
  reads after all of them (`g.M(f())`, where `f` changes `g`, calls `M` on the new `g`, and for a
  nil `g` panics after `f` ran). A value method called through a pointer that is not a local of
  the caller copies it first, `gp::ptr<T>(g)->M(...)`, so the object stays alive for the call.
- fmt calls `String()`, `Error()`, `GoString()` and `Format(f fmt.State, verb rune)` through the
  method tables of the descriptors (gocpp/fmt.hpp, [fmt](#fmt-and-the-builtins)): a method needs no member for it.
- Go has no methods on local types (a method is declared at package level on a package-level
  type), so a local type moved to the namespace has none of its own.
- Method values and method expressions (step 3.10b) are generic lambdas in a `gp::func`, so a
  stack trace leaves them out as Go leaves out its wrappers (`main.T.M-fm`): a panic in a method
  called through one shows the method and its caller. The receiver of a method value is
  evaluated like a method call's: its calls in their places, its reads after the calls of its
  scope (`h(g.M, f())`, where `f` changes `g`, binds the new `g`). A value receiver larger than
  128 KiB is captured in a box. Method values work wherever func values do: stored, passed,
  compared with nil (never nil), deferred, of variadic methods, of named types (also named func
  types) and of promoted methods.

Sources: [Phase 03 §2.5](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#25-methods),
and the example of the [root README §2](../../plans/2026-10-13-gocpp/README.md#2-what-it-looks-like)
(here with `math.Sqrt` instead of the C++ `std.sqrt`). Phase 15 step 15.3 borrows the pointers that don't
escape ([ADR-086](../adr/086-borrowed-pointer-parameters-and-receivers.md)), and step 15.2 keeps the
objects whose address does not escape on the C++ stack ([ADR-114](../adr/114-escape-analysis-keeps-non-escaping-objects-on-the-stack.md),
[Pointers and boxing](#pointers-and-boxing)).

### Borrowed pointers (ADR-086)

A pointer parameter or receiver that the callee only reads and writes through, compares, or lends on is
`gp::bptr<T>` (`gp::ptr<T>` converts to it implicitly): a raw `T*` with `->`, `*`, `==` and Go's nil checks, 8
bytes, no reference count.

```go
type base struct{ n int }
func (b *base) add(k int) { b.n += k }          // b is only used through: borrowed
type mid struct{ base; k int }
func (m *mid) add(k int) { m.base.add(k * 2) }  // passes the address of its field: borrowed too
type top struct{ *mid }
func main() {
	t := top{&mid{}}
	t.add(1)                                    // the pointer is loaded from a field: lent, the callee is pure
}
```

```cpp
void base::add(gp::bptr<base> b, int64_t k) { b->n = b->n + k; }
void mid::add(gp::bptr<mid> m, int64_t k) { base::add(gp::borrow(&m->base), k * 2); }  // no aliasing pointer
void main() {
    top t{gp::new_<mid>(mid{})};         // nothing takes the address of t: a plain local
    mid::add(gp::lend(t.mid), 1);
}
```

- **Callee** (`internal/lower/borrow.go`): `p` is borrowed unless it escapes: stored (also `x := p`), returned,
  captured by a func literal, converted to an interface, sent, used by `go` or `defer`, passed to a parameter
  that is not borrowed, an interface method, a func value or C/C++, reassigned, address-taken, a method value,
  converted, or `&p.f`/`p.arr[:]` that does not go straight into a borrowed parameter. A generic function, a
  method of a generic type, an aware function (`recover`), an `//export` function and, in a library build, an
  exported function keep owning pointers.
- **Caller** (`borrowemit.go`): the object must be alive until the call returns. `gp::lend(x)` passes a
  temporary, a local that is not boxed, a borrowed parameter, a box, or the address of a part of such an object
  (`gp::borrow(&x->f)`, `gp::borrow(&pkgVar)`); a pointer loaded from a field, an element, a package variable
  or a box is lent as it is only to a **pure** callee (it stores no pointer, slice, map, interface or func
  outside its locals, runs no unknown code) while no other argument runs code; anything else is copied first,
  `gp::ptr<T>(x)`, as every call was. `go` and `defer` store owning copies and call such a function through a
  lambda that lends them; func values and method values of it are lambdas that lend their parameters.
- **Const references** (step 15.3b): a parameter that is not borrowed and that the body never assigns is
  a `const T&` (strings, slices, maps, channels, funcs, interfaces, pointers that are kept); `refStable`
  in `borrowemit.go` says when the call passes its argument as it is. Func values and callbacks of such a
  function are `gp::func_of<&gp::adapt<&f>::call>()`, the adapter that takes the Go-level parameters.
- **Interfaces**: the thunk of a pointer method with a borrowed receiver calls
  `T::M(gp::unbox_borrow<T>(gp_self), ...)`, no copy; the call site copies an interface value that the method
  could change (`Shape(x).M()` for a field, element, package or boxed variable).

## Structs and named types

```go
type Point struct{ X, Y int }
type Celsius float64

func (c Celsius) String() string { return fmt.Sprintf("%.1f°C", float64(c)) }
```

```cpp
struct Point {
    int64_t X = 0;
    int64_t Y = 0;
    bool operator==(const Point&) const = default;   // only when comparable
    static constexpr auto gp_fields = gp::fields(    // for gp::convert and for fmt's C++ values
        gp::field(&Point::X, "X", true, false),      // member, Go name, exported, embedded
        gp::field(&Point::Y, "Y", true, false));
};
struct Celsius : gp::newtype<Celsius, double> {      // a distinct type with double's operators
    using gp::newtype<Celsius, double>::newtype;
    gp::string String() const;
};
```

- **For `fmt`** nothing is written into the struct: `fmt` reads values through the type descriptors
  ([fmt](#fmt-and-the-builtins)), whose field lists have the Go names, the exported and embedded flags, the tags and
  the offsets of the members (`gp::offset_of(&Point::X)`). `gp_fields` (`gp::field(&T::f, "name",
  exported, embedded)`, every field in declaration order, also blank `_` fields) is for
  `gp::convert` between struct types, and for `gp::cgo::fmt_arg`, which walks the C++ types of a
  value with a C/C++ part to register the text of its classes. A named non-struct type has
  `const U& gp_value() const` (its underlying value).

- **Zero values** come from default member initializers and `T{}`.
- **Keyed literals:** `Point{Y: 2, X: 1}` becomes `Point{.X = 1, .Y = 2}`. C++ needs declaration
  order, so if the values have side effects, they are first stored in temporaries in source
  order.
- **Anonymous struct types** get one generated name per distinct type (`gp_anon_3f2a…`), because
  Go type identity for them is structural. In the split layout they are in the global namespace
  (one type for the whole program) and every header that uses one writes the same guarded definition
  ([ADR-025](../adr/025-split-layout.md)); the name hashes the identity text, with the import path of
  the package of an unexported field name (`struct{ x int }` of two packages are two types).
- **Named non-struct types** (`Celsius`, `type IDs []int`) are distinct C++ types through
  `gp::newtype`, so they can have methods. Go also converts implicitly in some places (a `[]int`
  assigned to an `IDs` variable, a func literal passed as a `Handler`), so gocpp inserts a
  conversion wherever the source and target types are not identical.
- A `switch` on a newtype (an enum such as `type Color int`) switches on the underlying value,
  because C++ rejects a class type in a `switch`.
- **Order:** all structs are declared first, then defined in dependency order (only by-value
  fields create dependencies), then the functions follow. Runtime types such as `gp::ptr` and
  `gp::slice` accept incomplete types, so recursive types like
  `type Node struct{ next *Node; kids []Node }` work.
- **Runtime types have no plain-named members.** `gp::string`, `gp::slice` and friends expose only
  operators and `gp_` members; everything else is a free function (`gp::len(s)`). So your method
  named `get` or `len` can never clash with a runtime member.

Source: [Phase 03 §2.4](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#24-structs-and-named-types).

## Strings

A `gp::string` is immutable: copies and substrings share the bytes, and only concatenation
and conversions make new ones.

| gocpp | C++ | Notes |
|---|---|---|
| `"héllo"` | `"h\303\251llo"_gs` | static storage: no allocation, no reference count |
| `s[i]`, `len(s)` | `s[i]`, `gp::len(s)` | a `uint8_t`, bounds checked: `index out of range [5] with length 3` |
| `s[a:b]`, `s[a:]`, `s[:b]`, `s[:]` | `gp::sub(s, a, b)`, `gp::sub(s, a)`, `gp::sub(s, 0, b)`, `s` | shares the bytes; Go's checks and messages: `slice bounds out of range [:5] with length 3`, then `[3:2]` |
| `a + b`, `a + b + c` | `a + b`, `gp::concat(a, b, c)` | a chain of `+` allocates once |
| `string(r)` (an integer `r`) | `gp::rune_to_string(r)` | UTF-8; `"\uFFFD"` for a value that is no code point (negative, a surrogate half, above U+10FFFF) |
| `for i, r := range s` | `for (auto gp_it0 = gp::range_string(s); gp::range_next(gp_it0);) { int64_t i = gp_it0.gp_i; int32_t r = gp_it0.gp_r; ...` | `s` is evaluated once; an invalid UTF-8 byte is U+FFFD and steps one byte, as in Go; `i` and `r` are copies of the hidden counters (Go 1.22) |

`[]byte(s)`, `string(b)`, `[]rune(s)` and `string(runes)` are with the slices (below). As in
Go's compiler, a slice expression is evaluated in its place among the calls of its statement:
`fmt.Println(s[i:], f())` slices `s` (and panics, if `i` is out of range) before `f` runs,
while `s[i]` is checked after the calls.

## Slices

A `gp::slice<T>` is a view of a backing array on the heap: copies and sub-slices share the
array, as in Go, and `append` writes into it while it has room.

| gocpp | C++ | Notes |
|---|---|---|
| `var s []T`, `s = nil`, `s == nil` | `gp::slice<T> s{};`, `s = nullptr`, `s == nullptr` | nil is the zero value; `[]T{}` and `make([]T, 0)` are empty but not nil |
| `[]T{a, b}`, `[]T{5: a, b}` | `gp::slice_of<T>({a, b})`, `gp::slice_keyed<T>(7, {{5, a}, {6, b}})` | elements in source order; a keyed literal's other elements are zero |
| `make([]T, n)`, `make([]T, n, c)` | `gp::make_slice<T>(n)`, `gp::make_slice<T>(n, c)` | zeroed; `makeslice: len out of range`, `makeslice: cap out of range` |
| `s[i]`, `len(s)`, `cap(s)` | `s[i]`, `gp::len(s)`, `gp::cap(s)` | `s[i]` is a `T&` (`s[i] = v`, `s[i] += v`, `s[i]++`), bounds checked |
| `s[a:b]`, `s[a:b:c]` | `gp::sub(s, a, b)`, `gp::sub(s, a, b, c)` | shares the array; `slice bounds out of range [:5] with capacity 3` |
| `append(s, a, b)`, `append(s, t...)` | `gp::append(s, a, b)`, `gp::append_slice(s, t)` | also `append(b, str...)` for a `[]byte`; the capacity after growth is Go 1.25's (`growslice`), for every element type |
| `s = append(s, x)`, `s = s[1:]` | `s = gp::append(static_cast<gp::slice<T>&&>(s), x)` | `s` is moved into the call (no reference count traffic) when no other argument can read it; into `gp::sub` only for a local variable that is not boxed and not a named result, since its bounds check can panic |
| `copy(dst, src)`, `clear(s)` | `gp::copy(dst, src)`, `gp::clear(s)` | overlap safe; also `copy(b, str)` |
| `&s[i]` | `gp::ptr<T>(s.gp_owner(), &s[i])`, or `gp::elem_ptr(f(), i)` | the pointer keeps the array alive |
| `for i, v := range s` | `for (auto gp_it0 = gp::range_slice(s); gp::range_next(gp_it0);) { int64_t i = gp_it0.gp_i; T v = gp_it0.gp_v(); ...` | the loop holds a copy of `s`: it covers the original length and array, also when the body appends to `s` |
| `[]byte(s)`, `[]rune(s)` | `gp::to_bytes(s)`, `gp::to_runes(s)` | copies; an invalid UTF-8 byte is U+FFFD |
| `string(b)`, `string(runes)` | `gp::to_string(b)`, `gp::to_string(runes)` | copies; a rune that is no code point is U+FFFD |

The order of evaluation is gc's: an element `s[i]` is memory that a call can change (through
another slice of the same array), so it is read after the calls of its statement, like `*p`;
`append`, `copy`, `make`, `len`, `cap`, `[]byte(s)` and `[]rune(s)` are evaluated in their
places among the calls, and `string(b)` reads `b` where it is. In `s, s[0] = t, 5` the store
goes into the old `s`, and in `i, s[i] = 1, 2` to the old `i`, as in Go.

## Arrays

A `gp::array<T, N>` is a value: its N elements are in the object itself, so assigning, passing
and returning an array copies it, as in Go.

| gocpp | C++ | Notes |
|---|---|---|
| `var a [3]T` | `gp::array<T, 3> a{};` | every element zero |
| `[3]T{a, b}`, `[...]T{a, b}` | `gp::array<T, 3>{a, b}`, `gp::array<T, 2>{a, b}` | elements in source order; the missing ones are zero |
| `[5]T{2: a, b}` | `gp::array_keyed<T, 5>({{2, a}, {3, b}})` | keyed: elements in source order, the others zero |
| `[2][2]T{{a, b}, {c, d}}` | `gp::array<gp::array<T, 2>, 2>{gp::array<T, 2>{a, b}, ...}` | a nested literal names its type |
| `a[i]`, `p[i]` (`p` is `*[N]T`) | `a[i]`, `(*p)[i]` | a `T&`; `index out of range [5] with length 3`; a nil `p` panics with the nil dereference first |
| `len(a)`, `cap(a)`, `len(p)` | `N` (a constant), or `gp::len(f())` | `len(p)` of a nil `p` is N, without a panic, as in Go |
| `a == b`, `a != b` | `a == b`, `a != b` | when the elements are comparable; floats compare as numbers (NaN != NaN) |
| `a[lo:hi]`, `a[lo:hi:max]` | `gp::sub(&a, lo, hi)`, `gp::sub(&a, lo, hi, max)` | shares the array; `&a` is a pointer to it (below), so a sliced local array is boxed; `slice bounds out of range [:5] with length 3` |
| `p[lo:hi]` | `gp::sub(p, lo, hi)` | a nil `p` panics with the nil dereference |
| `&a[i]` | `gp::ptr<T>(a, &(*a)[i])` (boxed `a`), `gp::static_ptr(garr[i])`, `gp::ptr<T>(p, &(*p)[i])`, `gp::elem_ptr(f(), i)` | shares the owner of the array ([pointers](#pointers-and-boxing)) |
| `&[N]T{...}` | `gp::new_<gp::array<T, N>>(gp::array<T, N>{...})` | a new block |
| `[N]T(s)`, `(*[N]T)(s)` | `gp::to_array<N>(s)`, `gp::to_array_ptr<N>(s)` | a copy of `s[0:N]`; a pointer that shares `s`'s array; `cannot convert slice with length 2 to array or pointer to array with length 3`; `(*[0]T)(s)` of a nil `s` is nil |
| `for i, v := range a` | `for (auto gp_it0 = gp::range_array_copy(a); gp::range_next(gp_it0);) { int64_t i = gp_it0.gp_i; T v = gp_it0.gp_v(); ...` | over a copy of `a`, as in Go; `gp::range_array(a)` without the copy where the body can't change `a`; `gp::range_array(p)` through a pointer (the body's writes are seen) |
| `for i := range a` | `for (int64_t gp_i0 = 0; gp_i0 < N; gp_i0++) { int64_t i = gp_i0; ...` | `a` is not evaluated (`for i := range p` of a nil `p` doesn't panic), unless it has a call: `gp::len(f())` |
| `x := [1 << 21]int{5: 3}` (over 128 KiB) | `gp::ptr<gp::array<int64_t, 2097152>> x = gp::new_array_keyed<int64_t, 2097152>({{5, 3}});` | boxed, and built in its box (below) |
| `var garr = [3]int{1, 2, 3}` | `constinit gp::array<int64_t, 3> garr{1, 2, 3};` | an array literal of number and bool constants is set at compile time; the others in `gp_var_init` ([package initialization](#package-initialization)) |

**Range copies.** Go ranges over a copy of an array, so `for _, v := range a { a[1] = 100 }`
still sees the old `a[1]`. gocpp makes that copy only where the body could change the array:
for a local variable that is not boxed, when the body assigns to it or to a part of it; for any
other array (a package or a boxed variable, `*p`, an element of a slice), also when the body has
a call or writes to memory through a pointer, a slice or a package variable, or to a variable
that may hold the last pointer to the array's block (`p = nil` for `range *p`). An array that is
not reached from a variable is always held by the loop: a value (`f()`, a literal), and one in a
block that only a temporary owns (`*f()`, `f()[i]`, `**f()`, `*(&[N]T{...})`), which is freed
when the loop's first line ends. A copy of an array larger than 128 KiB goes to the heap.

The order of evaluation is gc's: an element of a package or a boxed array, or one behind a
pointer, is read after the calls of its statement, like `*p`; a slice of an array is taken in its
place among the calls; `[N]T(s)` reads `s` after the calls. In `a, a[0] = b, 5` the store goes
into the new `a` (only the index and the pointer of a target are saved, never the array), as in
Go.

**Arrays larger than 128 KiB** (Go's limit for a variable on the stack) are kept off the C++
stack where that is cheap: a local variable is boxed, and a literal or a conversion that
initializes it is built in its box (so is `&[N]T{...}` in its new block) (`gp::new_array<T, N>({a, b})`, `gp::new_array_keyed<T,
N>({{5, a}})`, `gp::new_to_array<N>(s)`); a parameter is a `const A&`, which the function copies
into a box at its entry, before any of its code runs (`int64_t sum(const gp::array<int64_t,
2097152>& a)`), so it is still a copy of the argument, read after the call's other arguments,
as in Go. Results and the other temporaries stay on the stack
([D24](language.md#d24-large-values-on-the-c-stack)).

Source: [Phase 03 §2.3](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#23-strings-slices-arrays-maps).
## Maps

A `gp::map<K, V>` is a reference to a hash table (one shared pointer, 16 bytes): copies, parameters
and results share the table, as in Go. The table is a Swiss table ([ADR-059](../adr/059-swiss-table-maps.md)):
one block of control bytes (7 bits of each key's hash, or empty or deleted) and slots that hold a key
and a value side by side, probed a group of slots at a time (SSE2, or 64-bit arithmetic), at
most 7/8 full, with a random hash seed for each map. Reading a missing key gives the zero value and never
inserts it, unlike C++'s `operator[]`.

| gocpp | C++ | Notes |
|---|---|---|
| `var m map[K]V`, `m = nil`, `m == nil` | `gp::map<K, V> m{};`, `m = nullptr`, `m == nullptr` | nil is the zero value; a nil map reads like an empty one (get, `len`, `delete`, `clear`, range) |
| `make(map[K]V)`, `make(map[K]V, n)` | `gp::make_map<K, V>()`, `gp::make_map<K, V>(n)` | the size hint only reserves room, for at most 2^22 entries (Go allocates a huge map's table as it fills); a negative hint counts as 0, as in Go, and a hint never panics |
| `map[K]V{k1: v1, k2: v2}` | `gp::map_of<K, V>({{k1, v1}, {k2, v2}})` | gc's order: the entries whose key and value are constants first, then the others in source order, so of two equal keys the later one that isn't constant wins |
| `v := m[k]` | `V v = gp::get(m, k);` | the zero value if `k` is missing; never inserts |
| `v, ok := m[k]` | `auto gp_t0 = gp::lookup(m, k); V v = std::get<0>(gp_t0); bool ok = std::get<1>(gp_t0);` | the multi-value rule of [multiple results](#multiple-results) |
| `m[k] = v` | `gp::set(m, k, v);` | a nil map panics: `assignment to entry in nil map` |
| `m[k] += v`, `m[k]++` | `gp::ref(m, k) += v;`, `gp::ref(m, k)++;` | takes the entry once (inserting `k` as the zero value first); also `-= *= &= \|= ^= &^=`, strings' `+=` |
| `m[k] /= y`, `m[k] %= y` | `gp::set(m, k, gp::div(gp::get(m, k), y));` | as gc: a division by zero panics before `k` is inserted; a constant divisor (not 0 or -1) is `gp::ref(m, k) /= 3` |
| `m[k] <<= n` | `gp::ref(m, k) = gp::shl(gp::ref(m, k), n);` | as gc: a negative `n` panics after `k` is inserted; a constant count below the width is `gp::ref(m, k) <<= 3` |
| `m[k] = append(m[k], x)` | `gp::slice<T>& gp_r0 = gp::ref(m, k); gp_r0 = gp::append(static_cast<gp::slice<T>&&>(gp_r0), x);` | the same `m` and `k` on both sides (variables, constants, `*p`, indexes and operators of them, as gc's `SameSafeExpr`): as gc, `m` and `k` are evaluated first (into temporaries unless they are names or constants, so their panics come first; a variable key of a type that gc's fast map calls convert, such as `int` or a pointer, is copied too), then `x`, then the entry is taken once and the slice is moved |
| `delete(m, k)`, `len(m)`, `clear(m)` | `gp::erase(m, k)`, `gp::len(m)`, `gp::clear(m)` | `clear` also removes NaN keys (Go 1.21) |
| `for k, v := range m` | `for (auto gp_it0 = gp::range_map(m); gp::range_next(gp_it0);) { K k = gp_it0.gp_key(); V v = gp_it0.gp_value(); ...` | starts at a random slot and goes round the table once: a key deleted before it is reached is skipped, its value is read when it is reached, an entry added during the loop may or may not be produced (as in Go), none is produced twice, and every entry that stays in the map is produced once, also when the table grows during the loop |
| `for s[f()], v = range m` | `auto gp_t0 = gp_it0.gp_key(); auto gp_t1 = f(); s[gp_t1] = gp_t0; v = gp::range_value(gp_it0);` | targets whose operands call functions: the key is copied first and the value read after the calls (its current value, or zero if a call deleted the entry), as Go reads them; where a call deletes the entry, Go may also clear the key it assigns, gocpp assigns the key as it was |

Keys can be bools, numbers, strings, pointers, and arrays and comparable structs of them; an
array or struct value `m[k]` is a copy, so `m[k][i]` and `m[k].f` can be read but not assigned,
as in Go.
Floats follow Go: `+0` and `-0` are one key (a store keeps the new key), and a NaN key is
never found again, so each `m[NaN] = v` adds an entry. A complex key follows the same rules for
each part ([complex numbers](#complex-numbers)). The order of a range is random, as in Go
([D8](language.md#d8-map-order-is-random-as-in-go)): each map has its own hash seed and each loop its own
start. `fmt.Println(m)`
prints the keys sorted, as Go does (step 3.15); `println(m)` is an error
([D23](language.md#d23-print-and-println-of-a-slice-or-a-map)).

The order of evaluation is gc's: `m[k]` reads the table, which a call can change (also the table
of a local map, which another variable can share), so it is read after the calls of its
statement, like `*p` and `s[i]`; but as an argument of `fmt`, a value that gc doesn't convert by
value (a `bool`, `int8` or `uint8`, an array, a struct, a pointer, a map) is copied in its place
([fmt](#fmt-and-the-builtins)), and so is `m[string(b)]`. `len(m)` and `make` are evaluated in
their places among the calls. A store `m[k] = v` evaluates the calls of `m` and `k`, then `v`
(with its panics), and only then takes the entry, so `m[k] = f()` stores into the map that `m`
is after `f` ran. A map literal is evaluated in its place among the calls, entry by entry, as gc stores
it: a panic in one entry comes before the calls of the entries after it.

As in Go, a goroutine that writes a map while another reads or writes it is a data race; a write, read
or range that finds a write in progress dies with `fatal error: concurrent map writes` (or `concurrent
map read and map write`, `concurrent map iteration and map write`), which catches some races, not all.
A reference taken with `gp::ref` is valid until the next store of a new key (the table can grow).

## Floating-point numbers and package math

gocpp copies what gc does on amd64 (`GOAMD64=v1` or `v2`), bit for bit, on every platform
([ADR-071](../adr/071-math-bit-exact.md)):

| Go | Generated C++ | Notes |
|---|---|---|
| `a*b + c` | `a * b + c` | two roundings: every compile has `-ffp-contract=off` and `-fno-fast-math` (the language flags, last on the command line, so that `GOCPP_CXXFLAGS` and a package's flags can't turn them off), and no x87 (SSE2 only). Only `math.FMA` fuses. |
| `int64(f)`, `uint8(f)`, ... for a float `f` | `gp::f2i<T>(f)` | in range, truncation; out of range, NaN and infinities are Go's amd64 values (`int64`: `MinInt64`; `uint64`: see `gocpp/arith.hpp`), never C++'s undefined behavior (`-fsanitize=float-cast-overflow` stays quiet). |
| `float64(i)`, `float32(i)` for an integer | a plain conversion | rounds to nearest even, once (a `uint64` above 2^63 too). |
| `x / 0.0` of variables | `x / 0.0` | `+Inf`, `-Inf` or NaN, no panic. |
| `min(x, y)`, `max(x, y)` of floats | `gp::min`, `gp::max` | NaN wins, `-0 < +0`, as in Go. Which payload a NaN result has is not specified (ADR-071). |
| `math.Sqrt`, `Abs`, `Floor`, `Ceil`, `Trunc`, `RoundToEven`, `FMA`, `Float64bits`, ... | `::gp::math::sqrt(x)`, ... | inline natives (`gocpp/math.hpp`): the instructions that Go uses. Calls through a function value work. |
| `math.Exp`, `math.Log` | `gp::math::exp`, `gp::math::log` | Go's amd64 assembly, transcribed (`runtime/src/math.cpp`): `Exp` takes the FMA path when the CPU has AVX and FMA (`GODEBUG=cpu.fma=off` and `cpu.avx=off` switch it off, as in Go); `Log` of a subnormal number is as wrong as Go's. |
| everything else in `math` | Go's own code, ported | never `libm`: glibc rounds some results differently from Go's. |

## Complex numbers

`complex64` and `complex128` are `gp::complex64` and `gp::complex128` (`gocpp/complex.hpp`): a
struct of two floats, the real part first (8 bytes with alignment 4, and 16 bytes with alignment
8, as in Go), with only operators and `gp_`-prefixed members. gocpp doesn't use `std::complex`,
because its `*` and `/` follow C's Annex G and differ between C++ libraries; each operation here is
what Go's compiler (gc) does on amd64 with `GOAMD64=v1` or `v2`, so the results are Go's bit for bit (the sign and payload
of a NaN aside, which Go doesn't promise either).

| gocpp | C++ | Notes |
|---|---|---|
| `var c complex128`, `1 + 2i`, `var k complex64 = 1.0 / 3` | `gp::complex128 c{};`, `gp::complex128(1.0, 2.0)`, `gp::complex64(0.33333334f, 0.0f)` | go/types folds every constant expression exactly; a `complex64` constant has `float32` parts, each rounded once. A constant never has a `-0` part. Constructors are `constexpr`, so a package variable with a constant value is `constinit` |
| `complex(r, i)`, `real(c)`, `imag(c)` | `gp::complex128(r, i)`, `gp::real(c)`, `gp::imag(c)` | `complex64` from `float32` parts; a part of a named float type is its value. Like `len`, gc evaluates them in their places among the calls: in `real(g) + f()` the package variable `g` is read before `f` runs |
| `a + b`, `a - b` | `a + b`, `a - b` | each part, in the parts' own type |
| `a * b` | `a * b` | `(ar*br - ai*bi) + (ar*bi + ai*br)i`, always in `float64` (a `complex64` is widened, and the parts are rounded back), never fused (`-ffp-contract=off`) and without C's recovery of infinities: `(Inf+0i) * 2` is `(+Inf+NaNi)`, as in Go |
| `a / b` | `a / b` | Go's `runtime.complex128div` (`runtime/src/complex.cpp`): Smith's algorithm with C99's corrections when both parts are NaN; a `complex64` is divided as a `complex128` and rounded back. A division by zero gives infinities or NaN and never panics |
| `-a`, `+a` | `-a`, `a` | `-` negates each part: `-(0+0i)` is `(-0-0i)` |
| `a == b`, `a != b` | `a == b`, `a != b` | both parts equal; a NaN part is never equal |
| `c++`, `c--`, `c += x` | `c++`, `c--`, `c = c + x` | `++` adds `(1+0i)`: the imaginary part gets `+ 0`, so a `-0` part becomes `+0`, as in Go |
| `complex64(c)`, `complex128(c)` | `gp::complex64(c)`, `gp::complex128(c)` | each part converted; the constructor is `explicit`, as Go needs a conversion |
| `type Phasor complex128` | `struct Phasor : gp::newtype<Phasor, gp::complex128>` | a named type holds the value and has its operators ([named types](#named-types)); `real(p)` is `gp::real(p.gp_value())` |
| `println(c)`, `panic(c)` | `gp::println(c)`, `gp::panic(c)` | Go's runtime format, each part like a float: `(+1.000000e+000-2.000000e+000i)` |
| `m[c]` (a complex key) | `gp::get(m, c)` | hashes both parts with the float rules: `+0` and `-0` are one key, a key with a NaN part is never found again |

`fmt` prints them as Go's `fmtComplex` does: `(1.5-2i)`, each part as
a float of half the size (a `complex64` has `float32` parts) with the verb, the imaginary part
always with a sign, a width and a precision for each part (`%8.2f` is `(    1.50   -2.00i)`); a
verb that doesn't fit gives the error form with the whole number, `%!d(complex128=(1.5-2i))` (the
C++ type names `complex64` and `complex128`). `%e`, `%g`, `%x` and the other float verbs work as for floats. Complex map keys print
sorted by the real part, then the imaginary part, each with `cmp.Compare`'s rules (NaN first,
`-0 == +0`); a named complex type sorts by its value, never by the `<` that `gp::newtype`
declares. As for any value, gc copies a complex argument that is not a variable into an
interface in its place among the calls. gc fuses `x*y + z`
into one instruction on arm64, and on amd64 from `GOAMD64=v3` on, so its complex products and
quotients can differ there in the last bit; gocpp gives the unfused results (amd64's at
`GOAMD64=v1` and `v2`) everywhere, and the tests compare with Go built with `GOAMD64=v1`.

Source: [Phase 03 §2.10](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#210-builtins-printing-and-package-initialization).

## Structs

A struct is a value, as in Go: its fields are in the object itself, so assigning, passing and
returning a struct copies it.

```go
type Point struct{ X, Y int }

type Line struct {
	Point Point // a field named like its type
	Name  string
	_     int
}
```

```cpp
struct Point;
struct Line;

struct Point {
    int64_t X = 0;
    int64_t Y = 0;
    bool operator==(const Point&) const = default;
    std::size_t gp_hash() const {
        return gp::hash_fields(X, Y);
    }
    static constexpr auto gp_fields = gp::fields(gp::field(&Point::X, "X", true, false), gp::field(&Point::Y, "Y", true, false));
};
static_assert(sizeof(Point) == 16 && alignof(Point) == 8);

struct Line {
    gpkg_main::Point Point;
    gp::string Name;
    int64_t gp_blank0 = 0;
    bool operator==(const Line& gp_o) const {
        return Point == gp_o.Point && Name == gp_o.Name;
    }
    ...
};
```

| gocpp | C++ | Notes |
|---|---|---|
| `var p Point`, `Point{}` | `Point p{};`, `Point{}` | the default member initializers make the zero value |
| `Point{1, 2}` | `Point{1, 2}` | in order; C++ evaluates a braced list in order |
| `Point{Y: f(), X: 1}` | `Point{.X = 1, .Y = f()}` | designated initializers need the fields' order; the values that C++ would then evaluate too late go into temporaries first, so they run in source order, as in Go |
| `[]Point{{1, 2}}`, `[]*Point{{1, 2}}` | `gp::slice_of<Point>({Point{1, 2}})`, `gp::slice_of<gp::ptr<Point>>({gp::new_<Point>(Point{1, 2})})` | an elided type is written out |
| `&Point{1, 2}`, `new(Point)` | `gp::new_<Point>(Point{1, 2})`, `gp::new_<Point>()` | a new block, unless the escape analysis keeps it on the stack: `gp::local_new<Point>(Point{1, 2})` in a local pointer variable, `gp::borrow_tmp(Point{1, 2})` as an argument of a borrowing callee ([ADR-114](../adr/114-escape-analysis-keeps-non-escaping-objects-on-the-stack.md)) |
| `p.X`, `pp.X` (`pp` is `*Point`) | `p.X`, `pp->X` | `->` panics with Go's message for a nil `pp` |
| `o.A` (promoted from an embedded `Inner`), through an embedded `*Mid` | `o.Inner.A`, `o.Mid->M` | the path that `go/types` gives; an embedded field is a data member named after its type, never a base class |
| `&p.X` (`p` boxed), `&pp.X`, `&s[i].X`, `&global.X` | `gp::ptr<int64_t>(p, &(*p).X)`, `gp::ptr<int64_t>(pp, &pp->X)`, `gp::ptr<int64_t>(s.gp_owner(), &s[i].X)`, `gp::static_ptr(global.X)` | shares the owner of the struct ([pointers](#pointers-and-boxing)); a local whose field's address is taken is boxed, unless that address does not escape (`&v.X` passed to a borrowing callee is `gp::borrow(&v.X)` and `v` stays a plain `P v{};`) |
| `&f().X` (`f` returns `*Point`) | `gp::field_ptr(f(), &Point::X)` | the pointer is evaluated once |
| `a == b`, `a != b` | `a == b`, `a != b` | when comparable: field by field in order, floats as numbers (NaN != NaN, -0 == +0); blank fields are skipped |
| `n = n.kids[0]`, `*p = *p.next` | `n = Node(n.kids[0]);` | a struct (or an array) that holds owners, reached through a pointer or a slice that the target may own, is copied before the store, which could free it while the generated `operator=` reads it |
| `p, p.X = q, 1` | `{ auto gp_t0 = p; p = q; gp_t0->X = 1; }` | the pointer of a target `p.f` (and the slice and index of `s[i].f`) is evaluated before the values, as in Go |
| `type T struct{...}` in a function | `struct T` (or `T_1`, ...) at namespace scope | C++'s local classes can't have the static members; its descriptor still says `main.T` |
| `struct{ X int }` (anonymous) | `struct gp_anon_7132535b4707e21c` | one C++ type for identical struct types (same fields, types, tags), named by a hash of the type; its descriptor says Go's `struct { X int }` |

- **Names.** A field keeps its Go name, with the escapes of [names](#names-inside-a-package),
  and a field named like its own struct gets a `_` (`Words_`), because C++ would read it as a
  constructor. A blank field `_` is `gp_blank0`, `gp_blank1`, ... A type that a field or a
  variable of the same name hides is written qualified, `gpkg_main::Point`: GCC rejects a member
  that changes the meaning of a type name used before it in the class. A type named `gp` or
  `std` becomes `gp_` or `std_`, since it would hide the namespaces `gp::` and `std::`.
- **For `fmt`**: the descriptor of the type has the fields with their offsets ([fmt](#fmt-and-the-builtins));
  `gp_fields` lists every field (also blank and embedded ones) for `gp::convert` and for the
  fmt check of C/C++ values. `fmt.Println(p)` prints `{1 2}`.
- **Map keys**: a comparable struct has `gp_hash()` over its non-blank fields (gocpp/hash.hpp),
  so it can be a key. A struct literal of constants is a static entry of a map literal, stored
  before the others as gc does, and in `m[k] = append(m[k], x)` a struct key `k` is read before
  `x` when gc's fast map calls take it (4 or 8 bytes of plain memory, or one field that they
  take: an `int`, a string, a pointer).
- **Order of definitions**: all structs are declared first, then defined so that a struct comes
  after the structs it holds by value (also in an array); a pointer, a slice or a map of an
  incomplete struct is fine, so recursive types work.
- **Order of evaluation** is gc's: a field of a package or boxed struct, and one through a
  pointer, is read after the calls of its statement (like `*p`), and a nil pointer panics there.
  As an argument of `fmt.Println`, a struct that is not addressable (a literal, a conversion) is
  copied in its place among the calls, unless Go converts it by value (8 bytes without pointers,
  or a struct whose only field is a string or a slice), as gc does (the same rule for arrays,
  pointers and maps: [fmt](#fmt-and-the-builtins)).
- **Larger than 128 KiB**: like arrays, a local variable is boxed and a parameter is passed by
  reference; a literal that initializes a new variable, and `&Big{...}`, is made in its block,
  `gp::new_init<Big>([&](Big& gp_b) { gp_b.n = 3; })` (the zero value, then the given fields); other
  literals are temporaries on the stack ([D24](language.md#d24-large-values-on-the-c-stack)).
- **Conversions between struct types** that are not identical: a named struct type and an
  anonymous one with the same fields are two C++ structs, and so are `type B A` and `A`. Go
  converts between the first two implicitly (`var p Point = struct{ X, Y int }{1, 2}`, an
  argument, a result, an element, a map key, `==`, a case value, a range target) and between any
  two explicitly (`B(a)`, also when only the tags differ): both are `gp::convert<Point>(x)`, a
  field-by-field copy through `gp_fields` ([named types](#named-types)); a field whose types
  differ only in tags is converted too (a struct field by field, an array element by element, a
  pointer with `gp::ptr_cast`, so it still points to the same struct), but not yet a slice or a
  map of such structs. `(*B)(pa)` is `gp::ptr_cast<B>(pa)`, which points at the same struct.
- (Methods are step 3.10, embedding [below](#embedding).)

Source: [Phase 03 §2.4](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#24-structs-and-named-types).

### Embedding

```go
type Base struct{ ID int }
func (b Base) Get() int  { return b.ID }
func (b *Base) Touch()   { b.ID++ }

type User struct {
	Base // embedded
	Name string
}
```

```cpp
struct User {
    gpkg_main::Base Base;          // a data member named like its type, never a base class
    gp::string Name;
    ...
    int64_t Get() const;                    // forwarders of the promoted methods (below)
    static void Touch(gp::bptr<User> gp_p);   // Touch borrows its receiver, so does its forwarder
};
int64_t User::Get() const { return (*this).Base.Get(); }
void User::Touch(gp::bptr<User> gp_p) { gpkg_main::Base::Touch(gp::borrow(&gp_p->Base)); }
```

- An embedded field is a data member named after its type (`Base`; for a pointer or an alias the name of
  the type or alias, `*pkg.T` is `T`), in declaration order, so layout, copies, `==` and `gp_hash()` are
  the struct's own. There is no C++ inheritance: Go embedding is not subtyping.
- The type of a field is written qualified when the name of a member would change its meaning
  (`gpkg_main::Base Base;`, also `gp::ptr<gpkg_main::Base> Base;`): GCC rejects `Base Base;`, and both
  compilers reject a later use of the type name in the class. A field named like its own struct gets a
  `_` (`Node_` for `type Node struct{ *Node }`), a C++ word one too (`class_`).
- **Promoted fields and methods in the program** are written as the path that `go/types` records in
  `Selection.Index` (`o.A` is `o.Inner.A`, through an embedded `*Mid` `o.Mid->A`, which panics for
  nil with Go's message): methods.go, structs.go. `&o.Inner` and `&o.A` are pointers that share the
  owner of `o` (`gp::ptr<Inner>(o, &o->Inner)`, [pointers](#pointers-and-boxing)); through an embedded
  pointer they share the owner of what that pointer points to (`gp::field_ptr(o.Mid, &Mid::A)`).
- **Forwarding members.** Every method in the method set of `*T` that `T` gets from an embedded field
  (a selection with a path longer than one) is a member of `T`'s struct, written like a method
  that `T` declares: a `const` member function when the method is in the method set of `T` (a value
  method of an embedded value, or any method of an embedded pointer's type), else a `static` one
  whose first parameter is the owning pointer. Its body is the call through the path, with the
  receiver adjusted as for a call in the program: the fields, an embedded pointer's `->`, and
  `gp::field_ptr` for the address of an embedded value. The parameters are `gp_a0`, `gp_a1`, ... passed on
  (moved, except numbers); the definitions come after all the structs (the embedded type may be defined
  later, through a pointer), with the fmt hooks. Members that an outer field or method hides, and
  names that are ambiguous at one depth, are not in the method set, so there is no forwarder. The
  forwarders are what C++ code and the method tables call: the thunk of a promoted method in a method table is the thunk of a declared one
  (`unbox<T>(self).M(args)`, `p->M(args)`, `T::PM(p, args)`, [Interfaces](#interfaces)), and generic code
  (Phase 07) calls `u.Touch()` without knowing the path. Calls that the program makes keep the full path.
  Because only those consumers call them, the forwarders are written only for the structs that need
  them (a type that promotes 100 methods into 20 structs would be 11000 lines and 3 times the compile
  time otherwise): the structs whose descriptors have method tables, and all of them with
  `lower.Options.AllForwarders` (the tests). The names of all the forwarders hide the package's names in the
  struct whether they are written or not.
- **Method sets** follow Go (`go/types`): `T` has the value methods of an embedded `E` and all the
  methods of an embedded `*E`; `*T` has all of them; the forwarders and (with 5.4/5.5) the method tables
  have exactly those. An embedded interface brings its methods as value methods: a call through a nil
  embedded interface panics like any call of a nil interface.
- **Embedded C/C++ types** are data members like the others; their members are promoted when a struct
  has exactly one of them ([interop.md](interop.md#embedded-c-types)).

Source: [Phase 05 §2.6](../../plans/2026-10-13-gocpp/phase-05-interfaces-errors/README.md#26-struct-embedding),
`internal/lower/promote.go`.

## Named types

A named type that isn't a struct (`type Celsius float64`, `type IDs []int`) is a C++ struct of
its own over `gp::newtype<T, U>` (`runtime/include/gocpp/newtype.hpp`), so it is a distinct C++
type that can get its own methods (step 3.10) and its Go name for `fmt`:

```go
type Celsius float64
type IDs []int
```

```cpp
struct Celsius : gp::newtype<Celsius, double> {
    using gp::newtype<Celsius, double>::newtype;
};
static_assert(sizeof(Celsius) == 8 && alignof(Celsius) == 8);

struct IDs : gp::newtype<IDs, gp::slice<int64_t>> {
    using gp::newtype<IDs, gp::slice<int64_t>>::newtype;
};
static_assert(sizeof(IDs) == 40 && alignof(IDs) == 8);
```

- **Two shapes.** Over a number or a bool, `gp::newtype` holds the value (`gp_v`) and has every
  operator of the underlying type on two values of the named type, giving the named type
  (comparisons give `bool`); the result converts back to the underlying type, so a
  `type Small uint8` wraps like a `uint8`. Over a string, a slice, an array, a map or a pointer,
  the named type **is** its underlying runtime type, a public base class: everything that reads
  it works unchanged (`ids[i]`, `gp::len(ids)`, range, `gp::get(m, k)`, `p->f`).
- **Sizes**: the size of the underlying type (no members of its own), checked by a
  `static_assert` after each type; `unsafe.Sizeof` agrees.
- **Members**: only `gp_` names (`gp_value()`, `gp_hash()`) and operators, so a
  Go method of any name can't clash with them. The constructors are inherited by the base's full
  name, so a type (or, from step 3.10, a method) named `newtype` works too.
- **Names of the bases.** A base class brings its name into the struct's body: there,
  `newtype`, `string`, `slice`, `array`, `map` and `ptr` are the runtime's classes. So a type of
  the package with one of these names is written qualified in a named type's struct:
  `struct Grid : gp::newtype<Grid, gp::array<gpkg_main::array, 2>>` for `type array [2]int;
  type Grid [2]array`.
- Like structs, named types are declared first and defined in dependency order (a named array
  of structs after the struct; a struct that holds a named type by value after it), and one
  declared in a function moves to the namespace.

| gocpp | C++ | Notes |
|---|---|---|
| `var c Celsius` | `Celsius c{};` | zero |
| `c = 5`, `c * 9 / 5` | `c = Celsius(5.0)`, `c * Celsius(9.0) / Celsius(5.0)` | an untyped constant has the named type |
| `n / m`, `n % m`, `n << k`, `n >> k` | `gp::div(n, m)`, `gp::rem(n, m)`, `gp::shl(n, k)`, `gp::shr(n, k)` | Go's panics and results, as for the underlying type; a constant divisor or count below the width uses the operator |
| `n += 1`, `n++` | `n = n + N(1)`, `n++` | also on slice elements, fields and map entries (`gp::ref(m, k) += y`) |
| `Celsius(f)`, `float64(c)` | `Celsius(f)`, `c.gp_value()` | `gp_value()` is the underlying value |
| `int(c)`, `Fahrenheit(c)` | `gp::f2i<int64_t>(c.gp_value())`, `Fahrenheit(c.gp_value())` | the conversion of the underlying types, then to the named type |
| `b && c` (`type ok bool`), `x < y` as an `ok` | `ok(b && c)`, `ok(x < y)` | C++ gives `bool`; a named bool is a condition by itself (`if (ok)`) |
| `n + m` (`type Name string`), `n[1:]` | `Name(n + m)`, `Name(gp::sub(n, 1))` | the runtime gives a `gp::string`; Go's result has the named type |
| `append(ids, 1)`, `ids[1:]`, `make(IDs, n)` | `IDs(gp::append(ids, 1))`, `IDs(gp::sub(ids, 1))`, `IDs(gp::make_slice<int64_t>(n))` | the same for literals: `IDs{1, 2}` is `IDs(gp::slice_of<int64_t>({1, 2}))` |
| `s[i]` with `i` of a named integer type | `s[i.gp_value()]` | also bounds, lengths and shift counts |
| `buf[:]` (`type Buf [64]byte`) | `gp::sub(gp::base_ptr(buf), 0)` | `gp::base_ptr` makes a `gp::ptr<Buf>` a pointer to its `gp::array` |
| `switch c` (`type Color int`) | `switch (c.gp_value()) { case 1: ... }` | C++ rejects a class type in a `switch`: the value, with the constants folded |
| `var ids IDs = []int{1}`, `f(s)` for a parameter of type `IDs` | `IDs(...)` | an implicit conversion (below) |
| `var s []int = ids` | `gp::slice<int64_t> s = ids;` | C++ copies the base class |

**Implicit conversions.** Go assigns a value to a variable of another type when both have
identical underlying types and one of them is not a named type: a `[]int` to an `IDs`, an
anonymous struct to a named one. `go/types` records no conversion there, so the emitter finds
those places (an assignment or declaration, an argument, a return value, an element or a key
of a composite literal, a map index, an operand of `==` and `!=`, a case value, a range target
with `=`, and one result of several, `a, b = f()`) and converts the value: to a named type with
`T(x)`, between two struct types with `gp::convert<T>(x)`; from a named type to its unnamed
underlying type, C++'s derived-to-base copy does it. The results of a call with several results
are converted one by one: `a, b = f()` where each is stored, `return f()` as
`auto gp_t0 = f(); return {IDs(std::get<0>(gp_t0)), std::get<1>(gp_t0)};`, and `g(f())` through
a lambda that `std::apply` calls, `[](auto&& gp_e0, auto&& gp_e1) { return g(IDs(gp_e0), gp_e1); }`.

**`fmt` and `println`** print a named type as its underlying value (`%v` of a `Celsius` prints
`36.6`), with its Go name in the error forms (`%!s(main.Count=5)`) and for `%T`.
A `String()` method (step 3.10) changes that. (`fmt` reads the Go type from the descriptor of the
value, [fmt](#fmt-and-the-builtins), so a named type over `int64` needs no tag.)

**Map keys** of a named type hash their value (`gp_hash()`); in `m[k] = append(m[k], x)` a key
of a named type over `uint32`, `uint64` or `string` is read before `x`, like an `int` key,
because gc converts it to its fast map call's key type.

**Not yet**: the conversions between strings and
slices of named byte or rune types (`[]MyByte(s)`, `string([]R{...})` for `type R rune`), and
between slice types (or structs with slice or map fields) whose element structs differ only in
their tags (`[]struct{ Q int }(s)` of a `[]struct{ Q int "t" }`): Go shares the elements there,
which C++ would have to reinterpret.

Source: [Phase 03 §2.4](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#24-structs-and-named-types).

## Pointers and boxing

```go
func NewCounter() *Counter {
	c := Counter{step: 1} // its address is returned below → c is boxed
	return &c
}
```

```cpp
gp::ptr<Counter> NewCounter() {
    gp::ptr<Counter> c = gp::new_<Counter>(Counter{.step = 1});  // boxed: lives on the heap
    return c;                                                     // &c == the box itself
}
```

- `*T` is `gp::ptr<T>`, a `std::shared_ptr` with nil checks. `new(T)` becomes `gp::new_<T>()`
  (the zero value), and `&T{...}` becomes `gp::new_<T>(T{...})`, unless the escape analysis keeps
  the object on the stack (below).
- **Boxing.** Before the escape analysis (below) takes the variables that do not escape back to the
  stack, a local variable (also a parameter, a receiver copy or a named result) lives on the
  heap, in a "box", when the function takes its address or the address of anything inside it,
  calls a pointer method on it, slices an array in it, or captures it in a closure **and** changes
  it anywhere, or captures it and it is larger than 128 bytes (Go shares those with closures
  too). A local variable larger than 128 KB (Go's limit for stack variables) is boxed
  too, so it can't overflow the C++ stack. Uses of a boxed `x` become `(*x)`, and `&x` is the
  box. These are the rules of the boxing analysis (`internal/lower/box.go`); the escape analysis
  (Phase 15 step 15.2, [ADR-114](../adr/114-escape-analysis-keeps-non-escaping-objects-on-the-stack.md),
  below) then takes the variables back to the stack whose address cannot outlive them, so a variable
  is in a box now only when its address, or a closure that can outlive the call, makes it escape
  (`gocpp build -gp:m` says why: `moved to heap: x: it is returned`).
  - A boxed parameter keeps its name: the C++ parameter is copied into its box at the
    function's entry, and the box is a variable of the same name in a block around the body,
    the shape of a shadowing declaration:
    `int64_t twice(int64_t n) { gp::ptr<int64_t> gp_t0 = gp::new_<int64_t>(n); { gp::ptr<int64_t> n = static_cast<gp::ptr<int64_t>&&>(gp_t0); ... } }`
    (a class type is moved into the box too; the moves are written as casts, because g++ -O0
    leaves a line of `<bits/move.h>` in the function for a call of `std::move`). A debugger shows the value the
    parameter came with in the frame line (`twice (n=21)`) and the box as `n` in the body
    (`print *n` shows its value).
  - A boxed named result starts as a new zero box, `gp::ptr<T> r = gp::new_<T>();`, and a
    bare `return` returns `(*r)`.
  - A boxed variable of a 3-clause `for` gets a new box for each iteration (Go 1.22): before
    the post statement, `i = gp::new_<int64_t>(*i);`, so a pointer keeps the variable of its
    iteration. The variables of a `range` loop are declared in the body, a new box each time.
- **Order of evaluation.** A boxed variable and `*p` can change in any call (through a
  pointer), so like a package variable they are read after the calls of their statement, as
  gc does: in `x + f()`, `*p = f()` and `y, z := x, f()`, `f` runs first (and a nil `*p` panics
  after it). In `p, *p = q, 1` the store goes through the old `p`, which is copied first.
- **Pointers into objects** share ownership with the object (the aliasing constructor of
  `std::shared_ptr`), so they are memory safe too:

  | Expression | Owner | C++ |
  |---|---|---|
  | `&x` (`x` is a boxed local) | its box | `x` |
  | `&p.f` (`p` is a `*T`) | `p` | `gp::ptr<F>(p, &p->f)` |
  | `&s[i]` (`s` is a slice) | the slice's array | `gp::ptr<T>(s.gp_owner(), &s[i])` |
  | `&a[i]`, `&a[i][j]` (`a` is a boxed array) | its box | `gp::ptr<T>(a, &(*a)[i])` |
  | `&p[i]` (`p` is a `*[N]T`) | `p` | `gp::ptr<T>(p, &(*p)[i])` |
  | `&f()[i]` (not a variable) | the result's block | `gp::elem_ptr(f(), i)` |
  | `&globalVar`, `&globalVar.f`, `&garr[i]` | a static owner that is never freed | `gp::static_ptr(globalVar)`, `gp::static_ptr(globalVar.f)`, `gp::static_ptr(garr[i])` |

- **Escape analysis** ([ADR-114](../adr/114-escape-analysis-keeps-non-escaping-objects-on-the-stack.md)).
  A local variable whose address is taken, `&T{...}` and `new(T)` are kept on the C++ stack when every
  pointer to the object is used only as a borrowed parameter or receiver of a callee
  ([ADR-086](../adr/086-borrowed-pointer-parameters-and-receivers.md)), is compared, or is read and
  written through, and a pointer variable that holds the address (`p := &x`, `p := &T{...}`) is
  never assigned, copied, stored, returned, sent, captured, converted to an interface, passed to
  an owning parameter or to unknown code (C/C++, `unsafe.Pointer`, an interface method or a func
  value), or used by `go` or `defer`. `gocpp build -gp:m` prints the decisions like
  `go build -gcflags=-m`.

  Limits: only a variable declared by a statement of a block, or an allocation held by a local
  pointer variable or passed straight to a call, is an object (a parameter, a result or the
  variable of a loop header keeps its box when its address is taken); an object is kept on the
  stack only when it is at most 2 KiB, and all of them together at most 16 KiB for one function
  (the C++ stack is fixed, and a function can call itself); the functions and methods of generic
  types are not analysed, so an instance of a generic function boxes as before; a variable whose
  address goes to a method that keeps its receiver (`sync.Mutex`'s `Lock`) escapes. A parameter or a
  result that a local closure captures and changes is still boxed (`moved to heap: p: a closure
  captures it and it changes`).

  | Go | C++ |
  |---|---|
  | `var c T; c.Inc(); bump(&c)` | `T c{}; T::Inc(gp::borrow(&c)); bump(gp::borrow(&c));` |
  | `p := &c` | `gp::ptr<T> p = gp::stack_ptr(c);` (a `gp::ptr` that owns nothing: copies cost no count) |
  | `p := &T{...}`, `p := new(T)` | `gp::local_ptr<T> p = gp::local_new<T>(T{...});` (the object is a member of the pointer variable) |
  | `bump(&T{...})` | `bump(gp::borrow_tmp(T{...}))` (a temporary of the call) |

  A variable that stays on the stack is still "memory that a call can change" for the order of
  evaluation (it keeps its entry in the map of boxed variables, with the reason `boxStack`).
  `-gp:noescape` turns the analysis off.
- Dereferencing a nil `gp::ptr` (`*p`, `p->f`, also `&p->f`) panics with Go's message:
  `runtime error: invalid memory address or nil pointer dereference`. Unrecovered, it also
  prints Go's signal line (`[signal SIGSEGV: ...]`).
- `p == nil` is `p == nullptr`, and `p == q` compares the addresses. A conversion between
  pointer types whose base types have identical underlying types, `(*Q)(p)`, is
  `gp::ptr_cast<Q>(p)` (`(*B)(pa)` for `type B A`); `(*int)(nil)` is
  `gp::ptr<int64_t>(nullptr)`. `&*p` is `gp::ptr<T>(p, &*p)`: Go's `&*p` panics for a nil `p`.
- `weak.Pointer[T]` is `gp::weak_ptr<T>`: `weak.Make(p)` is `gp::weak_make<T>(p)` (the type
  argument written out, so that `weak.Make[T](nil)` works) and `w.Value()` is
  `gp::weak_value(w)` (free functions, since runtime types have no plain-named members); through
  a pointer, `pw.Value()` is `gp::weak_value(*pw)`, which panics for a nil `pw`.
  `weak.Pointer[T]{}` is `gp::weak_ptr<T>{}`, and `==` compares the addresses the weak pointers
  were made from (also after the target is gone, as in Go). Method values (`f := w.Value`) and
  method expressions (`weak.Pointer[T].Value`) call `gp::weak_value` too. `weak` is a compiler
  intrinsic until generics come (Phase 07): the stub `stdlib/weak` gives go/types Go's
  declarations, and a type defined over it (`type WP weak.Pointer[T]`, not an alias) is gated to
  Phase 07. fmt prints a weak pointer as Go prints the struct Go declares for it,
  `struct { _ [0]*T; u unsafe.Pointer }`: `{[] <nil>}` for the zero value, `{[] 0xc000012345}`
  otherwise (gocpp's address is the one the weak pointer was made from, Go's that of its own
  handle: both differ from run to run), and `%T` names it `weak.Pointer[main.T]`.
- Freeing a long chain (a list of millions of nodes) doesn't recurse deeply: past a depth of
  128, the runtime puts the rest on a per-thread list and frees it in a loop.

Source: [Phase 03 §2.2](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#22-pointers-and-boxing).

## Closures

```go
func counter(step int) func() int {
	n := 0
	return func() int {
		n += step
		return n
	}
}
```

```cpp
gp::func<int64_t()> counter(int64_t step) {
    gp::ptr<int64_t> n = gp::new_<int64_t>(0);              // boxed: captured + changed
    return gp::func<int64_t()>([n, step]<int = 1>() mutable -> int64_t {
        (*n) = (*n) + step;
        return (*n);
    });
}
```

- A func value is a `gp::func<R(A...)>` (`gocpp/func.hpp`): the owner of the closure (a
  `std::shared_ptr`) and the function that calls it, 24 bytes. Copies share the closure, as Go's
  func values do. A function of the package as a value is `gp::func_of<&gpkg_main::f>()`, a
  closure without captures needs no allocation either, and a nil func is `nullptr`
  (`f == nullptr` is `f == nil`). Calling nil panics with Go's nil dereference message and signal
  line. A parameter larger than 128 KiB is a `const A&`, as in a function declaration.
- A closure that can outlive the call (every closure except the local closures below) is a C++ lambda
  with an explicit capture list. A captured variable of at most 128
  bytes (gocpp's size) that never changes after its initialization (and whose address is never
  taken) is **captured by value**: it is copied once, when the closure is made, which gives the
  same values, as it never changes. Any other captured variable is **boxed** (also a larger one
  that never changes: Go shares those too, so many closures of a big array share one array), and the lambda captures the box, so the closure and
  the function see the same variable, as in Go. The lambda is `mutable`, so the copies are not
  `const`. Nested closures, parameters and named results are captured the same way.
- A **local closure** ([ADR-114](../adr/114-escape-analysis-keeps-non-escaping-objects-on-the-stack.md))
  is a literal that is only called where it is made: `func() { ... }()` or `f := func() { ... }`
  with every use of `f` a call that runs at once (not `go`, `defer`, another literal or the body
  of a range over a func), and no `recover`. It is a raw lambda that captures by reference
  (`auto f = [&n]<int = 1>(int64_t d) mutable { n += d; };`, no `gp::func`, no allocation), and a
  variable that only local closures capture need not be boxed (a parameter or a result is still boxed). Formerly boxed captures are subject
  to the same 2 KiB object limit and shared 16 KiB storage budget as address-taken locals; larger
  captures, parameters and results keep their boxes. A variable that anything else captures is
  boxed as above, and the local lambda captures its box. `-gp:m` prints
  `func literal does not escape` or `func literal escapes to heap`.
- The body of a func literal is lowered like a function's (its parameters, named results, its
  own `defer` frame, break and continue), and written over several lines, each statement at its
  `.gp` line, so gdb stops and steps in a closure. A literal on one `.gp` line stays on one C++
  line.
- `<int = N>` is the literal's number in the function around it, as Go numbers them in stack
  traces (`main.main.func1`, `main.main.func1.1`, `main.init.func2` for a package variable's
  initializer, `main.T.M.func1` and `main.(*T).M.func1` in methods): the trace reads it from the
  lambda's mangled name, the same for g++ and clang++. A closure in a method captures the
  receiver like any other variable (a pointer receiver's pointer, a value receiver's copy).
- Calls: `f(x)` for a func value that the call can't change (a local variable that isn't boxed,
  a temporary), `f.gp_call(x)` for any other (a package or boxed variable, a field, an element),
  which keeps the closure alive while it runs (`f = nil` inside `f`). gc's order: a func value is
  read after the calls of its arguments (`f(g())` where `g` changes the package variable `f`
  calls the new `f`), unless it has a call in it (`fs[i()](g())`, `f()(g())`), which gc
  evaluates first. A literal called at once is called in place: `[...]() { ... }()`, over
  several lines `[...]() { ... }.operator()()`, so that clang++ gives the call the line Go gives
  it.
- A func that goes to C/C++ code (an argument of a C/C++ call, a C variable, member or literal element) is
  wrapped in `gp::cgo::callback`: `gp::cgo::fn<&gpkg_main::f>()` for a function of the package,
  `gp::cgo::fn_lit<gp::func<R(A...)>>(lambda)` for a literal without captures,
  `gp::cgo::fn_val(f)` for any other func. The first two convert to a C function pointer (a static
  `noexcept` trampoline), all three are callables for C++ ([interop.md](interop.md#callbacks-and-panics)).
- `defer f(x)` stores a copy of `f` with the arguments (`gp_df.gp_push_call(f, x)`; a nil `f`
  panics when the deferred call runs, as in Go), and `defer func() { ... }()` stores the lambda
  itself. A deferred closure that changes a named result changes what the function returns:
  the result is captured and changed, so it is boxed, and the exit returns the box's value.
- Go 1.22 loop variables: each iteration has its own variable. Only when a loop variable is boxed
  does gocpp make a new box per iteration, with the post statement applied to the new one.
- A closure in a package variable's initializer is lowered in `gp_var_init`, with the same
  boxing analysis.
- A local that holds a C/C++ object (Phase 04) and that a closure uses is always boxed, whether
  or not the closure assigns it, because a member call or a C++ function can change the object
  without an assignment: `auto v = gp::cgo::box([&] { return ::std::vector<int64_t>{}; });`, and the
  closure copies the box ([interop.md](interop.md#cc-objects-in-closures-and-defer)).
- A named func type (`type Handler func(int)`) is a `gp::newtype` over its `gp::func`, so it is
  called, compared with nil and passed like one; a func literal passed as a `Handler` is converted
  explicitly (`Handler(gp::func<void(int64_t)>(...))`), as Go converts it implicitly.
- `f(g())`, where `g` has several results, is `std::apply(f, g())`; when `f` is variadic, or Go
  converts some of the results, a generic lambda between them converts them and makes the slice:
  `std::apply([](auto&& gp_e0, auto&& gp_e1) { return gpkg_main::sum(gp::slice_of<int64_t>({gp_e0,
  gp_e1})); }, g())`.
- A closure that captures the variable that holds it (`var f func(); f = func() { f() }`) is a
  reference cycle, which is never freed (D1): it lives until the program ends, and
  LeakSanitizer reports it.
- Printing a func value (`fmt.Println(f)`, `println(f)`, also inside a struct) is not supported
  yet: Go prints the address of the func's code.

Source: [Phase 03 §2.6](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#26-functions-func-values-closures).

## Defer

```go
func load(n int) (count int) {
	defer add(&count, 1)
	defer fmt.Println("done", n)
	if n < 0 {
		return 0
	}
	return n * 2
}
```

```cpp
int64_t load(int64_t n) {
    gp::ptr<int64_t> count = gp::new_<int64_t>();     // boxed: &count is taken
    gp::defer_frame gp_df; try {
        gp_df.gp_push(add, count, 1);
        gp_df.gp_push_call([](auto&& gp_a0) { gp::fmt::Println("done"_gs, gp_a0); }, n);
        if (n < 0) {
            (*count) = 0; goto gp_ret0;
        }
        (*count) = n * 2; goto gp_ret1;
    } catch (gp::panic_error& gp_p) {
        gp_df.gp_take(gp_p);
    } catch (...) {
        gp_df.gp_adopt();
    }
    gp_df.gp_run(); return (*count);                  // the end of the body, or a panic
    gp_ret0:; gp_df.gp_run(); return (*count);        // at the line of the first return
    gp_ret1:; gp_df.gp_run(); return (*count);
}
```

- A function with a `defer` statement (also `main` and the `init` functions) gets the
  **single-exit shape**: a `gp::defer_frame`, the body in a `try` block, and one way out that
  runs the deferred calls. Functions without `defer` keep their plain shape.
- **The results are variables**, declared before the frame: named results keep their names, the
  others are `gp_r0`, `gp_r1`, …. A `return x` assigns them (with Go's order) and jumps to its
  own exit, which runs the deferred calls and then returns the variables. So, as in Go, the
  results are set before the deferred calls run, and a deferred call that changes a named result
  through a pointer changes what the function returns (`load(3)` returns 7). Each `return` has
  its own exit at its own line, so a panic in a deferred call shows the function at the line of
  that `return`, as in Go; the end of the body (and a panic) uses the exit at the closing brace.
- **`defer f(a, b)` evaluates `f` and its arguments at the defer statement**, in Go's order (the
  same as for the call `f(a, b)`): `gp_df.gp_push(f, a, b)` stores the function pointer and the
  arguments, converted to the parameter types (an array or struct larger than 128 KiB, which
  the function takes by const reference, is copied to the heap there, `gp::detail::big_arg`, not
  onto the C++ stack; `go f(a)`, `gp::go_fn`, does the same, and so do the ordered snapshots of
  arguments that a sibling's C++ copy needs, but for the shapes that ADR-086 lists. A literal, a
  call's result or a struct conversion, `gp::convert<S>(v)`, as the argument is still a C++
  temporary on the stack: `defer f([1 << 20]int{1: 3})` still overflows it, D24). A builtin or `fmt`
  call is stored as a generic lambda with the arguments that are not constants:
  `gp_df.gp_push_call([](auto&& gp_a0) { gp::println(gp_a0); }, x)`. The frame keeps a few calls in
  a small buffer inside it, and more (or bigger ones) on the heap. Defers in a loop accumulate until
  the function returns, and run last in, first out.
- **A panic runs the deferred calls too**: the `catch (gp::panic_error&)` keeps it (`gp_take`),
  `gp_run` runs the calls and throws the same panic again, so the trace still shows where it
  started, unless a deferred call recovered it (below). The handler for the panic is typed, and
  the one for everything else (`catch (...)`, `gp_adopt`) comes after it: a Go panic costs one
  throw, not a second one to find out its type.
- **A panic statement in a function with defers doesn't throw**: `panic(v)` in the function
  itself (not in a func literal, nor in the body of a range over a func) is
  `gp_df.gp_panic(gp::new_panic(v)); goto gp_pan0;`. The frame takes the panic as the handler
  would, and the `goto` leaves the try block, destroying its locals in the order the unwinding
  would, to the exit that runs the deferred calls (`gp_pan0:; gp_df.gp_run(); return ...;`, at the
  closing brace). The result is the same, what the deferred calls and `recover()` see, the chain,
  and the trace; what is saved is the C++ throw, a walk of the stack by the unwinder, which costs
  about a microsecond for a panic that a function recovers itself. A panic that comes from a
  callee (or a runtime error) is thrown.
- **A panic records its stack at the throw, up to the function that handles it**: the C++
  unwinding removes the frames before `run_main` sees the panic, and a walk of the stack costs
  about 50 ns a frame and 100 ns to start. So `gp::panic_error` walks only the frames from the
  throw up to the frame of the innermost function with a `defer_frame` (the frames are listed in a
  thread-local list, 4 bytes in each frame: `detail::top_defer`), and the rest of the stack, the
  callers of that function, is still on the stack when its `gp_run` knows that no deferred call
  recovered the panic: `gp_run` records it just before it throws the panic again
  (`panic_error::gp_complete`). A panic that is recovered never walks the callers. With no
  function with defers on the stack, or with AddressSanitizer (which moves locals to a fake
  stack), the whole stack is recorded at the throw, as before. (On Windows x86-64 the walk is a
  loop of `RtlVirtualUnwind` over the unwind tables of the PE file, `src/os/windows/trace.cpp`; it
  also reaches stacks of more than 300 frames, which `RtlCaptureStackBackTrace` in chunks did not.) The trace of an unrecovered panic is the same either way (the frames of
  the panic point, then the callers). A deferred call that
  panics doesn't stop the others: its panic replaces the running one, and the running one goes
  into its chain. An unrecovered panic prints the whole chain, the first panic first, as Go
  does (`panic: first` then `\tpanic: second`), and the signal line of a nil dereference once,
  after the chain. As in Go, two neighbouring panics of the chain whose values have the same
  interface words are printed once, as `panic: x [recovered, repanicked]` (also without
  `recover`): the same constant (gc also counts a local variable that only its declaration gives
  a constant), a value that gc keeps in static data (a bool, a 1-byte integer, a 2-, 4- or
  8-byte number whose bits are below 256, the empty string), or the same runtime error of the
  ones Go keeps in one place (nil dereference, division by zero, negative shift, a store into a
  nil map). (gc also gives that identity to a value from an inlined call of a function that
  returns a constant, `n := five()`; gocpp doesn't, and prints both panics.) The trace shows
  each deferred call on top of the panic that it ran in, with a `panic(...)` frame between
  them, as Go's does.
- **What the handlers keep** (`gp_take` and `gp_adopt`, step 5.10; `gp_on_exception` does both
  for code that doesn't know the type): a Go panic
  (`gp::panic_error`), as it is; `runtime.Goexit` (`gp::goexit_signal`): the deferred calls run, a
  `recover()` in them returns nil and `gp_run` throws it again at the end (a Goexit in a deferred
  call replaces the panic that was running, as in Go); a C++ exception that is neither, as a Go
  panic whose value is a `gp::CppException` (an `error`: `C++ exception <type>: <what()>`), so
  the deferred calls run for it and `recover()` can stop it ([interop.md](interop.md#c-exceptions));
  `std::bad_alloc` is Go's fatal error `out of memory` at once. A forced unwind (`pthread_exit`
  in C code) is thrown again at once, untouched, running no deferred call: it must pass, and
  running Go code during it isn't safe. A deferred call that throws one of these during a panic
  does what a deferred call that panics does (below).
- **`recover()`** (step 5.10) follows Go's rule: it stops a panic only when the function that
  contains the call is the function that the deferred-call machinery called, not a function
  that one of its callees calls. The function may be reached any way (a function, a method, a
  func value, a method value, an interface method, `defer mk()()`, a deferred func literal). A
  function that contains `recover()` is *aware*: its first statement takes the ticket that
  `gp_run` leaves for the call it makes, and `recover()` is `gp::recover(gp_dc)`:

  ```cpp
  void handler() {
      gp::defer_ctx gp_dc = gp::take_defer_ctx();   // the ticket: null unless gp_run called us
      gp::any r = gp::recover(gp_dc);               // nil, or the panic's value
      ...
  }
  ```

  `gp_run` gives the ticket only while it runs its calls for a panic that isn't recovered, to a
  call it knows to be aware (and takes it back when the call ends, so nothing the call calls can
  find it): `gp_df.gp_push_aware(f, ...)` for a function of the package that has a `recover` of
  its own, `gp_push_call_aware(lambda, ...)` for a deferred func literal or a method that has
  one, `gp_push_call_icall` for a call of an interface method (`gp::icall` looks at the ticket
  and clears it unless the thunk of that method is registered as aware:
  `gp::method_of_aware` in the method table), and a deferred func value (`gp::func`) is looked up
  by its code: a func literal that contains `recover` is made as `gp::func<Sig>(gp::aware(lambda))`,
  a function of the package that does as `gp::func_of_aware<&f>()`, and a method value of an aware
  or an interface method as `gp::aware(lambda)`. A normal call of an aware function finds no
  ticket, so its `recover()` returns nil, as in Go. A `defer recover()` is a lambda that calls
  `gp::recover(gp_dc)` with the function's own ticket when the function ends: it stops the panic only
  when that function is itself the deferred call that a panic runs (and does nothing otherwise, as
  in Go). When
  the call that recovered the panic returns, `gp_run` drops the panic, runs the other deferred
  calls as for a normal return, and the function returns normally, with the named results as its
  deferred calls left them (a result that was never set is its zero value). A panic that is
  recovered but still in a chain (the deferred call that recovered it panicked again) prints
  with `[recovered]`. The phase 05 README planned two entry points for such a function; the
  ticket does the same without a second copy of the function and without a larger `gp::func`.
  Functions without `recover` and without `defer` emit what they always did.
- **Stack:** the frame is 96 bytes, with room for one call (more go to the heap). At `-O0` a
  function with one defer takes about 160 to 185 bytes of C++ stack per call (g++, clang++),
  where the same function without it takes 24 to 32: with the default 8 MiB stack, a recursion
  with a defer at each level gets to about 40,000 to 50,000 levels, where Go's growing stack goes
  on (the C++ stack doesn't grow, as for large values:
  [D24](language.md#d24-large-values-on-the-c-stack)).
- **C++ destructors** of the body's locals run when their block ends, so before the deferred
  calls. That only matters for C/C++ objects (Phase 04): a C/C++ local that a deferred call is made
  on (`defer v.clear()`) is boxed, and the frame keeps the box
  ([interop.md](interop.md#cc-objects-in-closures-and-defer)).
- **Results of C/C++ types** (Phase 04): an unnamed result of a C/C++ type is a
  `gp::result_slot<R>` instead of `R gp_r0{};` (a class with no default constructor, a move-only
  class and a reference work there), a local that is returned is moved into it, and the exit returns
  `gp_r0.gp_take()` ([interop.md](interop.md#types-that-cant-be-copied)). (ADR-011 and the phase
  README called its members `.set` and `.take`; runtime types have only `gp_`-prefixed members.)
  A function that recovers a panic returns the zero value of an unnamed result, which a result
  of such a type may not have: a result that was never set is then a fatal error, not an access to
  a missing object.
- `-nochecks` doesn't change any of this. `os.Exit` (`gp::os::exit`, Phase 09) ends the program
  without running the deferred calls, as in Go, also from a deferred call.

Source: [Phase 03 §2.8](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#28-defer-without-recover).

## fmt and the builtins

`fmt.Print`, `Println`, `Printf`, `Sprint`, `Sprintln`, `Sprintf`, `Fprint`, `Fprintln`, `Fprintf`,
`Append`, `Appendln`, `Appendf`, `Errorf` and `FormatString` are the runtime's
(`runtime/include/gocpp/fmt.hpp`, `runtime/src/fmt.cpp`): a port of Go 1.25's `fmt/print.go` and
`fmt/format.go` that walks values by their type descriptors, as Go's walks them by reflection
([ADR-028](../adr/028-fmt-on-descriptors.md)). The `Sprint` functions return a `gp::string`,
`Errorf` a `gp::error`, the others Go's `(n int, err error)` as a `std::tuple<int64_t, gp::error>`.

```go
var big int64 = 5
fmt.Println(n, s, ok)
fmt.Println(p, xs, big, err)
fmt.Printf("%5d|%-6.2f|%v\n", n, f, m)
fmt.Fprintln(os.Stderr, "failed:", err)
return fmt.Errorf("read %s: %w", name, err)
```
```cpp
gp::fmt::Println(n, s, ok);                                   // C++ says the Go type: no descriptor
gp::fmt::Println(gp::fmt::as(&gp_td_Point, p), gp::fmt::as(gp_tdc_0, xs), gp::fmt::as(&gp::td_int64, big), err);
gp::fmt::Printf("%5d|%-6.2f|%v\n"_gs, n, f, gp::fmt::as(gp_tdc_1, m));
gp::fmt::Fprintln(gp::fmt::stderr_, "failed:"_gs, err);
return gp::fmt::Errorf("read %s: %w"_gs, name, err);
```

- **Operands.** An operand is a value of its exact C++ type, taken by value. A value whose C++
  type says its Go type (`bool`, `int` as `int64_t`, `uint` as `uint64_t`, `int8` to `int32`, `uint8`
  to `uint32`, `float32`, `float64`, `complex64`, `complex128`, `string`) is passed as it is. An
  interface value (`any`, `error`, `fmt.Stringer`, any interface) is passed as it is too: `fmt`
  uses its dynamic type, and the nil interface prints `<nil>`. Every other operand is
  `gp::fmt::as(descriptor, value)`: the descriptor of its Go type ([interfaces](#interfaces)),
  which is how `int64`, `uint64` and `uintptr` (the same C++ types as `int` and `uint`), named
  types, structs, slices, maps and pointers are told apart. An untyped `nil` is `gp::any()`. An
  operand of a type that has an `Error` method and is no pointer is converted to an `any` first,
  so `Errorf` can wrap it. An array or struct larger than 128 KiB is copied to the heap,
  `gp::fmt::heap(gp::new_<A>(a))`, not onto the C++ stack.
- **Everything prints as in Go**: the engine is Go's, so every verb (`%v %+v %#v %T %d %s %q %x %X %o
  %O %b %c %U %e %E %f %F %g %G %t %p %w`), flag (`+ - # 0` and space), width and precision
  (also `*`), argument index (`%[2]d`) and error form (`%!d(string=hi)`, `%!d(MISSING)`,
  `%!(EXTRA int=2)`, `%!(NOVERB)`, `%!(BADWIDTH)`, `%!(BADINDEX)`, `%!z(int=5)`) is. Maps print
  sorted by key (`internal/fmtsort`), a pointer to a struct, array, slice or map prints `&{...}`
  at the top level and its address below, a nil is `<nil>`, a struct `{1 2}`, `{X:1 Y:2}` with
  `%+v` and `main.T{X:1, Y:2}` with `%#v`. Width, precision and flags apply to each element of a
  composite value.
- **Methods**: `Format(f fmt.State, verb rune)` takes over every verb; `GoString() string` does
  for `%#v`; `Error() string` (first) and `String() string` for `%v %s %q %x %X` and by `Print` and
  `Println`, not for `%d`. They are looked up in the method table of the value's descriptor, so
  they work for a value in an `any`, in a slice, in a map, in a struct field (not in an
  unexported field, where Go's reflection can't call them either, except the exported fields of
  an embedded unexported struct), and for a pointer. A panic in a method prints
  `%!v(PANIC=String method: boom)`, or `<nil>` for a nil receiver, as Go's. `fmt.State` is a
  runtime interface (`gp::fmt::State`); `fmt.Stringer`, `fmt.GoStringer`, `fmt.Formatter` and
  `fmt.State` are runtime interface structs like `error`.
- **Writers**: `Fprint`, `Fprintln` and `Fprintf` take a `fmt.State` (the `f` of a `Format` method) or any
  value with a `Write([]byte) (int, error)` method: an `io.Writer`, a `*os.File` (`os.Stdout` is the
  variable of package `os`, since step 9.6, so assigning it redirects the call), a `*strings.Builder`. A
  value that is no interface is converted to `io.Writer` first; the call makes one `Write` call with the
  whole text (`gp::fmt::write_to`). The call needs the package `io` (the type `io.Writer`); Go's `fmt` imports
  it, so the build adds `io` to a program that calls a `Fprint` function with a writer of its own (not with a
  `fmt.State`) and does not import it. `fmt.Fprintf` and the other functions work as func values too, and with
  `import . "fmt"`. `Print`, `Println` and `Printf` flush C's stdio first and write once to the file that the
  variable `os.Stdout` holds when the program has assigned another file to it (`os.Stdout = w`, the usual way to
  capture output), copied one over it (`*os.Stdout = *w`) or closed the original, else once to descriptor 1
  ([interop](interop.md#printing-cc-values)); a failed write returns `(0, error)` as Go's. The assignments to `os.Stdout`, `os.Stdin` and
  `os.Stderr` are atomic stores (`gp::fmt::store_std`), so a goroutine that swaps them while others print cannot
  free a file under a printer, and `File.Close` of the original stream leaves its descriptor open until the prints in flight have ended
  ([ADR-100](../adr/100-fmt-stays-native-decision-9-7-a.md) lists what this does not cover).
- **Scanning**: `Scan`, `Scanln`, `Scanf`, `Sscan`, `Sscanln`, `Sscanf`, `Fscan`, `Fscanln` and `Fscanf` are the
  runtime's too (`gocpp/fmtscan.hpp`, `runtime/src/fmtscan.cpp`: a port of Go's `fmt/scan.go`, driven by the type
  descriptors of the pointer arguments as the printer is driven by the descriptors of its operands). The texts of the
  errors, the rules for spaces and newlines, the verbs and the widths are Go's. A pointer to a named type is scanned by
  the kind of the type, as Go's reflection does. `fmt.Scanner` (a `Scan(state fmt.ScanState, verb rune) error`
  method, found in the method table of the argument) and `fmt.ScanState` (`gp::fmt::ScanState`, a runtime interface
  over the scanner, with `Fscan` on it for scans inside scans) are runtime interface structs like `fmt.State`.
  `Fscan` reads through the `ReadRune` and `UnreadRune` methods of the reader when it has them and a byte at a time
  through `Read` when it has not (one rune of look-ahead is lost between two calls, as in Go). `Scan`, `Scanln` and
  `Scanf` read file descriptor 0 themselves, a byte at a time and unbuffered, until the program assigns another file to the
  variable `os.Stdin` (or copies one over it, or closes the original): they read what `os.Stdin` holds then, in every package and
  through func values (`gp::fmt::set_os_stdin`). `io.EOF` and `io.ErrUnexpectedEOF` are the runtime's
  two values (package `io`'s variables are set from them), so `err == io.EOF` holds for the scanner's errors. Number
  errors have Go's texts (`strconv.ParseInt: parsing "9999999999999999999": value out of range`) but are plain
  errors, not `*strconv.NumError`.
- **Errorf**: without `%w` the result is a `*errors.errorString`, with one `%w` a `*fmt.wrapError`
  (`Unwrap() error`), with several a `*fmt.wrapErrors` (`Unwrap() []error`): the runtime's own types
  (`runtime/src/fmt.cpp`), whose names `%T` prints as Go does.
- **C/C++ values** print by their C++ type ([interop](interop.md#printing-cc-values)).
- **Limits.** The printer recurses once per level of nesting, on the C++ stack: `fmt.Sprint` of a
  slice of slices of `any` about 10,000 levels deep (a recursive data structure built by a
  program) overflows the 8 MiB stack at `-O0`, where Go goes on past 100,000 levels. A `map[any]V` whose
  keys have different types prints those groups in an order of its own (Go orders them by the
  addresses of the types, which is unspecified). A C++ class held in an `any` prints through its
  `std::formatter` or `operator<<` only if a `fmt` call in the program names its type
  (`gp::cgo::fmt_arg`); an exception from that text, or from a method, prints as
  `%!v(PANIC=String method: C++ exception ...)`. The structs of package `sync` and `sync/atomic` are flatter than Go's, so
  `%+v` of a struct that holds a `sync.Mutex` shows `{state:0 sema:0}` where Go 1.25 shows `{_:{} mu:{state:0 sema:0}}`.
  Allocation counts (`testing.AllocsPerRun` of a `Sprintf`) are not Go's.
- **A final `a...`** (a `[]any`, as in `logf(f string, a ...any) { fmt.Printf(f, a...) }`) is `gp::fmt::spread(a)`: its elements are the operands, not one operand; the slice is held for the call, and the printer reads each element when it prints it (`live_span`), so a `String` method that stores into the slice changes the operands after it, as in Go.
- **A call with several results**, `fmt.Println(f())`, goes through `std::apply` and a lambda that
  describes each result.
- **Arguments are values at the call**: `fmt` takes each argument by value, as Go copies it
  into an interface. The order of evaluation is gc's: a variable (also a slice, an array, a map
  or a pointer) is read after the calls of its statement, so `fmt.Println(s, grow())` prints the
  `s` that `grow` made; a value that is not addressable is copied in its place among the calls,
  unless gc converts it by value (a 2-, 4- or 8-byte value without pointers, a string, a slice):
  `fmt.Println(m["k"], change())` prints the old `m["k"]` for a map of arrays, structs, pointers
  or maps, and the new one for a map of ints or slices.
- **A local that a closure changes**: gc also copies such an argument in place when it is a
  small local variable (and a field of one), unless its escape analysis moved the variable to the
  heap, which depends on gc's inliner: `ok := false; set := func() bool { ok = true; return ok };
  fmt.Println(ok, set())` prints `false true`. gocpp approximates it with a rule on the code
  (`lower/inplace.go`): it copies such a local when every func literal that captures it is called
  at once or held by a local that is only ever called, and has no `defer`, `go` or `recover` in
  its own body; otherwise it reads the new value. A part of a plain local that gc keeps in
  registers is copied too where an index could change: `fmt.Println(one[k], setk())` of a
  `var one [1]bool` reads `one[k]` before `setk` runs, as in Go. A parameter of a func literal
  is read after the calls, while gc copies it when it inlines the literal (its parameters become
  the caller's locals): `f := func(a [1]bool) { fmt.Println(a[gk], setk()) }; f([1]bool{})`
  prints `false 0` in Go and panics in gocpp ([D25](language.md#d25-fmt-arguments-that-a-closure-changes)). Where gc's inlining budget decides otherwise,
  the output can differ ([D25](language.md#d25-fmt-arguments-that-a-closure-changes)).
- **`min` and `max`** of non-constant values are `gp::min<T>(x, y, ...)` and `gp::max<T>(...)`
  (`gocpp/minmax.hpp`), with `T` the result type, Go's rules for floats (a NaN wins, `-0` is less
  than `+0`) and strings; named types compare their values. A constant call is folded. Like
  `len`, they are evaluated in their places among the calls.
- **`print` and `println`** (`gocpp/print.hpp`) write to stderr in the runtime's format; a pointer
  prints its address (`0x0` for nil). A slice or a map is a compile error
  ([D23](language.md#d23-print-and-println-of-a-slice-or-a-map)), and so are arrays and structs, as
  in Go.
- Complex numbers (`complex`, `real`, `imag`, and printing them) work (Phase 03 and step 5.11's fmt).

## Package initialization

```cpp
void gp_init_all() {                      // generated by the driver for the final program
    ::gpkg_c::gp_var_init();      ::gpkg_c::gp_init_funcs();
    ::gpkg_z::gp_var_init();      ::gpkg_z::gp_init_funcs();
    ::gpkg_b::gp_var_init();      ::gpkg_b::gp_init_funcs();
    ::gpkg_main::gp_var_init();   ::gpkg_main::gp_init_funcs();
}

int main(int argc, char** argv) {
    return gp::run_main(argc, argv, &gp_init_all, &gpkg_main::main);
}
```

Here package `main` imports `b` and `c`, and `b` imports `z`. Go 1.25 runs the inits in the order
`c`, `z`, `b`, `main`.

- **Inside a package**, package-level variables are set in Go's dependency order
  (`types.Info.InitOrder` from `go/types`), inside a generated `gp_var_init()`: a variable comes
  after every variable that its initializer refers to, also through functions, methods, method
  values and func literals, and otherwise in declaration order, across the files of the
  package (which the loader sorts by name, as the go command does). `var a, b = f()` calls `f`
  once (`auto gp_t0 = f(); a = std::get<0>(gp_t0); ...`) and `var _ = f()` still calls `f`.
  Then the `init()` functions (renamed `gp_init_1` … `gp_init_n`) run in source order, file by
  file, from `gp_init_funcs()`, each to its end (its deferred calls too) before the next. `init`
  can't be called or referred to (`undefined: init`, go/types' error, as in Go).

  ```go
  var total = sum(values) // after values
  var values = []int{1, 2}
  var origin = point{1, 2}
  var cells = [1 << 21]int{0: f()}

  func init() { println(total) }
  ```

  ```cpp
  constinit int64_t total{};
  constinit gp::slice<int64_t> values{};
  constinit point origin{1, 2};                  // a literal of constants: at compile time
  constinit gp::array<int64_t, 2097152> cells{};

  void gp_init_1() { gp::println(total); }

  void gp_var_init() {
      values = gp::slice_of<int64_t>({1, 2});
      total = sum(values);
      cells[0] = f();                            // built in place: no 16 MiB temporary
  }

  void gp_init_funcs() { gp_init_1(); }
  ```

- A panic during initialization prints Go's trace: the initializers of the package variables
  are in `main.init` (at the variable's line), the init functions are `main.init.0`,
  `main.init.1`, … in source order across the files, and a func literal is `main.init.func1` in
  a variable's initializer and `main.init.0.func1` in an init function.
- **Across packages**, gocpp uses Go's rule since Go 1.21: sort all packages by import path, then
  again and again initialize the **first** package in that list whose imports are all
  initialized. This is the order of `load.Program.Packages`; the emitter writes `gp_init_all()` in
  `pkg_init.cpp` of the main package, with a call of `gp_var_init()` and `gp_init_funcs()` of each
  package that has any (each declared in its `pkg.hpp`).
- Package variables are declared `constinit`, so C++ runs no dynamic initializers of its own,
  and no static initializer can read a variable of another C++ file before `gp_var_init()` has
  run (C++'s "static initialization order fiasco" can't happen). A variable with a constant
  value gets it at compile time (a string through `gp::static_bytes`), and so does an array or
  a struct literal whose values are number and bool constants or nested literals of the same
  kind, in a type made of numbers (also complex ones) and bools only (`point{1, 2}`, `point{y:
  2}`, `[3]point{1: {x: 4}}`; not strings, pointers, slices or maps, which are not literal types
  in C++); `var x T` is its zero value, `T x{};`. The others are zero at first and assigned in `gp_var_init()`.
  A variable larger than 128 KiB lives in static storage, never on the stack, and is never
  constinit with a literal (clang++ can't build a keyed literal of more than 1 << 20 elements at
  compile time); when a literal initializes it, also inside a conversion between types with the
  same underlying type, `gp_var_init()` stores the literal's elements and fields into the
  variable one by one (the variable is still zero then, and Go's initialization-cycle rule means
  nothing in the initializer can read it), so the value is never a temporary on the C++ stack. Any other
  initializer of such a variable (a call's result) is one ([D24](language.md#d24-large-values-on-the-c-stack)).
  A variable whose type holds a C or C++ class by value (`std.vector[int]`, `std.mutex`, a C struct, a
  struct of ours with such a field) is `gp::lazy<T>` storage, because the class's constructor may not be
  constexpr ([ADR-093](../adr/093-package-variables-of-c-classes-are-lazy-storage.md)):
  `gp::lazy<T> gp_lazy_x;` (no object yet), `constinit T& x = gp_lazy_x.gp_ref();` (the variable's own
  name, a constant reference), `static const gp::lazy_boot gp_boot_x{gp_lazy_x};` and, first in
  `gp_var_init()`, `gp_lazy_x.gp_ensure();`. The object is built (`T{}`) by whichever comes first, so a
  library's early `gp_var_init()` is not wiped by the dynamic initializer, and never destroyed.
- `gp::run_main(argc, argv, init, main)` stores the arguments (for `os.Args`), runs the init
  function, runs `main`, and exits with code 0. An unrecovered panic prints `panic: <message>`,
  `goroutine 1 [running]:` and a stack trace, and exits with code 2, as in Go (see
  [Runtime checks and panics](#runtime-checks-and-panics)).
- In the `c-archive` and `c-shared` build modes, initialization runs at the first exported call
  instead, as in Go.

## Runtime checks and panics

- The runtime checks what Go checks, with Go's messages and exit code 2: an index of a string,
  a slice or an array (`runtime error: index out of range [5] with length 3`), a slice
  expression of every form (`slice bounds out of range [:5] with capacity 3`), a slice to array
  conversion, a nil pointer dereference (`*p`, `p.f`, a value method through a nil pointer, a
  call of a nil func value), `(*T).M` of a value method with a nil pointer (`value method
  main.T.M called using nil *T pointer`), division and modulo by zero of every integer type,
  a negative shift count of a signed type, `make` with a bad length or capacity
  (`makeslice: len out of range`, also when the element is too big for the length), a store
  into a nil map (`assignment to entry in nil map`), and an `append` whose length overflows
  (`growslice: len out of range`, which a slice of 1-byte empty structs (D15) can't reach: its
  `make` fails first). Reading a nil map, `delete` and `clear` of one, and `make` of a map
  with a negative hint don't panic, as in Go; nor does the conversion of an out-of-range float
  to an integer, which gives the values of Go on amd64 (`gp::f2i`). TestPanics
  (internal/cppgen) runs each check and compares stderr and the exit code with real Go.
- Go's fatal errors, which no `recover` stops and which run no deferred calls, end the program
  the same way, with exit code 2:
  - **out of memory**: the runtime installs a new handler (`std::set_new_handler`), so an
    allocation that fails anywhere (a slice, `new`, a large local variable in its box, a map,
    a string) prints `fatal error: runtime: out of memory`, a blank line, `goroutine 1
    [running]:` and the trace, where it fails, instead of throwing `std::bad_alloc`. That also
    applies to C++ code that the program calls (Phase 04): like Go, a program can't recover
    from running out of memory, even where a C++ library would catch `std::bad_alloc`. With
    `-asan`, AddressSanitizer's allocator reports a failed allocation itself;
  - **stack overflow** (Linux): a goroutine runs on a fixed C++ stack (8 MiB by default; the
    main thread's is `ulimit -s`, 8 MiB by default too), where Go's stack grows up to 1 GB, so a
    recursion stops much earlier than in Go. Each goroutine's stack has a guard of 256 KiB below
    it (a frame is probed page by page, because `-fstack-clash-protection` is one of the compile
    flags, so it cannot skip over the guard), and every thread that the runtime started (and the main thread) has a SIGSEGV handler on
    an alternate signal stack (`sigaltstack`) that tells an overflow of its own stack from other
    faults and prints Go's lines, `runtime: goroutine stack exceeds 1000000000-byte limit`,
    `runtime: sp=0x… stack=[0x…, 0x…]` (the thread's stack) and `fatal error: stack overflow`,
    exit code 2. When several goroutines overflow at once, one reports. Other faults keep the
    action they had (a crash, exit code 139), and so does an overflow of a thread that the runtime
    didn't start (a C library's thread, a `std::thread`). Not with a sanitizer (it reports
    overflows itself: AddressSanitizer prints `stack-overflow`, exit code 1), not with `ulimit -s
    unlimited` for the main thread. Windows (step 14.1, ADR-053) reports the same three lines from a
    vectored exception handler, and also turns the other CPU faults (a nil or wild pointer in C
    code, an integer division by zero in C code, an illegal instruction) into Go's report
    (`panic: runtime error: invalid memory address or nil pointer dereference`, `[signal 0xc0000005
    code=0x0 addr=0x0 pc=0x...]`, exit code 2), where Linux leaves the crash.
- **Panic values** (step 5.10): a panic is a `gp::panic_error` that holds the value as a `gp::any`
  (`recover()` returns it): `panic("boom")` an `any` of Go type `string`, `panic(1.5)` a
  `float64`, `panic(err)` and `panic(x)` for an interface value the value itself (a value of
  another type is converted to an `any`, step 5.4), `panic(nil)` a `*runtime.PanicNilError`
  (Go 1.21: `panic called with nil argument`). The runtime's own panics are `runtime.Error`
  values with Go's types and texts, so `r.(error)` and `r.(runtime.Error)` hold and `%T` prints
  Go's name: `runtime.boundsError` (index and slice bounds, `cannot convert slice with length
  3 to array ...`), `runtime.errorString` (division by zero, nil dereference, negative shift,
  `makeslice: len out of range`, `unsafe.Slice: len out of range`, comparing and hashing
  uncomparable types), `runtime.plainError` (a store into a nil map, `value method main.T.M
  called using nil *T pointer`: no `runtime error: ` prefix) and `*runtime.TypeAssertionError`
  (a failed type assertion). All of them have `Error() string` and `RuntimeError()` methods, in
  descriptors made like a generated type's (runtime/src/panicval.cpp). A C++ exception that a
  function with defers catches is a `runtime.CppException` ([interop.md](interop.md#c-exceptions)).
  The text that an unrecovered panic prints is made as Go's `preprintpanics` and `printpanicval`
  make it: `Error()` of an error, else `String()` of a `fmt.Stringer`, else the value as
  `print` writes it (a named type with its name: `main.MyInt(5)`, `main.MyS("hi")`), else the
  type and an address (`(main.T) 0xc000012120`: the harness masks it). Two panics in a chain
  whose values are the same interface value (the same type and data) print once as
  `[recovered, repanicked]`, and a recovered one that is still in the chain as `[recovered]`.
  `runtime.Goexit` (`gp::goexit`) runs the deferred calls and ends the goroutine, `recover()`
  returns nil in them; from the main goroutine the program goes on until the other goroutines are
  gone, then `fatal error: no goroutines (main called runtime.Goexit) - deadlock!`.
- A panic is a C++ exception, `gp::panic_error`. Unrecovered, it prints Go's lines and then a
  stack trace: each function by its Go name, `(...)` when it has parameters, then a tab, the
  `.gp` file and line of the call (from the debug info that `#line` makes) and the offset in the
  function, like Go's trace. The runtime's own frames are left out.

  ```
  panic: runtime error: index out of range [5] with length 3

  goroutine 1 [running]:
  main.at(...)
  	/home/me/prog/main.gp:14 +0x19
  main.main()
  	/home/me/prog/main.gp:23 +0x34
  ```

  Like Go 1.25, a stack of more than 100 frames shows the inner 50, `...N frames elided...` and
  the outer 50, ending with `main.main()`.

  The panic records the return addresses where it starts, up to the function with deferred calls
  that will catch it (the rest of the stack when that function knows that the panic is not
  recovered; see "Defer"), or the whole stack with `backtrace()` when there is no such function: a
  panic costs 1–5 µs more than a plain C++ throw on a stack of up to about 25 frames then, and about 5 µs
  more when the first 100 addresses fill up. Only then a second walk records the whole stack,
  for the outer frames and the count, so its cost grows with the depth, and only deep stacks
  pay for it. The names and lines are looked up only when the program ends, from the
  program's symbol table and DWARF line table (about 2 ms). The names come back from the C++
  names: `gpkg_main::f` is `main.f`, a lambda is `main.f.func1`, `gp_init_1` is `main.init.0`.
- `gocpp build -nochecks` (and `gocpp run -nochecks`) turns off the bounds and nil checks: an
  index, a slice expression or a conversion out of range, a nil dereference, a call of a nil
  func value, a method call (or a method value) of a nil interface value and `(*T).M` with a nil pointer (the check of Go's wrapper, `runtime.panicwrap`,
  is a nil check too) are then undefined behavior, as in C++. It defines
  `GOCPP_NOCHECKS` for every compile, the runtime's too (whose object files are cached apart).
  The emitter writes no check of its own: every check is in a runtime function that
  `GOCPP_NOCHECKS` empties (`gp::check_wrap` for `(*T).M`), so the generated C++ is the same
  with and without the flag (TestNoChecksCalls checks that a `-nochecks` build of a third of the run tests (`GOCPP_TEST_ALL_NOCHECKS=1`: all of them),
  of a program that prints composite values with fmt, and of the runtime's own files calls none
  of these panics). Code that relies on catching such a panic is undefined behavior too, even
  when the program would end normally with the checks: `fmt` prints `<nil>` for a nil pointer
  whose `String` or `Error` method panics on it (`fmt.Println(nc)` with a nil `*Counter` whose
  `String` reads `c.n`), which needs the nil check, and so does a `recover` of such a panic
  (Phase 05). So only a program that never takes one of these panics behaves the same. Division by zero and a negative shift count still panic, and
  Go's results for `MIN / -1` and for a shift by the width or more stay, because without them
  C++ has undefined behavior and they cost little. The panics that are part of an operation
  stay too: a write to a nil map, `make` with a bad length or capacity, `append`'s overflow, and
  an index of a `[0]T` (which has no element to give), and so do the fatal errors.

A method prints as Go prints it: a value method (a const member function) as `main.T.M`, a
pointer method (a static one, whose mangled name has no qualifier) as `main.(*T).M`.

Where the trace differs from Go's (accepted divergences):
- `(*T).M` of a value method called with a nil pointer: Go's trace has a frame
  `main.(*T).M(...)` at `<autogenerated>:1` (its wrapper, which panics); gocpp's has none, and
  its panic value is a `runtime.Error` like Go's (`runtime.plainError`: step 5.10);
- the parentheses always hold `(...)` (the function has parameters) or `()`, where Go prints
  the argument words (`main.f(0x0?)`), or `(...)` for an inlined frame; and every frame has
  its offset, where Go prints none for an inlined frame;
- a Go name that gocpp escaped for a C++ keyword or macro keeps its `_` (`main.new_`);
- func literals have Go's names (`main.f.func1`), but Go's inliner copies a closure into the
  function it inlines it in and names the copy after that one (`main.main.main.func1.func3`);
  gocpp's names are those of a Go program built with `-gcflags=-l`;
- an optimized build (Phase 15) can show the line of an inlined runtime header as the
  innermost frame's line; gocpp builds at `-O0`;
- a stripped program shows the addresses instead (`?()` and `pc=0x...`, for `addr2line`);
- on Windows the trace reads the program's PE file (COFF symbols and the DWARF that MinGW writes
  into it): names and lines as on Linux; a program linked without `-g` shows names only, and a
  stripped one addresses.
- a panic that starts in a deferred call while another panic runs has a `panic(...)` frame
  with `?:0` for its place, where Go shows its runtime's `panic({0x...?, 0x...?})` and the line
  of `runtime/panic.go`;
- a deferred builtin call (`defer panic(v)`, `defer println(x)`) has no frame of its own; Go
  shows a wrapper there, `main.f.deferwrap1()`, at the line of the defer statement;
- a call in a statement over several lines shows the statement's first line, where Go shows the
  line of the call: `fmt.Println(1,` / `2,` / `get())`, and a call after a multi-line func
  literal in the same statement (`f(apply(func() {...}, 3), apply(func() {...}, 4))`);
- a fatal error's report is shorter than Go's. Out of memory: Go prints a `runtime stack:`
  section with its runtime's frames before the goroutine, a goroutine line with `gp=`, `m=` and
  `mp=`, frames with `fp=`, `sp=` and `pc=` and its own frames (`runtime.mallocgc`,
  `runtime.makeslice`); gocpp prints `goroutine 1 [running]:` and the program's frames, as for a
  panic. Go's message also depends on where its heap fails: a request too big for the address
  space (about 2^46 bytes or more) prints `runtime: out of memory: cannot allocate N-byte block
  (M in use)` and `fatal error: out of memory`, where gocpp always prints `fatal error:
  runtime: out of memory`, without the size. When the trace needs memory that isn't there, the
  report ends after the goroutine line (or after the `fatal error` line). A `std::bad_alloc`
  that C++ code throws itself (or `std::bad_array_new_length`, `new int[-1]`) gives the same
  report, with the trace where it was thrown (Phase 04, step 4.12: nothing unwinds before).
  Go also prints its runtime's other goroutines after goroutine 1 (the garbage collector's, the finalizer's, with `created by`
  lines); gocpp has none. A fatal error in a deferred call that a panic runs shows Go's shape:
  the deferred call's frames, `panic(...)` and the panicking function at the panic's line.
  Stack overflow: the numbers of the `sp=`
  line are the C++ stack's, and the report ends after `goroutine N [running]:`, without a trace
  and without Go's `runtime stack:` section (a signal handler can't safely walk the stack and
  read the program's file); Go prints its trace. When several goroutines fail at once, one
  reports and the others wait up to 30 seconds for the process to end;
- C or C++ output still in a `stdio` buffer is lost on a stack overflow (the handler can't
  flush it); gocpp's own output is never buffered.

Source: [Phase 03 §2.9](../../plans/2026-10-13-gocpp/phase-03-core-language/README.md#29-runtime-checks-and-panics-gos-exact-messages).

## Interfaces

Go's interfaces are satisfied by having the methods; gocpp copies Go's runtime for them: a **type
descriptor** for every type that goes into an interface, and an **itab** (a table of function
pointers) for every (interface, type) pair, found by the methods' names and signatures
([Phase 05 §2](../../plans/2026-10-13-gocpp/phase-05-interfaces-errors/README.md), ADR-016). This
section has the runtime's side, steps 5.1 to 5.3 (`gocpp/type.hpp`, `gocpp/iface.hpp`,
`runtime/src/type.cpp`), the emitter's shapes for interface types, descriptors, method tables and
thunks, and the conversions (step 5.4: `internal/lower/ifaces.go`, `typedesc.go`, `canon.go`,
`iconv.go`; the runtime's `gocpp/ifaceconv.hpp` and `gocpp/error.hpp`), the type assertions and
the type switches (step 5.5). `==` and hashing of interface values (step 5.6) and method values
(step 5.9) are below, `fmt` on interfaces comes from 5.11, and
[embedding](#promoted-methods-in-the-method-tables) (5.8: promoted methods in the tables) is below.

```go
type Shape interface{ Area() float64; Scale(k float64) }
type Rect struct{ W, H float64 }
func (r Rect) Area() float64      { return r.W * r.H }
func (r *Rect) Scale(k float64)   { r.W *= k; r.H *= k }

var s Shape = &Rect{2, 3}
fmt.Println(s.Area())
```

```cpp
// the interface: one struct, no data members (32 bytes), the wrappers defined after all types
struct Shape : gp::iface {
    using gp::iface::iface;
    static const gp::type_desc* gp_desc();   // its descriptor, defined after the descriptors
    double Area() const;
    void Scale(double k) const;
};
inline double Shape::Area() const { return gp::icall<double()>(*this, 0); }          // slot 0
inline void Shape::Scale(double k) const { gp::icall<void(double)>(*this, 1, k); }   // slot 1
inline const gp::type_desc* Shape::gp_desc() { return &gp_td_Shape; }

// one thunk per method of each named type: R(const gp::iface& self, Args...)
inline double gp_thunk_Rect_Area(const gp::iface& self) { return gp::unbox<Rect>(self).Area(); }
inline double gp_thunk_pRect_Area(const gp::iface& self) {   // the same method through a *Rect
    gp::bptr<Rect> p = gp::unbox_borrow<Rect>(self);   // the interface value holds the object: no copy
    gp::check_wrap(p, "value method main.Rect.Area called using nil *Rect pointer");
    return p->Area();
}
inline void gp_thunk_pRect_Scale(const gp::iface& self, double k) {
    Rect::Scale(gp::unbox_borrow<Rect>(self), k);       // Scale borrows its receiver (ADR-086)
}

// the method tables, sorted (exported names by name, then unexported ones by name and package)
inline const gp::method gp_vm_Rect[] = {   // the method set of Rect: the value methods
    gp::method_of<double()>("Area", nullptr, "func() float64", &gp_thunk_Rect_Area)};
inline const gp::method gp_pm_Rect[] = {   // the method set of *Rect: all of them
    gp::method_of<double()>("Area", nullptr, "func() float64", &gp_thunk_pRect_Area),
    gp::method_of<void(double)>("Scale", nullptr, "func(float64)", &gp_thunk_pRect_Scale)};
inline const gp::imethod gp_im_Shape[] = {
    gp::imethod("Area", nullptr, "func() float64"), gp::imethod("Scale", nullptr, "func(float64)")};

// the descriptors (header section 8)
inline const gp::type_desc gp_td_Rect = gp::named<Rect>(
    "main.Rect", "main", gp::shape_struct(gp_fields_Rect),
    gp::methods_of(gp_vm_Rect), gp::methods_of(gp_pm_Rect));
inline const gp::type_desc gp_td_Shape = gp::named<Shape>(
    "main.Shape", "main", gp::shape_interface(gp_im_Shape));

// var s Shape = &Rect{2, 3}   (the descriptor of *Rect is interned: keep it in a static)
static const gp::type_desc* const gp_td_pRect = gp::td_ptr<Rect>(&gp_td_Rect);
Shape s = gp::to_iface<Shape>(gp::new_<Rect>(Rect{2, 3}), gp_td_pRect);
static_assert(gp::thunk_matches<double(), decltype(&gp_thunk_pRect_Area)>, "...");   // per method
```

### What the emitter writes (steps 5.4 and 5.5)

```go
type Shape interface{ Area() float64 }
type Rect struct{ W, H float64 }
func (r Rect) Area() float64 { return r.W * r.H }

var s Shape = Rect{2, 3}             // a conversion: where Go assigns, passes or stores the value
a := any(1)                          // an int: the constant has the exact type of its default
n, ok := a.(int)                     // an assertion; v := a.(int) panics with Go's message
switch v := s.(type) { case Rect: _ = v.W; case nil: }
```

```cpp
struct Shape : gp::iface { using gp::iface::iface; static const gp::type_desc* gp_desc(); double Area() const; };
Shape s = gp::to_iface<Shape>(Rect{2, 3}, &gp_td_Rect);
gp::any a = gp::to_iface<gp::any>(int64_t(1), &gp::td_int);
auto gp_t0 = gp::assert_type2<int64_t>(a, &gp::td_int); int64_t n = std::get<0>(std::move(gp_t0)); ...
const Shape& gp_x0 = s;                                     // a switch: the tests in order
if (gp::type_is(gp_x0, &gp_td_Rect)) { Rect v = gp::unbox<Rect>(gp_x0); ... } else if (gp_x0 == nullptr) { ... }
```

- **Interface types.** Each interface type is a struct over `gp::iface` with no data members of
  its own (32 bytes, a `static_assert`): `Shape` for a named one, `gp_anon_i` and 16 hex digits of
  the SHA-256 of its identity text for an unnamed one with methods (identical types are one struct),
  `gp::any` for `any` and `interface{}`, `gp::error` (the runtime's, `gocpp/error.hpp`) for `error`.
  The structs are defined before the structs of the package (they hold no data, so a struct may
  hold one by value); the wrappers (`double Shape::Area() const { return gp::icall<...>(*this, 0); }`)
  after all the types, so that `Shape` may return a struct that holds a `Shape`. The slot of a method
  is its position in the interface's methods sorted as the runtime's tables are (exported names by name,
  then unexported ones by name and package). An interface that embeds others has all their methods.
- **Descriptors.** A named type that is not an interface has `gp_td_T` (`gp::named<T>(...)`) with its
  two method tables and the thunks (above); a named interface has `gp_td_I` and `gp_im_I`; every
  other type is a namespace-level `static const gp::type_desc* const gp_tdc_N` (`gp_tdp_T` for `*T`),
  made at program start from the descriptors of its parts and interned by the runtime. (In the split
  layout the descriptors are `extern` in `pkg.hpp` and defined in `pkg_desc.cpp`, and the
  composite ones are plain `const` pointers there; a package that converts a type of another package
  to an interface asks that package to define the descriptor and writes `&::gpkg_geom::gp_td_Point`,
  so the type has one descriptor in the program. The unit layout shows the `inline` and `static`
  forms of this section.) The
  registry grows while the functions are lowered and the section is written last, in dependency
  order, so only the types that flow into an interface have descriptors. **Shapes.** A named type's
  descriptor object is constant-initialized (usable before any dynamic initialization, and
  `td_ptr<T>(&gp_td_T)` may be written anywhere): its shape has the kind of the underlying type and,
  where the element's descriptor is a constant (a predeclared or a named type), the element; any other
  part, and the field list of a struct, is null. `%T`, `==`, assertions and itabs need nothing more;
  step 5.11's `fmt` and Phase 09's `reflect` take the rest from the C++ types.
- **Names and signature texts.** `internal/lower/canon.go` writes both: the name of a type as `%T`
  prints it (package names: `main.Rect`, `url.Values`) and the identity text of a method's signature
  (full import paths, `byte` as `uint8`, `any` as `interface {}`, no parameter names, aliases
  unaliased, a function-local type made unique, an interface type's methods flattened and sorted,
  `chan (<-chan int)`). The main package's path is `main` (what `reflect` says, whatever `go run`
  calls the package). `canon_test.go` compares the names of about 100 types with `%T` of a real Go
  program and the texts with `types.Identical` (`go/types`).
- **Conversions.** Go converts a value to an interface where it assigns it (an assignment, a
  declaration, a return, an argument, an element of a composite literal, a map key or value, an
  appended value, a case value, a comparison with an interface, a range variable): `noteConversions`
  finds those places and the value is converted where it is written. A concrete value is
  `gp::to_iface<I>(value, descriptor)` (a constant has the exact C++ type of its Go type, so
  `any(1)` holds an `int64_t` with `&gp::td_int`); an interface value of another type is
  `gp::iface_cast<I>(x)` (the itab is found in a cache of the template instance, then in the global
  cache; nil stays nil; a target without methods needs none); the nil of an interface type is `I()`;
  `x == nil` is `x == nullptr`. A struct, an array, a slice, a map or a func is copied into the box,
  a pointer shares its owner (a nil pointer is a typed nil: not a nil interface).
  The arguments of fmt's functions and of `print`, `println` and `panic` are not converted (their
  own paths: `noConvArgs`); printing an interface value with fmt is step 5.11's.
- **Calls.** `s.Area()` is the wrapper `s.Area()`. The call holds no copy of the interface (`gp::icall_keep`
  is for C++ code that needs one): the thunk reads the box once, at its entry (a value method copies its
  receiver as its first statement, or is read-only; a pointer method gets an owning `gp::ptr`), and Go's order
  of evaluation (a receiver is read after the calls of its call) is `order.go`'s, as for any other receiver.
- **Assertions.** `x.(T)` of a concrete `T` is `gp::assert_type<T>(x, descriptor)` (a `const T&` into
  the box; a pointer type gives the `gp::ptr`); `v, ok := x.(T)` is `gp::assert_type2<T>`, a
  `std::tuple<T, bool>` that the declaration moves out of (the zero value when it fails); an interface
  type `T` is `gp::assert_iface<I>(x)` and `gp::assert_iface2<I>(x)`. A failed one panics with the text
  of Go's `*runtime.TypeAssertionError`, exactly:
  `interface conversion: interface {} is string, not int`, `... main.J is nil, not main.T` (the static
  type of the operand), `... main.T is not main.I: missing method M`, `... interface is nil, not main.I`,
  and `(types from different packages)` or `(types from different scopes)` for two types that print
  alike. The panic value is a `*runtime.TypeAssertionError` (`detail::throw_type_assertion`), so `recover()` gives it and `r.(error).Error()` is that text.
- **Type switches.** The operand is read once (a const reference to an unboxed local, else a copy);
  the cases are tested in source order, `default` last wherever it is, each case's types in order:
  `gp::type_is(x, desc)` for a concrete type, `gp::type_has<I>(x)` for an interface type, `x == nullptr`
  for `nil`. `v` has the type of the case when it lists one type and the operand's interface type
  otherwise, is declared only in the clauses that use it, and may be boxed. A `break` in a clause turns
  the chain into a C++ `switch` on the number of the matching clause, as for the other switches.
- **Interface values in `==` and in maps.** `x == y` of two interface values (`iface`'s `operator==`):
  equal when both are nil, or the dynamic types are the same and the values equal; two values of an
  uncomparable type panic with `runtime error: comparing uncomparable type []int`; a map key or a
  struct field that holds an interface hashes by its dynamic value (`gp_hash`, panic `runtime error:
  hash of unhashable type []int`). A struct with an interface field has the generated `==` and
  `gp_hash` as any comparable struct.
- **Unhashable keys (step 5.6).** Go checks the key of a read or a delete in a nil or empty map without
  hashing it (`runtime.mapKeyError`) and panics `hash of unhashable type: []int` (no `runtime error: `), also
  when the key is a struct or an array that holds the interface and when the interface holds a struct, an
  array or a boxed value that holds one; every other use panics `runtime error: hash of unhashable type
  []int`. A key type that can panic has `static constexpr bool gp_hash_panics = true` (`gp::iface`, the structs
  the emitter writes with an interface in a non-blank field or an array of such, `gp::array<T, N>` for such a
  `T`; a `gp::newtype` inherits it; `internal/lower/ifaces.go: hashMayPanic`), and the map's read and delete of
  a nil or empty map call `gp::check_key(k)` (gocpp/hash.hpp): the key is hashed with the thread-local
  `detail::key_checking` set, which gives `iface::gp_hash` the first text. A key type that can't panic is never
  checked. NaN keys are never found (each insertion adds an entry; `clear` and range reach them) and +0/-0 are
  one key whose stored key is the latest inserted. Keys of different dynamic types are different keys whatever
  their values (`1`, `int64(1)`, `float64(1)`: one hash, told apart by `==`).
- **Method values and expressions of interface methods (step 5.9).** `f := i.M` is the lambda of a method
  value with the receiver captured as `gp::method_recv(i)`: a copy of the interface value (a later `i = ...`
  does not change `f`; a pointer in it shares its object) and a nil interface panics where the value is made,
  with Go's nil dereference. The same for a method promoted through an embedded interface field
  (`gp::method_recv(h.Shape)`) and as a deferred call's callee. The func value is `gp::aware`, so a deferred
  call of it gives the dynamic method its recover ticket (5.10). A method expression `I.M` is the lambda
  `[](auto&& gp_r, auto&&... gp_a) { return gp_r.M(gp_a...); }`: a nil interface panics when it is called.
- **C and C++ values.** A C/C++ value goes into an interface that has no methods (`any`) with
  `gp::to_iface_foreign<gp::any>(v)`: its descriptor is `gp::foreign_td<T>()` of its C++ type, so
  `std.string` and `C.int` are different dynamic types of their own, and `x.(std.string)`, `x.(C.int)`
  and the type switch cases of C/C++ types compare with the foreign descriptor of the C++ type. The
  comma-ok forms `v, ok := x.(C.int)` and `var v, ok = x.(C.int)` work too (not an assignment to variables
  that exist: declare new ones, as for any C/C++ value with two results).
- **C and C++ values, more.** A raw pointer (`&cvar`, a C function's result) is held as the `gp::cptr<T>`
  that a Go variable of type `*C.T` is, so `x.(*C.T)` finds it however it was made (a pointer to a local C
  variable owns nothing and is valid while the variable is). Const and nesting are normalised on both sides
  (`detail::foreign_norm_t`): a `const char*` is the dynamic type `*C.char`, a `const T* const*` and a `T**` are
  `**T` (held as the raw pointer, as the Go type `**T` is in C++), and `x.(*C.char)`, `x.(**T)` and the type
  switch cases ask for those. This holds for pointers that C made (a result, an out-parameter, `&cvar`
  of a C variable); `&p` of a gocpp variable `p` of type `*C.T` is a gocpp pointer to a `gp::cptr` and does
  not match `x.(**T)` (known limit). The normalisation covers `T*` and `gp::cptr<T>` at any depth, not the
  const of a container's element (`gp::array<const char*, N>` keeps its spelling in the descriptor name).
  Only an interface without methods holds a
  C/C++ value (a compile error otherwise); an interface method with a C/C++ type in its signature is a compile
  error; a Go type's method with one is left out of its tables. A Go struct with a C/C++ field is an
  ordinary named type for interfaces (its descriptor is partial), so a Go wrapper of a C handle implements
  interfaces; a value of it is not comparable through an interface (its `==` panics), a pointer to it is. A
  C++ type with `==` and no `std::hash` has one hash for all values.
- **Known differences from gc.** The order of a conversion inside a nested expression (`any(g).(P).a + mod()`
  is 107 here and 8 in gc; `[]int{any(g).(P).a, mod()}` is `[100 7]` here and `[1 7]` in gc: only an
  argument or an operand of a statement's list is copied in its place); a value method called through a nil
  `*T` in an interface always panics with Go's wrapper message, where gc devirtualizes a call it can see
  through and prints a plain nil dereference. A read or delete in a nil or empty map with an unhashable
  interface key panics "hash of unhashable type: []int", the text of Go's, and any other use "runtime error:
  hash of unhashable type []int", as Go. The trace of a panic leaves out the wrapper methods of interface
  structs (they carry `[[gnu::abi_tag("gp_wrap")]]`, which the trace recognizes in the mangled name), as Go has no
  frame for them.
- **Not yet.** A channel type comes with Phase 08; a type in a method signature with a C/C++
  part ("interface methods with C/C++ types") is reported as not supported.

**Descriptors are chosen by the Go type.** One `gp::type_desc` object per Go type, so a pointer
comparison is a type comparison: `gp::td_int` and `gp::td_int64` are different objects although both
types are `int64_t` in C++ (also `uint`, `uint64` and `uintptr`, and the three directions of
a channel), so `any(1).(int64)` fails and `%T` prints the right name.

| Go type | Descriptor |
|---|---|
| predeclared (`int`, `int8` … `uintptr`, `float32`, `complex128`, `string`, `bool`, `unsafe.Pointer`) | `gp::td_int` … `gp::td_uintptr`, `gp::td_string`, …: one `constexpr` object each in the runtime. `byte` is `td_uint8`, `rune` is `td_int32`; `interface{}` is `gp::td_any` |
| a named type (`type Rect struct{…}`, `type Celsius float64`, `type Shape interface{…}`) | an object in the package header: `gp::named<T>(name, package path, shape, value methods, pointer methods)`, where `shape` is `gp::shape_struct(fields)`, `shape_basic(kind)`, `shape_slice(elem)`, `shape_array(n, elem)`, `shape_map(k, v)`, `shape_chan(dir, elem)`, `shape_func(...)`, `shape_pointer(elem)` or `shape_interface(methods)` |
| `[]T`, `[N]T`, `map[K]V`, `*T`, `chan T` (and `<-chan T`, `chan<- T`), `func(...)`, `struct{...}`, `interface{...}` | built from the descriptors of the parts and **interned** (one per Go type, from any thread, no lock to read): `gp::td_slice<E>(elem)`, `td_array<E, N>(elem)`, `td_map<K, V>(key, elem)`, `td_ptr<T>(elem)`, `td_chan<C>(dir, elem)`, `td_func<F>({params}, {results}, variadic)`, `td_struct<S>({fields})`, `td_interface({methods})`. The template argument is the C++ type (its size and `==` come from it); the arguments are Go descriptors. The name is Go's: `[]int`, `<-chan int`, `chan (<-chan int)`, `func(int, ...string) (bool, error)`, `struct { X int "json:\"x\""; y string }`, `interface { N(); pkn.m() }` |
| a C or C++ value in an interface (`std::string`, a C `int`, a raw pointer) | `gp::foreign_td<T>()`: made from a template, named after the C++ spelling, `==` and the hash from `operator==` and `std::hash` when `T` has them; a raw pointer compares and hashes by address |
| a C type in a method signature, which `go/types` sees as `invalid` | its spelling in the signature text, or `gp::td_opaque("C.int")` in a `td_func` |

A named type has two method tables: the **value methods** (the method set of `T`) and **all
methods** (the method set of `*T`, which `td_ptr` puts on the interned `*T`). A method has its Go
name, the **import path of its package when the name is not exported** (an unexported `m` of
package `a` is another method than the `m` of package `b`, so another package's unexported method
never satisfies an interface), its signature as text and its thunk. The signature text is the
identity of the method's type, so it must be **canonical**: the same text for every spelling of an
identical signature (`types.Identical`), in the interface and in the type that has the method.
The emitter's **contract**: aliases unaliased, recursively; parameter and result names dropped;
`byte` as `uint8` and `rune` as `int32`; `any` as `interface {}`; every package as its full import
path (`func(net/url.Values, ...string) (int, error)`, a single space after each comma);
function-local types made unique (two types named `L` in two functions are two types); the type
arguments of an instantiated generic type spelled canonically too; a C type as it is spelled in the
source (`func() C.int`). `types.TypeString` does **not** do this (it keeps parameter names, `byte`,
`any` and alias names, and prints two local types alike), so a signature that differs only in such
a spelling would be a *missing method* at run time, or a false match. A Go-side canonicaliser with
a test for each rule is part of step 5.4; the runtime only compares the texts. With the text,
`Get() C.double` can't satisfy `Get() C.int`, which `go/types` alone would allow.

**Interface values.** `gp::iface` is `{ std::shared_ptr<void> data; const gp::type_desc* type;
const gp::itab* tab; }`, 32 bytes. `type` is the dynamic type's descriptor and is null exactly for
`nil`; `x == nil` is `x == nullptr`. `tab` is the itab (null for an empty interface). `gp::any` is
`interface{}`.

| Go | Interface value |
|---|---|
| `var x Shape` (nil) | `Shape()` or `Shape(nullptr)`: `data`, `type` and `tab` null |
| `*T` (also `&x.f`, `&a[i]`, `&global`) | `data` shares the pointer's owner and address: no copy of the object, and the object lives as long as the interface |
| a nil `*T` | `data` null, `type` the descriptor of `*T`: **not** nil (Go's famous gotcha) |
| any other value (numbers, strings, structs, arrays, slices, maps, funcs, C/C++ values) | `data` owns a new box with a copy of the value, as in Go |

Copies of an interface share the box (boxes are never written); a move leaves `nil`; the owner is
released through `gp::detail::release`, so a long list that goes through `any` fields is freed
without deep recursion. `gp::to_iface<I>(value, descriptor)` boxes a value; `gp::unbox<T>(x)` reads
it back (a `const T&` into the box, a copy for a temporary, a `gp::ptr` that shares the owner): the
type check comes first (step 5.5). A call of a method of a nil interface panics with `invalid memory
address or nil pointer dereference`. `gp::icall<R(A...)>(self, slot, args...)` calls the thunk in
`slot` of the itab, whose C++ type is `R(const gp::iface&, A...)`; `gp::icall_keep` holds a copy of
the interface for the call, for an interface that the method itself could change (a field, a global),
as `gp_call` does for func values.

**Itabs.** `gp::getitab(inter, type)` is the itab of the pair: for each method of the interface, in
order, the thunk of the type's method with the same name, package and signature text; null when the
type lacks one (`gp::missing_method` says which: Go's `missing method M`, step 5.5). Results, also
the misses, are cached in a global table that is read without a lock (an append-only open-addressed
table written under a mutex, like Go's `itabTable`); a static conversion (`to_iface`) also keeps its
itab in a function-local static, checked against the descriptor, so two Go types over one C++ type
(`type A int64`, `type B int64`) never share one. An itab is built once however many threads ask. The
method tables must be sorted (exported names by name, then unexported ones by name and package):
`getitab` ends the program with a fatal error otherwise (`gp::methods_sorted` checks one).

**Contracts of the runtime API.**
- Nil of an interface type is `Shape()`. The `std::nullptr_t` constructor is explicit, so
  `Shape s = nullptr;`, `return nullptr;`, `x = nullptr;` (`err = nil`), an argument `f(nullptr)`,
  a braced element `{nullptr, x}`, `result.set(nullptr)` and `gp::any z = 0;` don't compile. The
  emitter must write `T()` for every nil of an interface type (`Shape()`, `Shape(nullptr)`,
  `Shape{nullptr}` and `return {};` compile too); `x == nullptr`, `nullptr == x`, `x != nullptr` and
  `nullptr != x` compile.
- `td_interface(methods, name)`: the emitter must always pass the name, at every site, and it is
  the text Go's `%T` prints, not go/types': the same canonical form as the signature texts (method
  set flattened and sorted, aliases unaliased, `[]uint8`, `interface {}`, no parameter names,
  package *names* in qualified types, Go's spacing): `interface { Close() error; Read([]uint8)
  (int, error) }` for both `interface{ io.Reader; Close() error }` and `interface{ Close() error;
  Read(p []byte) (int, error) }`. The first call creates the descriptor, and a later call with
  another name is a fatal error (also a first call without a name followed by one with a name,
  whenever the name composed from the signature texts differs from the real one), so `%T` never
  depends on which site runs first. The Go-side canonicaliser of step 5.4 produces both this name
  and the signature texts, and is tested against `%T` of a real Go program.
- The `gp_equal` and `gp_hash` hooks of a descriptor take what `x.gp_data().get()` is for an interface
  `x` that holds the value: the box, an object of the C++ type; but for a `gp::ptr` (`*T`,
  `unsafe.Pointer`) the **target address**, because the interface shares the pointer's owner and
  has no `gp::ptr` object. Slices, maps and funcs have no hook (Go: `comparing uncomparable
  type`, step 5.6); interface-kind descriptors have a hook too (`gp_hash_panics`, `gp::check_key`).
- One runtime per process: interfaces and descriptors never cross a shared-library boundary. A
  library built with `-fvisibility=hidden` has its own copy of the runtime, so its descriptors and
  itabs are other objects than the program's (probed: the descriptor of the same named type, of
  `[]int`, of `int` and the itab are all different pointers, so `x.(T)` would fail across the
  boundary). Phase 06's `c-shared` mode keeps Go values out of its C interface.

**What the compilers check.** `gp::method_of<Sig>(...)` has a `static_assert` that the thunk's type is
`R(const gp::iface&, A...)` for the method's C++ signature, and the emitter writes
`static_assert(gp::thunk_matches<Sig, decltype(&thunk)>, ...)` for every method of a type at a static
conversion, so a C type that `go/types` can't tell from another is a compile error at the `.gp` line
instead of a call with the wrong signature (`runtime/reject_test.go`). An interface struct doesn't
convert to another one by copying (`B b = a;` doesn't compile), and `gp::to_iface` doesn't box an
interface value.

### Promoted methods in the method tables

The method sets that the tables hold are Go's, promoted methods included (`go/types`
`NewMethodSet`): a struct that embeds `Base` has `Base`'s value methods in the table of `T`, and all
of them in the table of `*T`; an embedded `*Base` or an embedded interface brings all of its methods
to `T` too. The thunk of a promoted method is the thunk of a declared one, because the struct has a
[forwarding member](#embedding) of the same form for it: `unbox<T>(self).M(args)` for the table of `T`,
`p->M(args)` for a method that `T` has (a const forwarder), `T::PM(p, args)` for one that only `*T` has (a static
forwarder with the owning pointer). The receiver is adjusted inside the forwarder, by the path of embedded
fields: the fields, `->` through an embedded pointer, and `gp::field_ptr` for the address of an embedded
value, so a pointer method of an embedded value changes the object that the interface holds.

- A promoted value method called through a nil `*T` in an interface is an ordinary nil dereference
  ("invalid memory address or nil pointer dereference"): Go's wrapper reaches the embedded field through the
  pointer. Only a **declared** value method of `*T` has `check_wrap`'s "value method main.T.M called using nil
  *T pointer". A pointer method promoted through a nil `*T` dereferences it too, to find the address of the
  embedded field; a pointer method promoted through a nil embedded pointer is called with that nil receiver.
- A method promoted from an embedded interface calls through its wrapper (`s.Speaker.Speak()`): a nil embedded
  interface panics with the nil dereference message, as in Go. A method that the outer type declares hides the
  promoted one, and a field of the outer type hides a method of the same name from deeper down (the type then
  lacks the method): the method set decides, so the itab never has a method that Go's selector rules
  don't pick, and an ambiguous name (the same name at one depth) is in no method set.
- **recover (5.10).** A promoted method whose declared body calls `recover()` is written with `gp::method_of_aware`
  in every table that has it (the table of `T`, of `*T`, and of each type that embeds it), so `defer i.M()` gives it the
  ticket; a method promoted from an embedded interface is written aware too (the dynamic method is not
  known), and the inner `icall` takes the ticket away unless the method that runs is aware
  (`tests/run/recover_iface_embedded.gp`).
- Forwarding members are marked by the table (`tables()`): the structs with tables get them, the others none.
  The interface struct of an interface with a method named like a type it uses (`Item() Item`) does not
  compile yet (step 5.4's ifaces.go writes the type unqualified).
- An anonymous struct type with embedded fields has its tables in `gp::td_struct<S>(fields, vm, pm)`
  (`gp_vm_gp_anon_...`, `gp_pm_gp_anon_...`), made with the descriptors, so `any(struct{ Base; n int }{...})`
  asserts to the interfaces that its promoted methods satisfy.
- A struct that embeds a C/C++ type has none of the C/C++ type's methods in its method set (`go/types` doesn't know them).

### The errors package and native functions (step 5.7)

`stdlib/errors` is a real package, ported from Go's `src/errors` (BSD-3-Clause) in `errors.gp`, `wrap.gp` and
`join.gp`, and lowered like any package of the program: `gpkg/errors/pkg.hpp`, one unit per file, descriptors in
`pkg_desc.cpp`, the namespace `gpkg_errors`. It differs from Go's source in two places, both listed in
`stdlib/errors/PORT.md`: `Join` ends with `string(b)` instead of `unsafe.String` (one more copy), and what Go does
with `internal/reflectlite` is three **native functions** (`comparableType`, `checkTarget`, `assign`).

A native function is a function of a standard package without a body and with a `//gocpp:native` line in its doc
comment ([ADR-027](../adr/027-native-std-functions.md)). Its calls become calls of the named C++ function with
the usual argument conversions; the generated code declares nothing:

```go
//gocpp:native gp::errors::assign
func assign(err error, target any) bool
```
```cpp
if (::gp::errors::assign(err, target)) { ... }     // in gpkg_errors, and from any package that calls it
```

`gocpp/errors.hpp` (included by `gocpp/rt.hpp`, defined in `runtime/src/errors.cpp`) has them, over the descriptors:

- `gp::errors::comparable(err)`: the dynamic type has an `==` hook (`gp_equal`), which is
  `reflectlite.TypeOf(err).Comparable()`. A struct with an interface field is comparable, and its `==` panics when the
  dynamic values can't be compared, as in Go (`errors.Is` does not guard against it either).
- `gp::errors::check_target(target)`: Go's three panics, as strings: `errors: target cannot be nil`, `errors: target
  must be a non-nil pointer`, `errors: *target must be interface or implement error` (the element type is not an
  interface and its method set lacks `Error`: a `*T` target where only `*T` has `Error` panics).
- `gp::errors::assign(err, target)`: `AssignableTo` and `Set`. When the target points to an interface variable, the
  value goes in with the itab of that interface (`getitab`, the variable is an `iface` at its address, interface
  structs have no members of their own); otherwise the dynamic type must be the element's descriptor, and the value is
  stored by the descriptor's **store hook**.

`type_desc::gp_store` (`void(void* dst, const std::shared_ptr<void>& data)`, set by `detail::with_cxx<T>` for every
descriptor of a C++ type that is copy-assignable and not an interface) assigns the value that an interface's `data`
holds to the object at `dst`: `*static_cast<T*>(dst) = ...` for a boxed value, and for a `gp::ptr<U>` a pointer that
shares the owner (as `unbox` makes it). It is null for an interface type and for a C++ type without copy assignment
(`errors.As` into such a target panics with a message of its own; Go has no such type).

Two differences from Go: `errors.As` into a Go struct value that holds a move-only C++ field (no copy assignment, so no
store hook) panics where Go would copy the value; and `sizeof(type_desc)` is 192 bytes (the store hook is one more
pointer).

**Objects of standard packages are shared.** The files of a standard package are the same text in every program, so the
object cache can give a program the objects another program made: their `#line` directives back to the generated file
name `$GOCPP/gen/gpkg/<path>/<file>` (like the `$GOCPP/stdlib/...` of the lines that map to `.gp` files), not the folder
of the program, and the object cache writes the folder of the generated files as `$GEN` in the arguments of its key and in
the paths of an entry (the files that the compile read, and the files that must be absent), and reads them in the
folder of the build that looks (`internal/build/objcache.go`, `TestLinkSharedAcrossGenRoots`,
`TestStdPackageObjectsAreShared`). A program that imports `errors` compiles its own units only. The lines of generated
code in a standard package's units name no file that exists, so a debugger shows no source for them (the lines that
map to `.gp` files are unchanged).

The names of the types of a standard package are Go's: `*errors.errorString`, `*errors.joinError`
(`interface conversion: error is *errors.errorString, not *main.MyErr`). A pointer to a named type has the package of
the named type for the "types from different packages" suffix of an assertion panic (Go's `*T` type has `T`'s package
path), so two `*a.Err` of `x/a` and `y/a` say "different packages", not "different scopes".

### The reflect subset (step 9.3)

`stdlib/reflect` is Go's `reflect` API, written in `.gp` over native functions ([ADR-035](../adr/035-reflect-subset-on-descriptors.md)):
`type.gp` (`Kind`, `Type`, `rtype`, `StructField`, `StructTag`, `Method`), `value.gp` (`Value`, `MapIter`, the
constructors), `deepequal.gp` (`DeepEqual`, Go's algorithm with its `visit` map) and `natives.gp` (the `//gocpp:native`
declarations of `gocpp/reflect.hpp`, defined in `src/reflect.cpp`). `internal/reflectlite` aliases it.

```go
v := reflect.ValueOf(&x).Elem()   // x is a struct { N int; S []string }
v.Field(0).SetInt(7)              // writes x.N: the field is the same storage at the field's offset
v.Field(1).Set(reflect.Append(v.Field(1), reflect.ValueOf("a")))
```

- **A type is a descriptor's address** (`uintptr`), and the descriptor, never `gp_full`'s copy, is its identity, so `Type`
  values (one `*rtype` for each descriptor) compare with `==`. `PointerTo(t)` and `SliceOf(t)` build and intern a
  descriptor at run time when the program has none.
- **A Value is `{typ, ptr, flag}`**: `ptr` is the address of the C++ object (for a pointer, the address of the
  `gp::ptr` object), and its owner keeps the storage alive. The flags are Go's (kind, `flagAddr`, `flagStickyRO`,
  `flagEmbedRO`); the panics and their texts are Go's (`reflect: call of reflect.Value.Int on string Value`,
  `reflect.Value.SetInt using unaddressable value`, `reflect.Value.Set using value obtained using unexported field`).
- **The operations are in `type_ops`** (`typeops.hpp`): `gp_trivial`, `gp_ctor`, `gp_dtor`, `gp_share` (the lifetime of
  a C++ object of the type: `New`, `Zero`, `MakeSlice`, `Set`) and `gp_refl`, one pointer to the constant group of the
  type's kind (`slice_refl`: make a slice over an array view, capacity; `ptr_refl`: a pointer that shares an owner;
  `map_refl`: new, len, find, set, erase, clear; `chan_refl`: len, cap). `type_desc` did not grow (208 bytes);
  `type_ops` went from 112 to 144 bytes (one per C++ type with a descriptor).
- **`fmt` and `reflect` share one reader**: `fmt` prints a `reflect.Value` operand as the value it holds (the name
  `reflect.Value` and the order of its fields are known to `pp::print_reflect_value`), honoring the read-only flags.
- **C/C++ values** are read as the Go kind of their shape (numbers, bool, string, `unsafe.Pointer` for every C pointer,
  a field-less `Struct` for a class); `Type.String()` is the C++ type's name; a class that can't be default constructed
  or copy assigned panics `reflect: C++ type X is opaque (it can't be made or assigned)` where reflect would make or
  store one. reflect does not make `gp::cptr` values.
- **Methods:** `NumMethod`, `Method(i)` (name, `PkgPath`, `Index`) and `MethodByName` list the exported methods; the
  `Type` of a method is nil and methods can't be called (`Value.Call`, `Value.Method` are not in the subset).
- **Not in the subset:** `MakeFunc`, `Value.Call`, `Value.Method`, `StructOf`, `FuncOf`, `MapOf`, `ArrayOf`, `ChanOf`,
  `Select`, channel `Send`/`Recv`/`Close`, `Value.Seq`: a call is a compile error.
## Package `os` and the system calls (step 9.6)

Package `os` is Go's own (`stdlib/os`, copies of go1.25.14's Linux files, `PORT.md`), over package `syscall`, whose system
calls are **native functions** named by `//gocpp:native gp::syscall::sys_*` lines (ADR-027, ADR-067). They are declared in
`gocpp/syscall.hpp` and defined in `runtime/src/os/linux/posix_file.cpp` (the only file of the runtime that includes the OS
headers for this; Windows gets its own file in Phase 14):

```go
//gocpp:native gp::syscall::sys_read
func sysRead(fd int, p []byte) (n int, errno int)
```
```cpp
std::tuple<int64_t, int64_t> sys_read(int64_t fd, const gp::slice<uint8_t>& p);   // (n, 0) or (0, errno)
```

- **The errno convention.** A native that can fail returns the Linux `errno` of the failure (0 for success), as an `int`
  result (a native that also returns a value, such as `sys_open`, returns `{-1, errno}` or `{0, errno}` for it: the value is
  meaningless when the errno is not 0), never an exception. The `.gp` wrapper makes the error: `syscall.Errno(e)` (boxed once for `EAGAIN`,
  `EINVAL`, `ENOENT`, as in Go), and package `os` wraps it in `*PathError`, `*LinkError` or `*SyscallError`. Another system
  maps its own codes to these numbers.
- **EINTR.** A native that a signal interrupts repeats the call (`retry` in `posix_file.cpp`), so Go code never sees `EINTR`
  from `open`, `read`, `write`, `stat`, ...; `close` is not repeated (the descriptor is gone whatever happens).
- **`O_CLOEXEC`** is added to every `sys_open`; `dup` is `F_DUPFD_CLOEXEC`.
- **Strings and slices.** A path is a `const gp::string&` (the `.gp` wrapper rejected a NUL byte with `EINVAL` first), copied to a
  C string in the native. A byte buffer is a `const gp::slice<uint8_t>&` whose data is read or written in place (one call,
  cut at 1 GiB). `stat` fills a `gp::slice<uint64_t>` of 16 numbers, which `fillStat` turns into a `syscall.Stat_t`.
- **Writes to descriptors 1 and 2** flush C's stdio first, like `fmt.Print`, so C and Go output interleave in program order.
- `os.Args` is `gp::args()`, the environment `gp::envs()` (package `syscall` keeps Go's copy under one `sync.RWMutex`, and
  `Setenv` also calls `setenv(3)`), `os.Exit` is `gp::os::exit`.

## Goroutines and channels

Phase 08 builds this; steps 8.1 to 8.6, 8.9 and 8.10 are in (the `go` statement, channels and their directions,
`select`, `range` over a channel; `sync` and `time` come next). The runtime is
`runtime/include/gocpp/{goroutine,waiter,chan,select}.hpp` and
`runtime/src/{goroutine,waiter,chan,select}.cpp`.

```go
go worker(jobs, results, 7)                 gp::go_fn(worker, jobs, results, 7);
go func() { ... }()                         gp::go_call([jobs]<int = 1>() mutable -> void { ... });
go obj.Method(a)                            gp::go_call([](auto&& gp_a0, auto&& gp_a1) { gp_a0.Method(gp_a1); }, obj, a);
go close(c)                                 gp::go_call([](auto&& gp_a0) { gp::close(gp_a0); }, c);
```

- **`go f(x, y)`** is lowered like `defer f(x, y)`: Go evaluates the function value and the
  arguments *now*, in the calling goroutine, in the order of a call (the receiver of a method call
  too, a value receiver as a copy), and the call runs in the new goroutine. The emitter writes the
  same shapes as for defer (a function of the package, a func value, a func literal as its lambda, a
  method with its receiver as the first argument, a builtin or a library function in a generic
  lambda, a C/C++ call with its object kept alive; [Defer](#defer)), with `gp::go_fn` instead of
  `gp_df.gp_push` and `gp::go_call` instead of `gp_df.gp_push_call`. `gp::go_fn(f, a...)` converts
  the arguments to `f`'s parameter types in the caller; `gp::go_call(c, a...)` stores `c` and copies
  of the arguments, which it gets as rvalues. A variable that a goroutine's closure shares with
  the function is boxed like any captured variable that changes, and a Go 1.22 loop variable is a
  new variable in each iteration, so `for i := range 3 { go func() { use(i) }() }` is right. A
  func literal that calls `recover()` is a plain call in a new goroutine (nothing is panicking
  there), and `go f()` with a nil func value is the fatal error `go of nil func value` at the go
  statement.
- **A goroutine is a detached OS thread** with an 8 MiB stack (ADR-007), started by
  `gp::detail::go_start`; there is no scheduler. The thread of a goroutine that ended is *reused*:
  it waits up to 5 seconds (at most 256 threads wait) for the next `go` statement before it exits,
  so a loop that starts a million short goroutines uses a few hundred threads, not a million.
  Goroutine ids are not reused (`goroutine 12 [running]:` is the twelfth started). The goroutine
  ends when its function returns; an unrecovered panic ends the whole program, `runtime.Goexit` ends
  only the goroutine (`gp::goexit()`), after its deferred calls.
- **Every goroutine has a record** with its id, its `gp::waiter` and why it is blocked
  (`"chan receive"`). `gp::waiter` is how a goroutine blocks: `gp_park()` waits for the waiter's
  one permit and takes it, `gp_unpark()` makes it available; `gp_unpark_with(f)` and
  `gp_wait(pred)` are the pair a waker uses to tell the goroutine that its operation is done (the
  channel code does that: `f` runs under the waiter's lock, `pred` is read under it, so the parked
  goroutine can destroy the cell the waker wrote to as soon as `gp_wait` returns).
  `gp::num_goroutine()` is `runtime.NumGoroutine`; `gp::num_blocked()` is how many goroutines wait
  inside a `gp::detail::block_scope` (the hook of the deadlock detector, step 8.11).
- **`gp::chan<T>`** is a `std::shared_ptr` to the channel object (16 bytes): a copy shares the
  channel, an empty handle is the nil channel, `==` compares the channels, and the hash is the
  address. `chan T`, `<-chan T` and `chan<- T` are the same C++ type with three different Go
  types: each has its own type descriptor (`gp::td_chan<gp::chan<T>>(dir, elem)`, interned with
  Go's name: `chan int`, `<-chan int`, `chan<- int`, `chan (<-chan int)`, `<-chan <-chan int`), so a
  type switch, `==` of interface values and (with step 5.11) `%T` tell them apart; the name that fmt's error forms print for a channel inside a struct is `chan T` whatever the direction, because the C++ type does not have it; a bidirectional channel
  converts to a directional one without any C++ code. A named channel type is a
  `gp::newtype` over it and can have methods (`type Queue chan int`).
- **The channel object** is Go's `hchan`: a mutex, a ring buffer, and two first-in-first-out queues
  of `sudog`s, the entries of goroutines that wait (on their own stacks: the waiter, a pointer to
  the value, a "done" cell that the waker sets). A send hands the value straight to a waiting
  receiver, else puts it in the buffer, else queues the sender; a receive takes a waiting
  sender's value (from the sender for an unbuffered channel, from the head of the buffer for a
  buffered one, whose slot the sender's value then takes), else a buffered value, else a zero
  value and `false` if the channel is closed, else it queues; `close` wakes all receivers (zero
  value, `false`) and all senders (they panic). A waiting goroutine spins for about 4 µs before it
  sleeps, so a hand-off to a goroutine that is running costs no system call. The mutex is a
  `std::mutex`, so ThreadSanitizer sees the happens-before edges Go promises.
- **The operations**:

  ```go
  c := make(chan T, n)     auto c = gp::make_chan<T>(n);   // makechan: size out of range
  c <- v                   gp::send(c, v);                  // the channel owns a copy
  v := <-c                 T v = gp::recv(c);
  v, ok := <-c             auto gp_t0 = gp::recv2(c); T v = std::get<0>(gp_t0); bool ok = std::get<1>(gp_t0);
  <-c                      gp::recv_drop(c);
  close(c); len(c); cap(c) gp::close(c); gp::len(c); gp::cap(c)
  ```

  `close(nil)`, a second `close` and a send on a closed channel (also one that was waiting when
  the channel was closed) panic with Go's texts (`close of nil channel`, `close of closed channel`,
  `send on closed channel`: `runtime.plainError` values, which `recover()` returns as errors);
  sending to or receiving from a nil channel blocks the goroutine for ever. A receive is a call for
  the [order of evaluation](#order-of-evaluation): `fmt.Println(<-c, len(c))` receives first;
  `len(c)` reads a count that a send or a receive changes. The element type needs no default
  constructor unless the program receives from a closed channel (a C++ type without one is a fatal
  error then). A C/C++ value that goes into a channel is copied if it is a variable and moved if it
  is a temporary or `std.move(x)` (`gp::cgo::defer_arg`, as for the arguments of a deferred call);
  `chan std.unique_ptr[C.int]` and `chan *lib.Type` work.
- **`select`** (step 8.5, [ADR-029](../adr/029-select-and-range-over-channels.md)) is a block with one
  object for each case, one call, and a `switch` on the number of the case that the call returns:

  ```go
  select {
  case v := <-a:
      use(v)
  case v, ok = <-x.c:
  case b <- f():
  case <-c:
  default:
  }
  select {}
  ```

  ```cpp
  {
      gp::sel_recv gp_s0{a};
      gp::sel_recv gp_s1{gp::chan<int64_t>(x.c)};   // a field: a copy of the handle
      gp::sel_send gp_s2{b, f()};
      gp::sel_recv gp_s3{c, gp::sel_drop};          // the value is not used
      switch (gp::select(gp_s0, gp_s1, gp_s2, gp_s3, gp::sel_default)) {
      case 0: { int64_t v = gp_s0.gp_take(); use(v); } break;
      case 1: { v = gp_s1.gp_take(); ok = gp_s1.gp_ok(); } break;
      case 2: {} break;
      case 3: {} break;
      default: {} break;
      }
  }
  gp::select();
  ```

  Go evaluates the channel expressions and the values to send once, in source order, when the
  statement starts, also for the cases that are not chosen (`case ch <- f():` calls `f` even when
  another case wins): the objects are declared in that order, each after the temporaries of
  its own calls and before the calls of the next case (as gc copies each channel and value into a
  temporary in source order: a later call that changes a variable does not change an earlier case). The left-hand sides of a receive case (`a[i], ok = <-c`) are evaluated only when the case
  is chosen, as the first statement of its body (the same code as the variables of a `range` loop). The
  number of a case is its position in the Go source, and the default is the `default:` label.
  A receive case holds the value in its own slot (no default constructor needed; a move-only C++
  element works, and nothing is constructed for a case that is not chosen); `gp::sel_drop` (a case
  whose value is not used) constructs nothing at all. A channel that is a local variable is held by
  reference, any other channel expression (a field, an element, a conversion) by a copy of the handle
  (`gp::chan<T>(x.c)`), and the result of a call as it is. `break` leaves the C++ `switch`, as it leaves
  the Go select; `continue` and labelled jumps go through it to the loop; a select without default that is a
  terminating statement in Go (every case body ends in one: return, goto, panic, a block, an if with
  else, `for {}` without break, a switch with default, a nested select, a labeled statement; no break
  to the select) is followed by `gp::select_unreachable();` so that a function may end with it
  without a `-Wreturn-type` warning.
  The algorithm is Go's `selectgo`: the cases are polled in a **random order** (uniform: several ready
  cases are chosen with equal probability), all the channels are locked in the **order of their
  addresses** (a channel in two cases once; no two selects can deadlock each other), the first ready
  case in poll order is done, else the default; else the goroutine leaves one entry for each case on its
  channel's queue, all sharing one **claim flag** and one wake-up cell, and parks as "select" (counted by
  `num_blocked()`). Whoever completes a case takes the flag first (a select that is taken is skipped
  and its entry dropped by `waitq::dequeue`), so one case happens; the goroutine then locks the channels
  again and removes its other entries. A send case on a closed channel panics when the poll reaches it
  (`send on closed channel`: a ready receive that comes first in the poll order wins, as in Go), a
  receive case on a closed channel is ready (zero value, `ok` false), a nil channel is never ready,
  and `select {}` and a select of only nil channels block for ever (counted as blocked). A select with
  up to 16 cases allocates nothing; 1,000 cases work (the generated `select_1000_cases` test).
  ThreadSanitizer's deadlock detector aborts above 64 locks held by a thread, so under TSan a
  select over more than about 60 channels needs `TSAN_OPTIONS=detect_deadlocks=0` (`gocpp run -race`
  sets it: [docs/guides/race.md](../guides/race.md)).
- **`range` over a channel** (step 8.6) receives until the channel is closed and drained:

  ```go
  for v := range ch {...}      for (auto gp_it0 = gp::range_chan(ch); gp::range_next(gp_it0);) { T v = gp_it0.gp_v(); ...
  for range ch {...}           for (auto gp_it0 = gp::range_chan_drop(ch); gp::range_next(gp_it0);) {...
  for x = range ch {...}       for (auto gp_it0 = gp::range_chan(ch); ...) { x = gp_it0.gp_v(); ...
  ```

  `ch` is evaluated once (the iterator holds it; reassigning the variable in the body changes
  nothing), the variable of each iteration is a new variable (Go 1.22: closures and `&v` see their own,
  and the body may assign to it), the value is moved out of the iterator (a move-only or C++ element
  works, and a closed channel does not need a zero value: `gp::chan_range` receives with
  `chan_recv_range`), a nil channel blocks for ever, and a closed buffered channel gives its buffer
  first. `break`, `continue`, labels, `goto` and `return` are the loop's. go/types rejects a range over a
  send-only channel and a second iteration variable.
- **A panic in a goroutine ends the program**, even when main returns first. A goroutine counts as
  handling a panic from the moment a deferred-call frame takes it until the panic object is gone
  (a `detail::panic_token` in `gp::panic_error`: recovered, or swallowed by a C++ `catch`, as fmt
  does for a `String` method that panics; no call is needed where a panic is caught), and when `main` returns, `run_main` waits for such
  goroutines (`detail::settle_panics`, at most 200 ms, as Go's `runtime.main` yields 1000 times),
  and if one has claimed the death of the program, it waits for the program to end. So
  `go func() { defer close(done); panic("x") }(); <-done` ends with `panic: x` and exit code 2, as in Go
  (the `defer wg.Done()` pattern); a deferred call that takes longer than the wait lets main win,
  as in Go. The goroutine trace is the goroutine's frames only: no `created by main.main in goroutine
  1` line, and the lambdas that `go` writes for a builtin (`go panic(..)`) may show as `?()` frames.
- **Blocked goroutines** (`gp::num_blocked()`): a goroutine enters its `block_scope` under the
  channel's lock, before its entry can be seen by a waker, and the waker calls `unblock` before it
  wakes it, so a goroutine that has been handed its value is not counted as blocked, though its thread
  has not run yet. The deadlock detector (8.11) compares `num_blocked()` with `num_goroutine()`.
- **Zero-size elements** (`chan struct{}`) take no buffer memory (`make(chan struct{}, 1<<40)` works,
  as in Go); the slots of a ring of them are one byte that nothing writes.
- **Idle threads** keep the stack pages they touched for up to 5 seconds (256 threads, worst case
  256 times the deepest recursion a goroutine reached); they are not returned with `madvise`.
- **Printing** a channel (`fmt.Println(c)`, `println(c)`) prints its address, `<nil>` (`0x0` for the
  builtin `println`) for the nil channel.
- If the OS can't start a thread, the program ends with Go's fatal error: `runtime: failed to
  create new OS thread (have N already; errno=E)`, then `fatal error: newosproc`, exit code 2.
- **Limits.** A goroutine blocked on a channel costs about 14 KB of resident memory and 8 MiB of address
  space (the stack is only committed when touched); measured on a 6.19 kernel with
  `vm.max_map_count` 1M and `threads-max` 2M: 1,000 blocked goroutines start in 0.1 s, 10,000 in
  0.8 s (65 MB), 100,000 in 13 s (1.3 GB; the machine was shared and loaded). A kernel with the
  default `vm.max_map_count` of 65,530 and no `MADV_GUARD_INSTALL` (before Linux 6.13) allows about
  20,000 to 30,000 threads (two mappings each); `ulimit -u`, `kernel.threads-max`, cgroup `pids.max` and
  `ulimit -v` limit it too, and when thread creation fails the program ends with the fatal error
  above. See [D7](language.md#d7-goroutines-are-os-threads).

Everything the OS does for this is behind `gp::os` (`runtime/include/gocpp/os.hpp`, the Linux
version in `runtime/src/os/linux/thread.cpp`): starting a detached thread with a stack size,
a thread slot, the stack bounds, and the stack-overflow hook. The Windows version
(`runtime/src/os/windows/`, step 14.1, [ADR-053](../adr/053-windows-os-layer-on-createthread.md))
starts threads with `CreateThread`, keeps the slot in TLS indexes (so an exception handler can read
it), and has no forced unwind (`exit_thread` ends the thread without running destructors).

The system calls of package `syscall` on Windows are one more thing behind the OS layer (step 14.3, [ADR-076](../adr/076-os-on-windows-over-a-generic-syscall.md)):
Go's own Windows code calls the system through four natives in `runtime/src/os/windows/win_syscall.cpp` (`gp::syscall::win_syscall15`
calls a function pointer with up to 15 integer arguments on the calling thread, clearing and then reading `GetLastError`;
`win_loadlibrary`, `win_loadsystemlibrary`, `win_getprocaddress`). A Go struct that the system fills (`WIN32_FIND_DATAW`,
`FILE_ID_BOTH_DIR_INFO`, `OVERLAPPED`) is the C++ struct that the compiler writes, with Go's field order and natural alignment and a
`static_assert` of its size, so its layout is the system's; a pointer argument is `uintptr(unsafe.Pointer(p))` of an object that does not
move.

**Portability notes for the C++ the compiler writes and the runtime (Windows, LLP64).** `long` is 32 bits
on Windows, so `int64_t` is `long long` there and `long` is `int32`: `%T` of a C `long long` prints `int`
(as does `int64_t`: C++ cannot tell them apart), and a C `long` prints `int32`. Output never goes
through the C library's text mode: `\n` is one byte, and a console gets UTF-16 (`WriteConsoleW`; the console's code page is not changed, as in Go). The
arguments and the environment are UTF-8 (Go's splitting of the command line), not the ANSI code page.

### The runtime package and the end of the program (steps 8.9 and 8.10, ADR-038)

- **The program ends with `gp::exit(code)`**: `run_main` after `main` returns (and after the settling of
  a panic that a goroutine is still reporting), `os.Exit` and the fatal errors. It flushes what C and
  C++ code printed through stdio (gocpp's own output is one `write` per call, never buffered), runs
  the leak check when the program is built with `-asan` (so a leaking program still fails under ASan,
  although the process ends with `_exit`), and calls `_exit`. **No C++ static destructor, `atexit`
  function or thread-local destructor runs**, because goroutine threads may still be using what they
  would destroy; a C++ global that must flush (a `std::ofstream`) has to be flushed by the program. A
  goroutine that is running, blocked or in a system call does not delay the exit (1000 blocked goroutines
  and a spinning one: about 0.11 s for the whole program). Exit codes: `main` returns 0 whatever
  else runs, a panic in any goroutine is 2, `gp::exit(n)` is n; a broken pipe on stdout or stderr is
  SIGPIPE.
- **`runtime` is a package written in `.gp`** (`stdlib/runtime`, `PORT.md` there lists the differences)
  with these natives (`gocpp/runtimepkg.hpp`, namespace `gp::runtime`):

  | Go | gocpp |
  |----|-------|
  | `Gosched()` | `sched_yield`: a hint, not Go's "run another goroutine first" |
  | `NumGoroutine()` | `gp::num_goroutine()`: the main goroutine and every goroutine from its `go` until its function has returned |
  | `GOMAXPROCS(n)`, `NumCPU()` | the value is remembered and used by nothing; the default is the CPUs the process may run on (`sched_getaffinity`), lowered by the cgroup CPU limit (rounded up, at least 2), overridden by `$GOMAXPROCS` |
  | `Goexit()` | `gp::goexit()`: deferred calls run, `recover()` returns nil, the goroutine ends; in `main` the program goes on until the other goroutines end, then `fatal error: no goroutines (main called runtime.Goexit) - deadlock!` |
  | `LockOSThread`, `UnlockOSThread`, `KeepAlive`, `GC`, `SetFinalizer` | nothing (a thread for each goroutine, reference counting) |
  | `Caller`, `Callers`, `CallersFrames`, `FuncForPC`, `Stack` | the program's symbol table and DWARF line table; names are Go's, files and lines those of the `.gp` source; `Stack(buf, true)` adds the other goroutines: the stack of one that is blocked or sleeping, only the header of one that runs |
  | `ReadMemStats` | the heap numbers from the allocator; the counters stay 0 |
  | `Error`, `PanicNilError`, `TypeAssertionError` | real Go types; the runtime's panics use the package's values once the package is loaded |
  | `Version()`, `GOOS`, `GOARCH` | `go1.25.14`, `linux`, `amd64` |
  | `runtime/debug` | `Stack`, `PrintStack`, `FreeOSMemory` (`malloc_trim`), and `SetGCPercent`, `SetMemoryLimit`, `SetMaxStack`, `SetMaxThreads`, `SetPanicOnFault` that keep their values, and `SetTraceback`, which sets the traceback level of a panic and of a fatal error, either way (`all`, `system`, `crash` and a number from 1 print every goroutine, `single` only the goroutine, `none` and `0` only the text; the `GOTRACEBACK` variable is the floor, as in Go). Differences: `crash` ends with exit code 2, not an abort (SIGABRT, 134); `wer` is a word that Go does not know on Linux (level 0 with all goroutines), and on Windows it is `crash`; a `fatal error:` prints one goroutine by default, where Go prints all of them for a throw |

## Generics (steps 7.1 to 7.3)

A generic function becomes a C++ function **for each list of type arguments that the program names**
(an *instance*), lowered as if the function were written with those types
([ADR-030](../adr/030-generic-instances.md)). Types are never C++ template parameters, because `int` and
`int64` are one C++ type and the semantics of `a + b`, `T(x)`, `len(s)`, `x.M()` or `any(x)` depend on
the Go type.

```go
func Map[T, U any](xs []T, f func(T) U) []U {
	out := make([]U, 0, len(xs))
	for _, x := range xs {
		out = append(out, f(x))
	}
	return out
}

func main() {
	fmt.Println(Map([]int{1, 2, 3}, func(i int) string { return fmt.Sprint(i * 2) }))
}
```

```cpp
namespace gpkg_main {

gp::slice<gp::string> gp_inst_33fba50d_Map(gp::slice<int64_t> xs, gp::func<gp::string(int64_t)> f);

// Map[int,string]
gp::slice<gp::string> gp_inst_33fba50d_Map(gp::slice<int64_t> xs, gp::func<gp::string(int64_t)> f) {
    gp::slice<gp::string> out = gp::make_slice<gp::string>(0, gp::len(xs));
    for (auto gp_it0 = gp::range_slice(xs); gp::range_next(gp_it0);) {
        int64_t x = gp_it0.gp_v();
        out = gp::append(static_cast<gp::slice<gp::string>&&>(out), f(x));
    }
    return out;
}

void main() {
    gp::fmt::Println(gp::fmt::as(gp_tdc_0, gpkg_main::gp_inst_33fba50d_Map(gp::slice_of<int64_t>({1, 2, 3}), ...)));
}
```

- **Types of the body.** `go/types` recorded every expression of the generic function in terms of the
  type parameters. `internal/lower` replaces them by the type arguments (`subst.go`: `Types`, the
  variables, `Implicits`, `Instances`, and a selection `x.String()` with `x` of type `T` is looked up
  again on the type argument; `generics.go: apply`). The lowering then runs unchanged, so an `int8`
  sum wraps, `T(x)` truncates as Go does, `a / b` panics for integers, and `any(x)`, `%T`, `case T:`
  and `x.(T)` see the type argument. A constant converted to `T` has the type argument's type;
  `unsafe.Sizeof(x)` is a constant in the instance. The methods of a constraint are called as the type
  argument has them: a value method, a pointer method (`*T`), a promoted one, a method of an
  interface type argument (dynamic dispatch).
- **Where and what.** An instance is written in the translation unit of the function that asks for
  it, before that unit's functions (a prototype first), in the namespace of the asking package:
  `gp_inst_<hash>_<name>`, the hash of the unit and the type arguments (two units that need one
  instance have one copy each). A generic function of another package is instantiated by the asking
  package from the other package's syntax and types: the names in the body (functions, variables,
  types, unexported ones too) are the other package's, fully qualified, and `pkg.hpp` of the other
  package is not changed. Instances of instances (a generic function that calls one) and recursion are
  found while the unit is lowered; one instance per unit and type arguments.
- **As values.** `f := Map[int, string]` and `var g func(int) int = Id` are `gp::func_of<&instance>`;
  `defer`, `go` and method values of instances go through the call forms of ordinary functions.
- **Traces.** The frame of an instance is `main.Map[...]`, a closure in it `main.Map[...].func1`
  (Go's names; `runtime/src/trace.cpp` reads `gp_inst_<hash>_Map`).
- **C and C++ type arguments.** `go/types` records no instance when a type argument (or an argument
  of the call that fixes one) is a C/C++ type. The instance is then made from the syntax: a written
  type argument (`Zero[std.vector[int]]()`) is spelled and baked into the instance; the others are
  **C++ template parameters of the instance**, deduced by the C++ compiler from the call
  (`template <typename T> T gp_inst_..._Id(T x)`; `Id(v)` with `v` a `std::vector`). Values of such a
  type can be copied, passed, compared (`comparable`: C++'s `==`), stored in slices and maps, boxed in
  an interface (only `any`, as for any C/C++ value) and printed by `fmt` (when the C++ type has a
  formatter or `operator<<`); a method of the constraint, `T interface{ size() C.size_t }`,
  called on it is the C++ member call `x.size()`. `go/types` cannot check these constraints and the
  C++ compiler does: its errors are the user's, at the `.gp` line. A type argument that C++ cannot
  deduce (`T` only in `[]T` of a C++ vector, or the pointee of `&x` of a C++ variable) is a C++ error
  asking for the type.
- **Operators and callbacks with C types.** `Add[C.double](1.5, 2.5)` with `a + b` in the body is
  C++'s `+` (the constants in it are C++ literals), as for C values; an instance with written
  type arguments goes to C as a callback (`stdlib.qsort(..., Cmp[int32])`: a plain function
  pointer) and is a func value (`h := Id[std.string]`). A generic function whose type argument C++
  deduces (`var h func(std.string) std.string = Id`) can be neither: a user error that asks for the
  type arguments. What the C++ compiler says about the body of an instance (`fmt` cannot print a
  `std::vector`) is the user's error at the line of the body, with the call as "from here".
- **A generic function of another package that uses C/C++ names** (a header import, `C.int`, a
  C++ value) can only be instantiated in its own package: its body is lowered with the asking
  package's C/C++ state, not the owner's (a user error at the call, "Phase 12").
- **Known differences from gc.** A variable, parameter or type named `C` is rejected
  (`cannot declare C - C is reserved for C's built-in types`, the loader's rule), but a **type
  parameter** may be named `C` (functions, generic types and their receivers): it shadows the
  pseudo-package in its scope, where `C.int` is Go's "C.int is not a type". For `T = *Base`
  and a value method `String`, calling `x.String()` on a nil `x` in generic code panics with the nil
  dereference text, where gc says `value method main.Base.String called using nil *Base pointer`
  (the exit code is the same). A method value `x.Value` with `T = *Counter` copies `*x` when it is
  evaluated, as the spec says; gc's generic code binds the pointer, so later changes show through.
  A generic function named like a C++ keyword (`class`) shows in a trace as `main.class_[...]` (the
  `_` of the escape).
- **Not built.** A C/C++ type as a type argument of a generic *type*
  (see below), a generic function as a func value when one of its
  type arguments is a C++ type that C++ deduces. (`cmp`, `slices`, `maps` and `iter` are Go's own
  generic packages since step 7.10: their functions are instantiated like yours, in the unit that asks.)
- **Cost.** Each instance is lowered and compiled like a function written by hand. A program with 20
  generic functions (a loop, a closure, a map, a slice) each instantiated with 10 types (200 instances
  in one unit) compiled in 15.2 s of CPU with g++ and 12.3 s with clang++; the same program with the 200
  functions written out by hand (4200 lines instead of 600): 15.7 s and 12.4 s. A smaller program of the same
  shape (step 7.12, 20 generic functions of one-line bodies and 200 calls, with a warm runtime cache, `-O0 -g`):
  generic 2.6 to 3.0 s with g++, 2.1 s with clang++; written out: 2.5 to 2.6 s and 2.1 s; the binaries differ
  by 7 KB (4.170 MB against 4.163 MB with g++, 3.512 against 3.506 with clang++; hello world is 3.5 and 3.0).
  (A first build in a fresh cache pays for the runtime objects the program uses: measure the second one.)
  A change to a generic function body recompiles the units that instantiate it, and no header.

### `-gp:concepts`: C++20 concepts for Go's constraints (step 7.9)

`gocpp build -gp:concepts` and `gocpp emit -gp:concepts` (off by default: without the flag the files are
byte for byte the same as before) also write C++20 `concept`s into `pkg.hpp` of each program package.
They are for C++ code that works with the package (the `cpp-lib` mode, step 6.10, or any C++ that includes
`pkg.hpp`): to ask whether a C++ type is in a Go constraint's type set and has its methods, and to put a
`requires` clause or a `static_assert` on C++ code that wants the same types, so that a wrong type is an
error that names the constraint and not a failure inside a template. The generated code does not use
them (under ADR-030 there is no C++ template to put them on: a generic function exists for the instances
the Go code names).

```go
package k

type Integer interface{ ~int | ~int8 | ~int16 | ~int32 | ~int64 }
type Ordered interface{ Integer | ~string }
type Greeter interface{ Hello() string }

func Max[T Ordered](a, b T) T                       { /* ... */ }
func Len[S ~[]E, E any](s S) int                    { return len(s) }
func Greet[T Greeter](x T) string                   { return x.Hello() }
```

```cpp
#include <gocpp/concepts.hpp>   // the building blocks (the header includes it itself)

// for each named interface type of the package that has no type parameters: gp_concept_<Name>
template <typename T>
concept gp_concept_Integer =
    gp::concepts::tilde<T, int64_t> || gp::concepts::tilde<T, int8_t> || /* ... */;

// for each generic function (also an unexported one): gp_sat_<Func>, the constraints of all the
// type parameters, in order; a constraint that names another type parameter uses its template parameter
template <typename T>
concept gp_sat_Max = gp_concept_Ordered<T>;
template <typename S, typename E>
concept gp_sat_Len = gp::concepts::tilde<S, gp::slice<E>>;
template <typename T>
concept gp_sat_Greet = gp_concept_Greeter<T>;
// where gp_concept_Greeter<T> is, for the method Hello() string:
//   requires(T& x) { { x.Hello() } -> std::same_as<gp::string>; }
//   || requires(T& x) { { x->Hello() } -> std::same_as<gp::string>; }
//   || requires(T& x) { { gp::concepts::ptr_elem_t<T>::Hello(x) } -> std::same_as<gp::string>; }
```

```cpp
template <typename T>
    requires k::gp_sat_Max<T>
T twice(T x) { return x + x; }   // twice(gp::string("a")) is an error that names gp_sat_Max
static_assert(k::gp_sat_Greet<k::Named> && !k::gp_sat_Greet<int64_t>);
```

The pieces are in `runtime/include/gocpp/concepts.hpp` (which only a `pkg.hpp` with concepts includes;
`rt.hpp` does not): `tilde<T, U>` is Go's `~U` (`T` is `U`, or a defined type over `U`: a
`gp::newtype`'s `gp_underlying`), `exact<T, U>` is `U`, `comparable<T>` is `std::equality_comparable`
(a slice, map or func has no `==` in C++ either; a struct has it when its fields do), and a method is a
`requires` expression for `x.M(a)` returning exactly the Go result type, for `x->M(a)` (a value method of
the pointee through a `gp::ptr`) or for `ptr_elem_t<T>::M(x, a)` (a pointer method, a static function that
takes the pointer first, so only a pointer has it: as in Go's method sets). The `x->M` and static forms need
`T` to be a `gp::ptr` itself (`is_ptr<T>`): a defined pointer type (`type NPS *S`, a `gp::newtype` over a
`gp::ptr`) has no methods in Go and satisfies no method constraint. A method named like its struct is a
member with a `_` at the end (`Visit_`, because of the constructor): the requirement tries both names. The
text of a concept uses names that no Go name can be (`gp_T`, `gp_x`, `gp_a0`, `::std::`, `::gp::`), and a
type parameter named `std` or `gp` is renamed as the other reserved names are. A union is the disjunction of its
terms, an embedded interface the conjunction of its elements and methods. `-gp:concepts` also writes the
forwarding members of every struct (as `AllForwarders` does), so a promoted method satisfies a method
constraint as it does in Go.

What it does **not** give, precisely: (1) a concept may accept more types than Go's constraint, never fewer
types that Go accepts: `int` and `int64` are one C++ type (`int64_t`), `uint8` and `byte` are one, so
`~int` also accepts a defined type over `int64`; two defined struct types are two structs but `~struct{...}`
is not spelled; (2) a term that C++ cannot spell (an anonymous struct, a C or C++ type, a type of the
standard library, a generic type) is left out of its union, which makes the concept accept everything for
that union; (3) a method signature with such a type is left out (no requirement); (4) a method's result is
checked with `std::same_as`, so a C++ method that returns a convertible type does not satisfy it; (5) an
interface with type parameters (`type Set[T any] interface{...}`) has no concept (7.3); (6) it never makes
a generic function callable from C++ for an arbitrary type: the instances are the ones the Go code names,
and a C++ caller still calls those by name; (7) the C++ names are those of the package's lowering, so
a renamed C++ keyword method is the escaped one. (8) the flag writes the forwarding members of every
struct, so the emitted C++ is larger (about 1.7% more bytes over the test programs, up to 43% for programs that
embed a lot; the `-O0` binaries grow by 0 to 1.4%). A program built with the flag behaves as without it
(`TestConceptsRun`).

The tests are in `internal/cppgen/concepts_test.go` and `internal/cppgen/testdata/program/concepts/`:
`static_assert`s (positive and negative) over each concept, compiled with g++ and clang++ (two modules:
`concepts` and `concepts2`, the second with cross-package constraints, names that the text of a concept uses,
a method named like its type, a variadic method, a defined pointer type, a Unicode name and an unexported
generic function); a corpus test (`TestConceptsCorpus`) that emits about 120 of the run tests with the
option and compiles them with both compilers; `TestConceptsFlag` in `cmd/gocpp` (emit, build and run with
`-gp:concepts`); `runtime/test/concepts_test.cpp` (the building blocks); snippets that
must be rejected with an error that names the concept; the output without the flag has no concept and
does not include the header; the program with the flag prints what real Go prints.

### Generic types (step 7.3)

A generic type is **one C++ struct, method set and type descriptor for each instance**
(`Stack[int]`, `Pair[string, []int]`), not a template: the instance is a type of its own, as in
`go/types`, and its struct, its methods and its descriptor are written the way a struct declared with
those types would be. Go's `%T` text is the descriptor's name.

```go
type Stack[T any] struct{ items []T }

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }
func (s Stack[T]) Len() int  { return len(s.items) }

type Pair[K comparable, V any] struct {
	Key K
	Val V
}

var s Stack[int]
p := Pair[string, Stack[int]]{"k", s}
fmt.Printf("%T\n", p) // main.Pair[string,main.Stack[int]]
```

```cpp
namespace gpkg_main {
struct gp_inst_e0e468d0_Stack {                      // Stack[int]
    gp::slice<int64_t> items;
    static constexpr auto gp_fields = gp::fields(gp::field(&gp_inst_e0e468d0_Stack::items, "items", false, false));
    static void Push(gp::ptr<gp_inst_e0e468d0_Stack> s, int64_t v);
    int64_t Len() const;
};
struct gp_inst_5122dbb8_Pair {                       // Pair[string, Stack[int]]
    gp::string Key;
    gp_inst_e0e468d0_Stack Val;
    ...
};
inline const gp::type_desc gp_td_gp_inst_5122dbb8_Pair =
    gp::named<gp_inst_5122dbb8_Pair>("main.Pair[string,main.Stack[int]]", "main", ...);
inline void gp_inst_e0e468d0_Stack::Push(gp::ptr<gp_inst_e0e468d0_Stack> s, int64_t v) { ... }
}
```

(`tests/golden/generics_types.cpp.golden` is the whole file.)

- **Shared items, made by the declaring package.** An instance is shared text, like an unnamed
  struct (ADR-025): every package that mentions it writes the same struct, thunks, descriptor and
  method bodies in its `pkg.hpp`, under macro guards (`GP_INST_<hash>` for the struct,
  `_IMPL` for the descriptor and method tables, `_POST` for the method bodies, which go after the
  header's tail), all `inline`. The text is made by the package that declares the generic type,
  in that package's namespace (`gpkg_<declaring package>`), where its unexported fields, methods,
  helper functions and variables are; every importer's `pkg.hpp` has the same text, so `Box[b.Feet]`
  named by `a`, `b`, `c` and `main` is one type (one descriptor: assertions, type switches, `%T`, map
  keys and `==` agree). The name is `gp_inst_<8 hex digits of a hash of the identity text>_<Name>`; a
  hash that clashes with another instance's takes 10 or 12.
- **Methods.** The methods of an instance are lowered with it, from the generic method's syntax and
  the substitution of ADR-030 (so value and pointer receivers, promoted methods through an embedded
  instance, method values and expressions, and calls through interfaces are the ones of any struct).
  A method that returns another instance (`Swap() Pair[V, K]`) asks for that instance, to a fixed
  point (a recursive or mutually recursive generic type is a finite set of instances).
  Instances are written for what the program names: a type's methods are all lowered when the type
  is, whether called or not.
- **Descriptors.** An instance's descriptor is named with Go's `%T` text: type arguments in full (import
  paths for packages, `main.Point`), a comma without a space, nested instances inside:
  `main.Pair[string,[]int]`, `*main.Stack[main.Pair[int,map[string]bool]]`. A type declared in a function
  that is a type argument gets gc's number (`main.Box[main.point·1]`): the 1-based place of its declaration
  among the defined types declared in function bodies of its package, in source order (closures and generic
  functions included, aliases not; `internal/lower/canon.go: localOrdinal`); outside the brackets it has none.
  `%v` and `%+v` use the
  field names and values of the instance, a `String()` or `Error()` method is called, and an
  interface that the instance implements has its method table (value set, pointer set) like any struct.
- **Interfaces.** Generic interface types are instances too (`Getter[int]`: an interface struct with the
  methods substituted, named like the struct instances); a generic type satisfies a generic interface by
  its method tables, and `v.(Getter[int])`, `case *Stack[int]:` and `case Box[string], Box[bool]:` compare
  descriptors.
- **Traces.** `main.Stack[...].Peek` for a value method and `main.(*Stack[...]).Pop` for a pointer method
  (Go's names; `runtime/src/trace.cpp`).
- **Generic aliases** (Go 1.24, `type SP[A any] = Pair[string, A]`) and aliases of instances
  (`type IntStack = Stack[int]`) are `go/types` aliases: the same type, no C++ of their own.
- **Types declared in generic functions** (`func F[T any]() { type local struct{ x T } ... }`, also in a
  method of a generic type) are types of each instance, as in Go: `%T` of `local{v}` in `F[int,string]` is
  `main.local[int,string]` (also for a local type that does not mention `T`; the arguments are the
  function's, or the receiver's), and the type of `F[int,string]` is another type than the one of
  `F[bool,bool]` or of a `local` of another function. The lowering gives each one a synthetic generic
  origin whose type parameters are copies of the function's (`internal/lower/localtypes.go`), replaces
  every mention in an instance's body by its instance, and from there it is an instance of a generic
  type as above (no methods, a struct or a named non-struct type).
- **Generic types declared in functions** (`func F() { type Box[T any] struct{ v T } }`; Go accepts them, and
  they have no methods). In a function that is not generic the type is a generic type like a package-level
  one with a name of its own (two functions may declare a `Box`: two types, also for the same arguments);
  the C++ is that of any other instance. In a generic function the synthetic origin has the function's type
  parameters first and the type's own after them, and `Box[string]` in `F[int]` is the instance
  `[int, string]` of it: `%T` writes `main.Box[int;string]`, as gc does (`internal/lower/localtypes.go`,
  `canon.go`). A local generic type with a C/C++ type argument, or inside a generic function whose type
  argument is a C/C++ type that C++ deduces, is the same user error as a package-level one.
- **Standard generic types.** `atomic.Pointer[T]` is `{_ [0]*T; lk uint32; v *T}` with the spin lock
  of `atomic.Value`, written in Go (`stdlib/sync/atomic/type.gp`); `iter.Seq[V]` and `iter.Seq2[K, V]` are
  generic function types: an instance is a named type whose `%T` is `iter.Seq[int]`.
- **Generic functions over `S ~[]E` with a C++ element type.** When C++ deduces `S` (a Go slice of a
  C++ type, `[]std.vector[int]`), `E` is not deducible from the arguments, so the template gives it the
  default `typename gp::detail::slice_elem_of<S>::type`; `len`, `cap`, index, slice expressions, `range` and
  `append` on a value of `S` are the slice operations (`tests/interop/generics_cxx_slice_core.gp`).
  `make(S, n)`, `copy` and conversions to `S` are not built for a deduced `S`. `E` may come before `S`
  (`func Wrap[T any, S ~[]T](xs S)`): the template parameters are written with each `E` after its `S`, so
  that the default can name it (`tests/interop/generics_cxx_range_func.gp`).
- **Range over a generic iterator with a C++ type argument** (`for s := range Seq(v)`, `Seq[T any](xs []T)
  func(yield func(T) bool)`, `v []std.string`): `go/types` gives the call an invalid type, so the lowering
  does not know what the iterator yields. The loop body is a lambda with `auto` parameters, passed as it is
  to the iterator (a `gp::func` converts from any callable), and the range variables are `auto` locals as
  for `x := lib.f()`; `break`, `continue`, `return`, labels, `defer` and a variable that a closure captures
  (boxed) work as for Go types (`tests/interop/generics_cxx_range_func.gp`,
  `generics_cxx_range_adapters.gp`). With written type arguments (`for s := range Seq[std.string](v)`, a
  variable `it := Seq[std.string](v)`, or the instance `Each[std.string]` as the iterator) go/types types
  nothing, so the lowering records the instance's signature for the range expression first
  (`rangefunc.go: typeExplicitIterators`) and the loop variables get the written C++ types; a range variable
  of a Go type there (an `int` index) is a C/C++ value for the lowering's checks, converted with `int(i)`
  (`generics_cxx_range_explicit.gp`). The iterator must be written as a func type: `iter.Seq[T]` with a C++
  `T` is the generic type limit below.
- **Not built.** A C/C++ type as a type argument of a generic type (`Box[std.string]`,
  `Stack[std.vector[int]]`), also through a generic function whose type argument is a C++ type
  (`func F[T any](v T) Box[T]`): a user error that says so at the instantiation, because the fields,
  the descriptor and the equality of an instance are made from Go types and every package that
  mentions it must write the same text. (The design that would build it: a placeholder for the written
  C++ type, part of the instance's identity, allowed where the asking package is the declaring one,
  with the header including the C/C++ headers; deduced type arguments would stay an error.) This includes
  `iter.Seq[std.string]`. Instances need the split layout (`gocpp build`).
- **Cost.** Each instance's text is in every translation unit that includes the header of a package that
  mentions it, so the compile time grows with instances times units: a program with 20 generic types,
  each with 3 methods and 10 instances (200 instances, all printed with `fmt`) is 17k lines of C++ and
  compiled in 69 s with g++ and 56 s with clang++ (4 units, on a loaded machine), against 38 s and 35 s
  for the same 200 types written out by hand.

Source: [Phase 07 §2](../../plans/2026-10-13-gocpp/phase-07-generics/README.md), [ADR-030](../adr/030-generic-instances.md).

## Range over functions

`for x := range seq { body }` is Go's own rewrite (`cmd/compile/internal/rangefunc/rewrite.go`,
[ADR-033](../adr/033-range-over-func.md)): `seq` is called with the body as its `yield` function.

```go
func find(n int) (int, bool) {
	for x := range Count(10) {
		if x == n {
			return x * 2, true
		}
	}
	return 0, false
}
```

```cpp
std::tuple<int64_t, bool> find(int64_t n) {
    gp::ptr<int64_t> gp_r0 = gp::new_<int64_t>();      // the results are variables of the function,
    gp::ptr<bool> gp_r1 = gp::new_<bool>();            // boxed: the body sets them
    {
        auto gp_rs0 = gp::new_<gp::rangefunc_state>(); Count(10)(gp::func<bool(int64_t)>([n, gp_rs0, gp_r0, gp_r1]<int = 0>(int64_t x) mutable -> bool {
            gp_rs0->gp_enter();                        // READY -> PANIC, or Go's misuse panic
            if (x == n) {
                (*gp_r0) = x * 2; (*gp_r1) = true; gp_rs0->gp_next = -1; return gp_rs0->gp_exit();
            }
            return gp_rs0->gp_continue();              // the end of the body: READY, true
        }));
        gp_rs0->gp_finish();                           // the iterator returned: EXHAUSTED
        if (gp_rs0->gp_next == -1) {
            return {(*gp_r0), (*gp_r1)};               // the return, in the function itself
        }
    }
    return {0, false};
}
```

- **The body is a normal closure**: an explicit capture list, never `[&]`; the variables of the function
  that it assigns are boxed like those of any closure. The range variables are its parameters, so each
  iteration has its own (a variable that a closure keeps or whose address is taken is boxed in the body).
  `for a[i], m[k] = range seq` has parameters of our own (`gp_p0`) and the assignment first in the body.
  The range expression is evaluated once, before the loop.
- **State.** Each loop run has a boxed `gp::rangefunc_state` (`runtime/include/gocpp/rangefunc.hpp`) with
  Go's states: `gp_enter()` (READY to PANIC; any other state panics: DONE `range function continued
  iteration after function for loop body returned false`, EXHAUSTED `... after whole loop exit`, PANIC
  `... after loop body panic`), `gp_continue()` (READY, `true`), `gp_exit()` (DONE, `false`) and
  `gp_finish()` after the iterator returned (PANIC there is `range function recovered a loop body panic
  and did not resume panicking`; then EXHAUSTED). All are `runtime.Error`s with `runtime error: ` in
  front. A `yield` that an iterator keeps and calls after the loop finds EXHAUSTED and panics before the
  body touches anything (ASan-clean: the state, the captured boxes and the results are all boxed).
  `-nochecks` leaves these checks on.
- **Jumps.** `break` is `return gp_rs0->gp_exit();`, `continue` `return gp_rs0->gp_continue();`. A
  `return` sets the results and `gp_next = -1`; a `goto` or a labeled `break`/`continue` to something
  that is not a loop of the nest gets a code below -1; a labeled `break` or `continue` of an outer
  range-over-func loop number `i` (outermost 0) gets `2(i+1)` / `2(i+1)-1`. The loop exits (`gp_exit`),
  and the code after the call of each loop on the way tests `gp_next` and either passes it on
  (`return gp_rsJ->gp_exit();`) or, in the function that holds the target, does the jump (`goto`,
  `return`, or the labels of a plain `break L` and `continue L`, flow.go). `gp_next` is a member of the
  state of the outermost loop of the nest, which the bodies inside capture when they use it. A `goto`
  to a label in the same body is a `goto`.
- **defer and recover.** A `defer` in the body registers on the function's own frame: the body captures
  `gp_df` by reference (the body only runs while the loop's function is running, also when the iterator
  calls `yield` on another goroutine; a late call panics first). `recover()` in the body is **nil**, as in
  Go: the body is a closure that the iterator calls, not the deferred function that a panic runs, also
  when the function with the loop is itself that deferred function (a function whose only `recover()` is
  in a body is not "aware", recover.go, and takes no ticket). `recover()` in the range clause, in the
  function's code after the loop, and in a func literal that the body `defer`s (the panic runs it) work
  as usual. The function's results of a function with a `return` with values in a body
  are boxed variables with names of our own; an unnamed result becomes one, as in Go, so a deferred
  call that recovers a panic of the iterator after the body returned makes the function return what
  the body set.
- **C/C++ values.** The yield function may take C/C++ values (`func(yield func(std.string) bool)`): the
  body's parameter has the C++ type written in the yield parameter, and the range variable is a C/C++
  value for the checker (a conversion `int(x)` of it is a cast), also boxed when a closure keeps it.
- **Costs** (300,000,000 iterations of `sum += x & 3` over a counting iterator, g++ 15 / clang++ 21 on
  the shared 128-core machine, user CPU): with `-O2`, 0.58 s / 0.54 s (1.9 ns an iteration, the same as
  the closure called directly, and 5.8x / 5.4x Go 1.25's 0.10 s, which inlines the iterator and the
  body); with gocpp's default `-O0`, 8.6 s / 10.6 s (28 and 35 ns: the indirect call, the state
  checks and the boxed `sum` are not inlined; a plain `for` loop is 1 ns). Each run of a loop
  allocates the state and the body's closure. Compile time: 100 functions with two nested loops each
  (200 loops): 13.3 s of CPU with g++ and 8.3 s with clang++ at the default flags, the same as 200
  func literals passed to the iterator (12.1 s, 8.9 s), and 11 times 200 `range` over slices (1.2 s):
  the cost is the closure (`gp::func` construction and call templates), not the state machine.
- **Recursion** through a loop body costs three C++ frames a level (the function, the iterator, the
  body lambda): about 10,000 levels pass and 20,000 end in `fatal error: stack overflow`, earlier than
  plain recursion.
- **Stack traces** leave the bodies out (the lambda is a generated helper: `<int = 0>`); Go shows
  `main.f-range1`. A func literal inside a body is numbered with the function's other literals
  (`main.f.func1`).
- **Differences from gc.** A `defer` in a body inside a func literal that gc inlines is attached to
  the caller in gc 1.25 (a gc bug: `go run` of such a program runs the literal's deferred calls late);
  gocpp runs them when the literal returns, as the spec says. Range over a value whose type is a type
  parameter with a func core type (`S ~func(yield func(int) bool)`) works: the instance has the concrete
  type. `iter.Seq`, `iter.Seq2`, `iter.Pull` and `iter.Pull2` are Go's own (step 7.10, ADR-078); the coroutine of `Pull` is a goroutine (a thread) that hands control back and forth.

Source: [Phase 07 §2.5](../../plans/2026-10-13-gocpp/phase-07-generics/README.md#25-range-over-func-iterators-go-123),
[ADR-033](../adr/033-range-over-func.md), `internal/lower/rangefunc.go`.

## Package time (step 8.8)

`time` is Go's own code (`stdlib/time`, ported by hand: `PORT.md` lists the changes), lowered like any
package, so `Duration`, `Time`, `Month`, `Location`, `Format` and `Parse` are C++ written by the emitter
from Go's algorithms. The parts that need the runtime are `//gocpp:native` functions of `gp::time`
(`gocpp/time.hpp`, ADR-027, ADR-041):

| Go (inside package time) | C++ |
|---|---|
| `now() (sec int64, nsec int32, mono int64)`, `runtimeNano() int64` | `gp::time::now()` (a `std::tuple`), `gp::time::nano()`: `system_clock` and `steady_clock` (CLOCK_REALTIME and CLOCK_MONOTONIC through the vDSO) |
| `time.Sleep(d)` | `gp::time::sleep(int64_t ns)`: the goroutine waits on its own `gp::waiter` with a deadline; it is not counted as blocked. On Windows a timed wait is on a high-resolution waitable timer set 300 us early, with a spin for the rest, so it ends a fraction of a millisecond late and not at the next 15.6 ms tick, and the system's timer tick is left alone ([ADR-133](../adr/133-timed-waits-on-windows-use-high-resolution-timers-with-a-short-spin-at-the-end.md)); before Windows 10 1803 the last 32 to 64 ms hold 1 ms system ticks (`timeBeginPeriod`, [ADR-132](../adr/132-timed-waits-ask-windows-for-1-ms-ticks-for-the-last-part-of-the-wait.md)) |
| `startChan(c, when, period, f)` | `gp::time::start_chan<Time>(c, when, period, f)`: arms a timer on the channel object `c` (a template over the element type, because the runtime does not know `time.Time`) |
| `startFunc(c, when, f)`, `stopTimer(c)`, `resetTimer(c, when, period)`, `trySend(c, v)` | `gp::time::start_func`, `stop`, `reset`, `try_send` |
| `callOnce(id, f)`, `getenv`, the file functions of the zone loader | `std::call_once`, `std::getenv`, C stdio |

A `*time.Timer` is `{C, r, initTimer}` and a `*time.Ticker` `{C, r, initTicker}`; `r` is the channel object
that carries the timer's record (`C` itself, a `gp::chan<Time>` with a buffer of one element and
`len == cap == 0`; for `AfterFunc` a channel that nobody uses). One thread, started with the first timer,
keeps the armed timers ordered by deadline: when one is due, it calls the Go function `sendTime(c, due)`
(a send that never blocks) or starts a goroutine for the `AfterFunc` function. The map holds a channel
timer weakly, so a `Timer`, `Ticker` or `After` channel that nothing holds is freed (and leaves the map)
although it was not stopped. A native takes only types of the runtime (`int64`, `string`, `[]byte`,
channels and funcs of them): a `Duration` is converted by a Go wrapper (`Sleep` calls `sleep(int64(d))`).

```go
t := time.NewTimer(50 * time.Millisecond)   // c := make(chan Time, 1); startChan(c, when(d), 0, sendTime)
fmt.Println(len(t.C), cap(t.C))              // gp::len(c), gp::cap(c): 0 0 (a timer channel)
<-t.C                                        // gp::recv(c): an ordinary receive; select works the same
```

A timer that is due is run by the receive, the non-blocking receive or the `select` poll that looks at its
channel (Go's `maybeRunChan`; ADR-041), so a timer whose deadline has passed is never "not yet". Divergences:
`LoadLocation` and `Local` read the system's zoneinfo
(`ZONEINFO`, `/usr/share/zoneinfo`, `/usr/share/lib/zoneinfo`, `/usr/lib/locale/TZ`, `/etc/zoneinfo`); there is
no embedded database (`time/tzdata`) and no `$GOROOT` zip.

Source: [Phase 08 §2.5](../../plans/2026-10-13-gocpp/phase-08-concurrency/README.md#25-sync-syncatomic-time-runtime),
[ADR-041](../adr/041-time-package-and-timers.md).

## `sync` and `sync/atomic`

Go's `sync` is written in `.gp` (`stdlib/sync`), over natives (`//gocpp:native`, ADR-027) that are
templates in `gocpp/sync.hpp` and `gocpp/atomic.hpp`; the design is [ADR-040](../adr/040-sync-on-a-semaphore-table.md).

```go
type Mutex struct {
	state int32
	sema  uint32
}

func (m *Mutex) Lock() { mutexLock(m) }

//gocpp:native gp::sync::mutex_lock
func mutexLock(m *Mutex)
```

```cpp
struct Mutex { int32_t state = 0; uint32_t sema = 0; /* ... */ static void Lock(gp::ptr<Mutex> m); };
void Mutex::Lock(gp::ptr<Mutex> m) { ::gp::sync::mutex_lock(m); }   // one CAS when the mutex is free
```

| Go | C++ |
|---|---|
| `var mu sync.Mutex`, `mu.Lock()` | `Mutex mu;` (a boxed `gp::ptr<Mutex>` when its address is taken: a method call is one), `Mutex::Lock(mu)` |
| `defer mu.Unlock()` | the usual `defer`; a deferred native can't be a function pointer (templates), so Go code writes `defer func() { onceSet(o) }()` |
| `mu.Lock` as a value | `gp::func<void()>` over a lambda that holds the pointer, as for any method value |
| `type C struct { sync.Mutex; n int }`, `c.Lock()` | the promoted method: `Mutex::Lock(gp::field_ptr(c, &C::Mutex))` |
| `var l sync.Locker = &mu` | an interface value holding the `gp::ptr<Mutex>`; `l.Lock()` is `icall` |
| `unlock of unlocked mutex` | `fatal error: sync: unlock of unlocked mutex`, exit code 2: `gp::detail::fatal`, not a panic |
| `wg.Add(-1)` below zero | `panic("sync: negative WaitGroup counter")`, a Go string |
| `atomic.AddInt64(&x, 1)` | `gp::sync_atomic::fn_add(p, int64_t(1))`: `std::atomic_ref`, sequentially consistent |
| `var n atomic.Int64`, `n.Add(1)` | `struct Int64 { int64_t v; }`, `gp::sync_atomic::ty_add(n, delta)` (no pointer to the field) |
| `atomic.LoadPointer(&p)` | `gp::sync_atomic::fn_load_pointer(p)`: a spin lock of a table of 64, keyed by the address |
| `atomic.Value` | `struct Value { uint32_t lk; gp::any v; }` with a spin lock |
| `atomic.Pointer[T]` (step 7.3) | `gp::atomic_ptr<T>` (a lock and a `gp::ptr<T>`) |

A blocked `Lock`, `RLock`, `Wait` or `Wait` of a `WaitGroup` parks the goroutine's thread on its own
`gp::waiter` through a table keyed by the address of the object's semaphore word, so the objects are plain
words (copyable, no destructor), and the goroutine counts as blocked (`gp::num_blocked`) with Go's reason
(`sync.Mutex.Lock`, ...) for the deadlock detector of step 8.11.

## `#line` and debugging

- Before every generated line whose `.gp` line is not "the previous line + 1", gocpp writes a
  `#line N "/abs/path/file.gp"` directive. So compiler errors and debuggers (gdb, lldb) point at
  `.gp` lines, and a breakpoint on a `.gp` line stops at the right place.
- The paths are absolute, so editors that match breakpoints by full path find the file. They are
  written as C string literals, so Windows backslashes are escaped (`#line 6 "C:\\work\\hello.gp"`).
- Your variable names stay the same in C++, so `print s` works in the debugger.
- The lines that have no place in the `.gp` source (the C++ `main` wrapper) get `#line`
  directives that point at the generated file itself, in the work folder; `gocpp emit` leaves
  them out.
- A C++ compile error in generated code is a bug in gocpp: `gocpp build` prints
  `internal error: generated C++ did not compile`, the compiler's first errors (at `.gp` lines,
  thanks to `#line`) and the work folder, which it keeps; it exits with status 2.

### The internal packages and their natives (step 9.2)

`stdlib/internal/*` ([PORT.md](../../stdlib/internal/PORT.md), [ADR-045](../adr/045-internal-shims-and-test-access.md)) are
lowered like `errors`. Where Go has assembly, the function is native (ADR-027) and its C++ takes the C++ types of the Go
parameters, by reference:

| Go (`internal/bytealg`) | C++ (`gp::bytealg::`, `gocpp/bytealg.hpp`) | Over |
|---|---|---|
| `IndexByte`, `IndexByteString` | `index_byte`, `index_byte_string` | `memchr` |
| `LastIndexByte`, `LastIndexByteString` | `last_index_byte`, `last_index_byte_string` | a backward loop (`memrchr` is a GNU function) |
| `Count`, `CountString` | `count`, `count_string` | 8-byte words without optimization, a loop the compiler vectorizes with it |
| `Equal`, `Compare`, `CompareString` | `equal`, `compare`, `compare_string` | `memcmp` (`Compare` gives -1, 0, +1) |
| `Index`, `IndexString` | `index`, `index_string` | `memmem` |
| `MakeNoZero` | `make_no_zero` | an array that is not zeroed (`gp::detail::new_array`); panics like `make` when `n` is negative |

A nil slice and the empty string have a null data pointer, which `memchr` and `memcmp` must not get, so each function
checks the length first. `internal/godebug`'s `env` (`gp::godebug::env`) and the handle table of `runtime/cgo`
(`gp::cgo::handle_new`, `handle_value`, `handle_delete`) are in `gocpp/shims.hpp`.
