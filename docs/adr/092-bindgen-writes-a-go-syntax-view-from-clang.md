# ADR-092: `gocpp bindgen` writes a Go-syntax view of a header from clang's answers

Status: accepted (2026-10-19). Builds on [ADR-060](060-typed-interop-probes.md) (the probe, used for the values
of macros) and [ADR-074](074-typed-interop-declarations-and-foreign-types.md) (the foreign view whose type words it
reuses); the contract is [docs/spec/typed-interop.md](../spec/typed-interop.md) §12.

## Context

Phase 12 §2.7 says that `gocpp bindgen <header>` "writes a readable gocpp **view** of a C/C++ header, as comments or a
stub file, for docs and the editor", like Zig's `translate-c` or `c-for-go`, and that "struct-valued macros are shown as
`var`, because Go constants must be basic types". The example is three comment lines. The text leaves open the form of the
output, how declarations are found, which of the included files count, what happens to namespaces, classes and templates,
and what a macro becomes. The exit criterion is that the output for `raylib.h`, `sqlite3.h` and `SDL.h` is reviewed.

## Decision

1. **A stub `.gp` file, in Go syntax, that `gocpp check` accepts and `gocpp fmt` keeps.** Not comments: a file can be
   checked, formatted, searched and opened in the editor, and a golden test can compile it. One package per header,
   named like an import of the header names it (`raylib`, `SDL`, `sqlite3`; `-pkg` when the rules give none, as for
   `<string.h>`). Functions have no body, methods too, so it is a description, not a program: names are the header's
   (`InitWindow`, field `x`), which Go does not export, so the package is not importable, and nothing builds or links it.
   The first line is `// Code generated by gocpp bindgen from <raylib.h>. DO NOT EDIT.`, where the header is spelled as the
   user wrote it (never a path of this machine). The text is formatted by `internal/format` before it is returned, so it is
   stable under `gocpp fmt` by construction.
2. **clang answers, nothing is parsed by hand.** Three runs of `clang++` on a file that only includes the header: the
   preprocessor with `-E -dD` (the macros, with the file of each, and the line markers that say which files the header
   includes), the JSON AST dump (the declarations), and the probe of step 12.2 for the type and value of each macro (and
   of each const variable, because clang does not fold `constexpr int n = 3 * 4` in the AST). A fourth, tiny run
   (`auto x = (RED);`) reads the initializer of the macros whose value is a struct. The dump of `SDL.h` is 446 MB (clang's
   own headers, glibc's inline functions, intrinsics), so `scanTU` cuts it into top-level declarations with a byte state
   machine (760 MB/s) and decodes only what matters (the declarations of the view, and every type that another declaration
   could name). clang prints a file name only where the file changes, so the scanner tracks it (a differential test
   replays the whole dump with `encoding/json`). `clang++` is required (`GOCPP_CLANG`); without it the command says
   so with the message of the other typed commands and exits with 3: there is no opaque mode of a view. `-std` is
   C++20 or newer (the probe's helpers need C++20, and gocpp compiles C++ in C++20).
3. **Which files are in the view** (`-scope`). The header, plus: the header that a wrapper stands for (libstdc++'s
   `<stdlib.h>` includes `<cstdlib>`, which includes the C library's file: same name, or `cX`/`X.h`); the parts of a
   header, in folders named `bits`, `asm`, `asm-generic` or `linux` that an in-scope file includes (that is where `<math.h>`
   declares its functions and `<errno.h>` its numbers); and in `auto` (the default) the headers of the same folder that
   an in-scope header includes (an umbrella header such as `SDL.h`), **except** when the header lies directly in a folder of
   the compiler's own include path (`/usr/include/zlib.h`), where its neighbours are the system's headers: then it is alone.
   `header`, `dir` and `tree` choose exactly. Anything else that the view uses is *referenced*: it is written, under its
   own heading, when a written declaration names it (`FILE` for `fopen`), by the same code as the rest, so every view is
   closed under what it mentions. Types that no header in reach declares (`std::string`, a template instance) become an
   empty struct with the C++ spelling as its comment.
4. **Namespaces are flattened with underscores** (`geo_Vec`, `outer_inner_Deep`; inline namespaces add nothing, unnamed
   ones are dropped, a comment says the C++ name). One file per namespace would have needed imports between them, and the
   names a Go-syntax stub could not resolve; one file keeps `gocpp check` honest. Collisions get a number; a struct, union
   or enum named like a function, variable or typedef gets cgo's prefix (`struct_stat`); Go keywords, `init` and the Go names the
   output uses get a trailing `_` (`type_`, `range_`).
5. **Types.** C numbers are `C.int`, `C.uchar`, `C.longlong`, `C.size_t`, `C.bool`, ...; fixed-width integers are Go's
   (`uint8`, `int64`, `uintptr`); `T*` is `*T`, `void*` is `unsafe.Pointer` (the import is added when needed), a function pointer
   is a func type (`func(C.int, *C.char) C.int`), `va_list` is `C.va_list`, C varargs are `...any`, `T&` is `*T`, arrays
   are `[N]T` (`[0]T` when unsized), `__int128` is `[16]byte`. Typedefs are aliases (`type Quaternion = Vector4`); a typedef that only names a tag
   is the tag (`typedef struct { ... } Color` is `Color`, `typedef struct Vec2 Vec2` is `Vec2`); forward declarations are
   `struct{}` with a comment. `const`, `noexcept`, default arguments, attributes and the C++ calling convention are not
   shown. Enums are an integer type over their underlying type (unsigned unless a value is negative or too large, as in C++, or
   the declared one) and a `const` block; the constants of a scoped enum carry the enum's name.
6. **Classes** are structs with their public data members and public bases embedded; public non-static, non-template,
   non-operator member functions are bodiless Go methods (a value receiver when `const`); constructors, destructors,
   operators, static members, conversions, member templates and overloads after the first are comment lines after the type;
   unions say so; bit fields say their width; anonymous unions and structs become `anonN` fields with their members written
   inside. Templates are one comment line each (`struct template geo::Box<typename T>`): Go has no spelling for them.
7. **Macros.** A macro whose value the probe reads as a number, bool, char or string is a `const`
   (`const BUFSIZ = 8192`); a float that is `float` is written as a float32 (`3.14159`, not `3.1415927410125732`); a macro
   of an enum type is a typed const (`MOUSE_LEFT_BUTTON MouseButton = 0`); a macro whose value is a struct is a **`var`**
   with a positional literal (`var RAYWHITE = Color{245, 245, 245, 255}`; nested structs, and fields that clang filled in,
   are read from the initializer; anything that is not a literal, a cast or a unary minus is not translated). Not
   translated, and listed by reason under "Not translated": function-like macros, pointers (`SQLITE_TRANSIENT`), values
   that are not constants, bodies that are not an expression, and macros that depend on where they are used (`__FILE__`).
   Not listed: empty macros, include guards, names that start with `__`, and the implementation macros of the C and C++
   libraries (`_GLIBCXX_*`, `_X` from a `bits/` file). `const` and `constexpr` scalar variables become consts when the
   compiler can evaluate them.
8. **Patterns.** `-include` and `-exclude` are regular expressions on the qualified C++ names of top-level
   declarations and macros (the enumerators of an unnamed enum are chosen one by one); a type that a written declaration
   uses is written whatever they say.
9. **Unnamed types, attributes, stand-ins.** An unnamed struct, union or enum is written inline under the declarators of the
   field, variable or typedef that has it (`entries [16]struct { ... }`, `*struct { ... }`); the text clang prints for it
   (`(unnamed struct at /path/x.h:13:18)`) is never written. Packed and aligned records say so and are listed as "layout
   differs"; `_Atomic(T)` is T with a comment; a typedef with no Go spelling (vector types, `_BitInt`) is a byte array of its size
   so that its users check, of the size the compiler gives (`sizeof`, with `// aligned(N)`). A struct macro's literal is built after the
   names are known and folds the operators and conversions of the tree with C's rules for the desugared type of each node (a random
   comparison with the compiler, `TestFoldFuzz`, is part of the tests); undefined behaviour is not folded but listed. A macro with
   the name of an enumerator (and another body) is listed, not written twice.
10. **The cache.** The macros' types and values come from the probe of 12.2, so they use its cache on disk (ADR-088) by
   default (`GOCPP_NOPROBECACHE=1` off, `Config.CacheDir` for tests); a hit runs no compiler, and the key has the
   headers' contents and the flags. The views do not change with the cache.
11. **Deterministic.** The order is the compiler's (the dump and the definition order of macros), referenced types
   sort by name, no run-dependent path or value is written (the probe's own file name in `__FILE__`-like macros is
   caught by its value), and the temporary folder is removed on every path.

## Consequences

- The output is a documentation and editor artifact. It is not a binding generator: nothing in it is imported, and
  phase 12's typed mode does not read it.
- C++ is described, not translated: templates, overloads, operators, constructors and references appear as comments or as
  `*T`; the view of `<vector>` is a list of what is not a template, plus one comment line per template. `-scope` and the
  patterns are the controls.
- A header that does not compile, or is not found, is an error with the wording of `gocpp check`'s header check.
- The tests pin the output with golden files per case (`testdata/golden`), the real headers of the zoo and the libraries
  (goldens guarded by a hash of the compiler and the files, so another machine compares nothing instead of failing), and a
  `gocpp check` and `gocpp fmt` of every view. Only clang 21 was available: the reader decodes the keys of
  `-ast-dump=json` that it needs and ignores the rest (the clang 17 to 21 comparison is step 12.12's), and a dump it cannot
  read is an error with the decoder's message.

## Not decided here

Windows headers (the view is of this machine's headers, as the probes of typed mode), comments and doc comments of the
header (clang's JSON has none without `-fparse-all-comments`), a mode that writes `//gocpp:` directives for the
libraries, and the editor's use of the view (step 12.13 builds its own index).
