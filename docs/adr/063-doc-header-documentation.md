# ADR-063: `gocpp doc` documents C/C++ headers from their Doxygen comments, read as text

Status: accepted (2026-10-18). Step 13.4 ([Phase 13](../../plans/2026-10-13-gocpp/phase-13-tooling/README.md)).

## Context

`go doc` shows the documentation comments of a package. A gocpp program also imports headers
(`import "<stdio.h>"`, `import "./physics.h"`) and C++ namespaces (`import "::std::chrono"`). They are
opaque packages: gocpp does not parse them, the C++ compiler checks every name when the program is
built. `gocpp doc` has to say something about them, and the answer must not need a C++ parser (the
Phase 12 typed probes ask the compiler one question at a time; they do not read a header).

## Decision

- **Doxygen comments are the documentation.** For a header file the command reads the comments
  `///`, `//!`, `/** */` and `/*! */` that stand directly above a declaration, with a **line
  reader and regular expressions**, not a parser. A declaration is the text from the comment to the
  first `;` or `{`; its name is guessed from its shape (function, `struct`/`class`/`enum`/`union`,
  `using`, `typedef`, `#define`, variable). A declaration that the reader cannot make sense of is left
  out, and a comment with no declaration right below it (a blank line is enough) documents nothing.
  Only the header file itself is read, not the headers it includes.
- **The compiler answers what the comments cannot.** `gocpp doc <vector> std.vector` asks the existing
  kind probe (namespace, type, template, value, macro, not found) and the finder of the header file
  through `Env.Probe`; tests replace it with a fake. `<name.h>` that the compiler does not find is an
  error (exit 1); a compiler that fails is told in the text, since the header may exist.
- **Windows-1252.** A header that is not valid UTF-8 is read as Windows-1252, the usual encoding of old
  headers; there is no other detection.
- **`std` and `::ns` are not packages.** `gocpp doc std` prints a fixed text (a namespace needs no
  import; ask with a header) instead of guessing the names.
- **Derived methods come from fixed tables.** The methods that `#Derive(String | Equal | Clone | JSON)`
  generate exist in no `.gp` file; `internal/doc/derive.go` holds their signatures as a table and
  lists them with the comment "generated by #Derive(...)". A change to the derives has to change the
  table (the tests list the signatures).
- **`#Derive` on a type group is not shown.** The spec says `#Derive` goes "on top of a type"; the
  documentation lists derived methods for the macro lines above a single `type T ...` declaration
  only; the macro line above a group is not printed either (golden `derive-on-type-group`). When the expander defines what a group
  means, `derive.go` follows it.
- **Build constraints are the compiler's.** Files are chosen by `load.MatchFile`, the rule of the
  loader for the compiler `gocpp` (the tags `gc` and `cgo` are false). A file that needs `cgo` is
  hidden, which `go doc` does not do.

## Alternatives

- **Parse the header with libclang or the compiler's AST dump.** Complete and exact, but a C++ front
  end in the doc command, slow (one compiler run for each header, more for the includes) and not
  available in the editor without a toolchain. Rejected for now; the probes stay for single names.
- **Show nothing for a header.** Simple, but a header's own comments are the only documentation its
  functions have, and the users of `gocpp doc` ask for them.
- **Guess the encoding with a library.** More cases, one more dependency, for a rare file.

## Consequences

- The header documentation is partial by design: undocumented declarations do not appear, a
  declaration the reader misreads (a macro that expands to a declaration, a name in a complicated
  declarator) has a wrong name or is missing. The text of the command says the package is opaque.
- No C++ parser is needed, so it works in an editor and with no compiler, apart from the kind probe.
- The derived-method tables can drift from the expander; a test per derive keeps the signatures.

## Evidence

`internal/doc/header_test.go` (comment forms, CRLF, Windows-1252, unterminated and nested comments),
`internal/doc/testdata/golden/header-*.txt`, and the review of step 13.4 that found the multi-line
comment bug a line reader is prone to.
