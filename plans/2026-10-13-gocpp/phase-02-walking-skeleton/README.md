# Phase 02: Walking Skeleton (hello world end-to-end)

> Build the thinnest possible path through **every** layer: `.gp` → typed AST → C++ →
> native binary → run. Support only a tiny subset of the language, but do it properly with
> tests, `#line` debugging and both compilers. Every later phase widens this path.

| | |
|---|---|
| Depends on | Phase 01 |
| Unlocks | Phase 03, Phase 13 (it builds on the `#line` mapping) |
| Milestone | **M1: `gocpp run hello.gp` prints "hello"** |
| Size | medium (about 2–3 weeks) |
| Progress | [STATE.md](STATE.md) |

---

## 1. Idea

Finish an end-to-end path early, before going wide. Once one tiny program works from
source to binary:
- the architecture is proven (or its problems show up early, when they are cheap to fix);
- the test harness from Phase 00 starts producing real signal;
- every later feature is "add a case to an existing pipeline", never "build a new pipeline".

**Supported subset in this phase:** `package main`, `func main`, functions with parameters and
multiple results, basic types (`bool`, `int*`, `uint*`, `float32/64`, `string`), `const`
(including `iota`), `var`, `:=`, assignments (including `a, b = b, a`), all arithmetic,
comparison and logical operators, `if/else`, all `for` forms (including `for i := range 10`),
`switch` (expression and tagless, `fallthrough`), labeled `break`/`continue`, `goto`, string
concatenation, `len(string)`, the builtins `print`/`println`/`panic`, and `fmt.Print/Println/
Printf` for basic types. Everything else fails with "not supported yet (Phase NN)" (the
Phase 01 gates).

Small as it is, this subset already contains several places where Go and C++ disagree. The
audit found them by running the same code through Go and through both C++ compilers, and the
rules below handle them.

## 2. How it works

### 2.1 Example

```go
// hello.gp
package main

import "fmt"

func add(a, b int) (int, bool) {
	return a + b, a+b > 10
}

func main() {
	s, big := add(7, 5)
	fmt.Println("hello, gocpp", s, big)
}
```

`gocpp emit hello.gp` prints:

```cpp
// hello.gp.cpp: generated by gocpp, do not edit
#include <gocpp/rt.hpp>

namespace gpkg_main {

std::tuple<int64_t, bool> add(int64_t a, int64_t b);   // prototypes first:
void main();                                           // Go doesn't care about order, C++ does

#line 6 "/home/me/hello/hello.gp"
std::tuple<int64_t, bool> add(int64_t a, int64_t b) {
#line 7 "/home/me/hello/hello.gp"
    return {a + b, a + b > 10};
}

#line 10 "/home/me/hello/hello.gp"
void main() {
#line 11 "/home/me/hello/hello.gp"
    auto gp_t0 = add(7, 5);
#line 11 "/home/me/hello/hello.gp"
    int64_t s = std::get<0>(gp_t0);
#line 11 "/home/me/hello/hello.gp"
    bool big = std::get<1>(gp_t0);
#line 12 "/home/me/hello/hello.gp"
    gp::fmtshim::Println("hello, gocpp"_gs, s, big);
}

} // namespace gpkg_main

int main(int argc, char** argv) {
    return gp::run_main(argc, argv, nullptr, &gpkg_main::main);
}
```

Then `gocpp run hello.gp` compiles it and prints `hello, gocpp 12 true`.

Three details in this output are deliberate (all found by the audit):
- **`#line` is repeated** before every generated line whose `.gp` line is not "the previous line
  + 1". Without the repeats, the three lines generated for Go line 11 would be mapped to lines
  11, 12 and 13, and a breakpoint on line 12 would stop before `s` is assigned.
- **`#line` uses absolute paths.** The C++ is compiled in a work directory. With a relative
  path, the debug info says `hello.gp` relative to that directory, and editors (VS Code) that bind
  breakpoints by full path can't match it. The path is written as a C string literal, so a
  Windows path's backslashes are escaped (`#line 6 "C:\\work\\hello.gp"`); the test also covers a
  path with spaces.
- **Package namespaces are flat** (`gpkg_main`, `gpkg_fmt`), never nested under `gpkg::`. Inside
  a nested `gpkg::main`, the C function `time()` would be hidden by the package namespace
  `gpkg::time` (Phase 06 has the full naming rule).

### 2.2 Backend structure (`internal/cppgen`)

The emitter walks the **typed AST** (`go/ast` + `types.Info`) and writes C++ through a small
writer. There's no separate IR yet; Phase 03 adds a lowering pass in front when the rewrites get
complex.

| File | Job |
|---|---|
| `writer.go` | Indentation, and `#line N "/abs/file.gp"` before each generated line whose mapping is not "previous + 1" |
| `names.go` | Identifier mangling: C++ keywords get a `_` suffix (`new` → `new_`, `class` → `class_`; the list includes words that are keywords or operators in GCC's and Clang's C++ mode, such as `_Pragma` and `_Complex`); user names starting with `gp_` also get a `_` suffix (generated names never end in `_`, so they can't clash); a method named like its type (`func (U) U()`, which C++ would read as a constructor) becomes `U_`; other names C++ reserves (`_X`, `a__b`) stay as written, because GCC and Clang accept them even with `-Wall -Wextra -pedantic` (checked; only Clang's opt-in `-Wreserved-identifier` warns), and `gocpp vet` warns about them; names that are **macros** in the headers the runtime includes (`EOF`, `errno`, `assert`, `stdin`, `stdout`, `stderr`, `NULL`, `EINVAL`, `ENOENT`, `EAGAIN`, `SEEK_SET`, `BUFSIZ`, …) get a `_` suffix. Without that, `io.EOF` would not compile; Phase 04 extends this list from the user's own headers |
| `names.go` (shadowing) | A Go declaration that uses the name it declares, like `v := v` or `x := x + 1`, gets a new C++ name (`v_1`). In C++ the new name is already in scope inside its own initializer, so `int64_t v = v;` would read garbage (seen in the audit) |
| `types.go` | gocpp type → C++ type spelling (basic types in this phase) |
| `expr.go`, `stmt.go`, `decl.go` | Expressions, statements, declarations |
| `file.go` | Prologue (`#include`s), namespace, prototypes, the C++ `main` wrapper |

Compiler-made temporaries always start with `gp_` (`gp_t0`), so they can never collide with user
names. That is also why user names starting with `gp_` are escaped.

### 2.3 Expressions: the important rules

- **Constants are pre-computed.** If `info.Types[e].Value` is set, emit the folded value from
  `go/constant` as a C++ literal of the final type (`go/types` already records the type an
  untyped constant converts to). For example `1 << 62` becomes `INT64_C(4611686018427387904)`.
- **String literals** become `"..."_gs` (a `gp::string` pointing at static storage, no
  allocation). Printable ASCII is written as-is, every other byte as a 3-digit octal escape
  (`\303\251`). Never use `\x`: in C++ it is greedy (`"\x41BC"` is ONE character).
- **Go-only operators:** `a &^ b` → `a & ~b`, `^x` → `~x`.
- **Small integer types are cast back.** C++ converts `int8`, `int16`, `uint8`/`byte` and
  `uint16` operands to `int` before doing arithmetic, so results that should wrap don't. With
  `a, b uint8 = 200, 100`, Go says `a+b > 250` is false (it wraps to 44), and the direct C++ says
  true. So every `+ - * / % << >> & | ^ &^`, unary `-` and `^` on these four types is wrapped in a
  cast to the Go type: `uint8_t(a + b)`. (`-fwrapv` doesn't help here: there is no overflow in
  `int`.) Differential tests cover the common idioms, such as `s[i]-'0' <= 9`.
- **Signed overflow wraps** like Go because every compile uses `-fwrapv`.
- **Division and modulo** call `gp::div(a, b)` / `gp::rem(a, b)`, which return the Go type. They
  panic on zero, and `MIN / -1` gives `MIN` and `MIN % -1` gives `0` (Go defines both; C++ makes
  them UB/SIGFPE). Plain `/` is emitted only when the divisor is a constant other than `0` and
  `-1`.
- **Shifts** call `gp::shl/shr(x, n)`, which handle `n >= width` (Go gives 0, or -1 for a
  negative signed `>>`; C++ makes it UB) and panic on a negative `n`. A plain `<<` is emitted
  when `n` is a constant below the width.
- **Float → int conversion** uses `gp::f2i<T>(x)`. Out-of-range values are UB in C++ and
  implementation-specific in Go, so we copy Go on amd64, per type: `int64` and `int32` give
  their MIN value (`int64(f)` with `f := 1e300` is `-9223372036854775808`); `int16`, `int8`,
  `uint16` and `uint8` convert through `int32` and then truncate (`uint8(f)` with `f := 300.0` is
  `44`; `int16(3e9+7)` is `0`, as the CVTTSD2SL instruction gives MIN for out-of-range values);
  `uint32` converts through `int64` and truncates; `uint64` uses Go's two-range algorithm (checked
  against real Go 1.25 on amd64 by job 2.7). Go on arm64 saturates instead,
  so these cases run in the differential tests only on amd64.
- **`fmt.Println` float output** follows Go's `%v` rules exactly: shortest round-trip digits
  from `std::to_chars`, then exponent form when the decimal exponent is < -4 or >= 6. Verified
  with Go 1.25.7: `123456.0` → `123456`, `1000000.0` → `1e+06`, `1234567.0` →
  `1.234567e+06`, `0.0001` → `0.0001`, `0.00001` → `1e-05`. Special values print as Go does:
  `+Inf`, `-Inf`, `NaN` (`std::to_chars` would write `inf`/`nan`). (The `1e21` cutoff people
  remember is from `encoding/json`, not `fmt`.)

### 2.4 Statements: the important rules

| Go | C++ |
|---|---|
| `x := e` | `int64_t x = e;`: user variables get explicit C++ types; only compiler temporaries and opaque C values (Phase 04) use `auto` |
| `var x T` | `T x{};` (value-init = Go zero value) |
| `a, b = b, a` | `{ auto gp_t0 = b; auto gp_t1 = a; a = gp_t0; b = gp_t1; }`: Go evaluates the whole right side first |
| `a, b := f()` | `auto gp_t = f(); T0 a = std::get<0>(gp_t); …` (also handles `a, err := …` when `err` exists) |
| `if x := f(); x > 0 {…}` | `{ int64_t x = f(); if (x > 0) {…} }`: the extra block keeps Go's scope |
| `for cond {}` / `for {}` | `while (cond) {}` / `for (;;) {}` |
| `for i := range 10` | a hidden counter: `for (int64_t gp_i = 0, gp_n = 10; gp_i < gp_n; gp_i++) { int64_t i = gp_i; … }`. Since Go 1.22, assigning to `i` in the body does **not** change the iteration (`for i := range 5 { print(i); i += 2 }` prints `0 1 2 3 4`); a plain `i++` loop would print `0 3` |
| 3-clause `for` whose post isn't one C++ expression (`i, j = i+1, j-1`) | `for (init; cond;) { { body } gp_cont_N:; post; }`, and `continue` → `goto gp_cont_N`. The body sits in **its own block**, so the `goto` never jumps over a variable's initialization (C++ forbids that) |
| `switch` | evaluate the tag once, find the index of the first matching case **in source order** (cases evaluated lazily, like Go), then a native C++ `switch` on that index. `fallthrough` → `[[fallthrough]];`, and `break`/`continue` just work. Integer tags with constant cases can switch directly |
| `break L` / `continue L` | `goto L_break` / `goto L_continue`, with the loop body in its own block before the label |
| `goto L` | C++ `goto`; every statement's temporaries are wrapped in `{ }`, so a Go `goto` over a plain statement never jumps over a C++ initialization |
| `return a, b` | `return {a, b};` (`std::tuple` list-initialization, evaluated left to right) |

### 2.5 Evaluation order (minimal version, here already)

Go evaluates function calls, method calls and channel operations in an expression **left to
right**. C++ leaves function arguments and most operands unordered, and the two compilers
really differ. The audit measured: `fmt.Println(next(), next())` prints `1 2` in Go and with
clang++, but `2 1` with g++. `g(x, f())`, where `f` increments `x`, gives `2 2` in Go and g++
but `1 2` with clang++.

So this phase already has a small ordering pass, not Phase 03. Calls are moved into
`gp_` temporaries in Go's order whenever a neighbouring operand is neither a constant nor a local
variable that can't change. That matches what Go's compiler does. Loop conditions, `else if`
conditions and `case` expressions can't move their temporaries above the whole statement,
because they run many times or only sometimes. Each has its own shape (the condition becomes a
small block inside the loop or branch). Phase 03 extends the pass to every construct.

### 2.6 Runtime v0 (`runtime/include/gocpp/rt.hpp`)

Small, but the API shape is final so later phases only grow it:
- `gp::string` (minimal): literal, concatenation, comparison (`<=>`), `len`, byte index `s[i]` (in the Phase 02 subset; slicing `s[a:b]` is Phase 03), print.
- `operator""_gs`, the integer helpers (`div`, `rem`, `shl`, `shr`, `f2i`, all returning the Go type).
- **`panic` is a C++ exception from the start:** `throw gp::panic_error{...}`. `gp::run_main`
  catches it, flushes stdout, prints `panic: msg` + `goroutine 1 [running]:` and exits with
  code 2, like Go. Using an exception now means the `defer` of Phase 03 can run during a panic
  without changing any call site later.
- builtins `print`/`println` write to **stderr** and use Go's *runtime* number format, which is
  different from `fmt`. Verified with Go 1.25.7: `println(1.5, 3.0, -0.25, 'x')` prints
  `+1.500000e+000 +3.000000e+000 -2.500000e-001 120`, and a nil pointer prints `0x0`.
- **Output order like Go:** Go's `os.Stdout` is not buffered, so `fmt.Print` to stdout, `println`
  to stderr and a panic message appear in the order they happen. Each `fmt` call is one `write`
  (or at least stdout is flushed before every stderr write, panic and exit). The audit showed
  that buffered C++ stdio prints `b, panic, a, c` where Go prints `a, b, c, panic`. A test pipes
  both streams into one and checks the order.
- `gp::fmtshim::Print/Println/Printf`: variadic templates for basic types, with the `Printf` verbs
  `%v %d %s %t %f` (Phase 03 adds width and precision, `%+v`, `%q` and the `Sprint` family).
  This is a stand-in until the real `fmt` (Phase 05 needs `any`, Phase 09 completes it).
- `gp::run_main(argc, argv, init, main)`: stores args (for `os.Args` later), runs init, runs main,
  catches panics, exits 0.
- **Portable from day one** (Linux and Windows are the targets, your decision): the runtime
  calls the operating system only through one small layer, `runtime/src/os/` (write to a file
  descriptor, exit, arguments, environment; threads come in Phase 08), with a Linux version now and
  a Windows version in Phase 14. Everything else uses standard C++ (`std::chrono`, `<atomic>`,
  `std::filesystem`). A CI check fails if a POSIX header appears in the runtime outside that
  folder (the standard library's own per-OS files are a separate, allowed place).

### 2.7 The driver

```
gocpp build [-o out] [file.gp | dir]   # transpile + compile
gocpp run [file.gp | dir] [args...]    # build to a temp dir, run, forward the exit code (a dir = a package, like `go run .`)
gocpp emit file.gp                     # print the generated C++
   -x       print every command (like go build -x)
   -work    keep the work directory and print its path
   -asan    build with AddressSanitizer + UBSan (-fsanitize=address,undefined
            -fno-omit-frame-pointer), for the sanitizer runs from Phase 03 on
```

- **Compiler detection:** `GOCPP_CXX` → `CXX` → `clang++` → `g++` in `PATH`; check versions
  (Clang ≥ 17, GCC ≥ 13). Phase 01 already has the finder (`build.FindCXX`, for the namespace
  probe); this phase adds the version check and the flags. A compiler named in `GOCPP_CXX` or
  `CXX` that doesn't exist is an error (no fall-back). To decide here: whether `CXX` may carry
  arguments (`ccache g++`), split like cmd/go splits `CC`. The process-group handling of the
  probe (`internal/interop`) moves to `internal/build` for the real compiles. For **clang only**, add `-Qunused-arguments` (NixOS wrapper noise, seen
  in the spike). g++ rejects that flag (`unrecognized command-line option`, verified), so flags
  must be chosen per compiler family.
- **Flags (debug default in this phase):** `-std=c++20 -fwrapv -fno-strict-aliasing
  -ffp-contract=off -g -O0 -I<runtime>`. `-std=c++20` (not `gnu++20`) avoids predefined macros
  like `linux`/`unix` colliding with gocpp names. The driver always passes an explicit `-O`
  level, because a Nix shell's compiler wrapper turns on "hardening" by default, which silently
  makes a missing `-O` into `-O2`. The same hardening warns about `_FORTIFY_SOURCE` at every
  `-O0` file, and a `-U_FORTIFY_SOURCE` flag doesn't help: the wrapper adds
  `-D_FORTIFY_SOURCE` (3 with gcc, 2 with clang) again *after* the user's flags (checked with both compilers). So a tiny
  runtime header, `gocpp/nofortify.h`, holds `#if !defined(__OPTIMIZE__)` /
  `#undef _FORTIFY_SOURCE` / `#endif`; `gocpp/rt.hpp` includes it before anything else, and the
  user's own C/C++ files (Phase 04) get it with `-include`, which works whatever the command
  line says (checked, also with `-Werror`). The project's own dev shell turns hardening off, so a driver test sets
  `NIX_HARDENING_ENABLE` to nixpkgs' default list itself to check this.
- **Runtime files** are embedded in the `gocpp` binary (`go:embed`) and extracted once to
  `$XDG_CACHE_HOME/gocpp/rt/<version>/`. A `//go:embed` pattern can't reach a parent folder, so a
  tiny Go package inside `runtime/` (`runtime/files.go`, package `rtfiles`) holds the directive,
  and the driver imports it (the same trick for `stdlib/`, Phase 01).
- **C++ compile errors** in this phase are always gocpp bugs, since there is no interop yet. Print
  "internal error: generated C++ did not compile", the first errors (already pointing at `.gp`
  lines thanks to `#line`) and the work dir path.

### 2.8 Debugging works from day 1

Because of `#line`, `gdb ./hello` → `break hello.gp:12` → `run` → `print s` works, with
variable names unchanged. A test checks this with gdb in batch mode
(`gdb -batch -ex 'break hello.gp:12' -ex run -ex 'print s'`), and a second check reads the line
table (`objdump -l`) to make sure every generated line maps to the right `.gp` line.

## 3. Steps

1. **2.1 Emitter skeleton**: writer with `#line` (absolute paths, repeated where needed),
   prologue, flat namespace, prototypes, main wrapper.
2. **2.2 Names**: C++ keywords, reserved names, the runtime's macro names, `gp_` temporaries,
   shadowing renames (`v := v`), per-scope collisions + tests.
3. **2.3 Expressions**: constants via `go/constant`, string literal escaping, operators with the
   small-integer cast rule, calls, conversions, the integer and float helpers.
4. **2.4 Statements**: declarations, assignments (including parallel), `if`, `for` (all forms, with
   the hidden range counter and blocks before labels), `switch` via case index, labels, `goto`,
   `return`.
5. **2.5 Minimal evaluation-order pass** (§2.5), including the loop-condition / `else if` / `case`
   shapes.
6. **2.6 Functions**: parameters, multiple results via `std::tuple`, prototypes.
7. **2.7 Runtime v0** (§2.6, including the OS layer and the "no POSIX outside it" check) + its own
   C++ unit tests (a tiny test file compiled with both compilers).
8. **2.8 Driver**: `build`, `run`, `emit`, `-x`, `-work`, `-asan`, compiler detection, embedded runtime.
9. **2.9 Error path**: internal-error reporting for C++ compile failures.
10. **2.10 Tests**: run tests for the subset, 3 golden tests, differential tests vs real Go
    (small-integer wrapping, division and `MIN/-1`, shifts, float printing incl. `+Inf`, float →
    int on amd64, string ops, switch/fallthrough, labels and `goto`, `v := v`, call order,
    stdout/stderr order).
11. **2.11 Debug test**: gdb batch test + line-table check (§2.8; skip gdb if missing).

## 4. Deliverables

- `internal/cppgen` (subset), `runtime/` v0, `cmd/gocpp` with `build/run/emit`
- At least 25 run tests and 25 differential tests, passing on GCC 15 and Clang 21
- Examples `hello`, `fizzbuzz`, `primes` passing

## 5. Exit criteria

- `gocpp run examples/hello` (and `gocpp run .` inside that folder) prints the expected text on both compilers.
- All subset run tests and differential tests pass on **both** compilers (they must agree with
  Go, and therefore with each other, on evaluation order).
- gdb stops at a `.gp` line and prints a local variable; the line table maps every generated
  line to the right `.gp` line.
- `gocpp emit` output for the 3 golden programs is reviewed and readable.
- Every unsupported feature produces a clear phase-gate error, never broken C++.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Polishing the skeleton forever | Strict subset; everything else stays behind the Phase 01 gates |
| Go and C++ disagree in small ways (promotion, order, shadowing, UB) | Rules in §2.3–2.5 come from running the same code in Go and both compilers; differential tests on every rule |
| GCC and Clang disagree | Run every test on both from day 1 |
| `#line` confuses errors that point at generated-only code | Map them back to the closest `.gp` line or report as an internal error with the generated file |
